### 1.2 关键突破：内核 msgbuf 从 128 KiB 提到 1 MiB

`[源码+实测]` `config/MASTER:286`（`msgb_small` 行）`CONFIG_MSG_BSIZE_DEV` 131072 → **1048576**。

**为什么必须**：`headset` 初始化在 **19.97 秒**，而 128 KiB 的 msgbuf 只保留最近约 24 秒
（`subr_log.c:570` 写满归零覆盖），所以一直被吞掉。提到 1 MiB 后日志起点从 24.18 秒
提前到 **19.66 秒**，`headset` 输出就出来了。

**安全核实** `[实测]`：`MAX_MSG_BSIZE` 就是 1 MiB；**BSS 增长 917504 字节 = 缓冲增长，
精确相等**（链接器腾了空间，没覆盖别的对象）。

### 1.3 705 卡在哪

```
HP verify failed at 0x260b wanted 0x9f got 0x1f        （两次）
HP shutdown incomplete; analog off was NOT confirmed
restored 36 configuration bytes: incomplete
```

`0x260b` = `MT6368_ZCD_CON3`（`mt6368.h:418`，过零检测）。baseline `0x1f`，想写 `0x9f`，
**只差 bit7，写两次都读回 `0x1f`** `[实测]`。

**`HP preconditions` 记录了 `CLKSQ=0x00`、`NCP=0x00`** `[实测]` —— 时钟与负压泵都没开。

`[DSH推断]` 这可能就是写不进去的原因（ZCD 是模拟模块，需要时钟）。
**但这是推断，不是结论** —— 由 Codex 侧判定。

### 2.3 主线告诉我们什么

`mt6895.dtsi:2743-2757` 注释 `[源码]`：主线也卡在 `panthor_fw_ping_work()`，
根因是 BG3D 时钟被 `clk_disable_unused()` 关掉，表现为 **SError**。

**我们连 `GLOBAL_IF` 都没等到，比它更早** —— 但**这只是「没达到它出错时的阶段」，
不能推出「我们的取指没发生」**（这条我错过一次，见 §4）。

### 2.4 GPUEB IPI：补丁就绪，但两次试验失败

**主线在 `media,mt6895` 上强制要求** `[源码]`（`panthor_fw.c:1131-1146`）：
写 `MCU_CONTROL=AUTO` **之前**调 `mt6895_gpueb_power_on()`，失败就 `return` 不启动 MCU。

**补丁早已存在**（`docs/headset-wip/findings/GPUEB-INTEGRATION-PATCH.md`，1130 行），
我已修好它的上下文偏移，**能 `git apply` 且能编译** `[实测]`。

**但 trial 703/704 两次都失败**：日志只有 735 字节。

🔴 **735 字节不是「XNU 早期就死」** —— 它是 `logbook_boot_note()` 在 `jump_to_kernel`
之前预写的记录（`mtkloader.c:1937`，`:2054` 传 `reason=0xfeedface`，`:3777` 调用）。

**判据**：`reason = 0xfeedface` = loader 预写、内核没回来；`reason = 0x0` = 正常返回。
701/705 都是 `reason = 0x0` `[实测]`。

**所以我们不知道 XNU 在 703/704 跑到了哪一步。**

⚠️ **而且 SRAM 地址有陷阱**：补丁注释说「三窗口都在 `gpueb_base` 外」是**错的** ——
`mbox0_base`（SRAM，`0x13c5fd80`）落在 `gpueb_base`（`0x13c40000 + 0x22000`）**之内** `[源码]`。
四个控制寄存器 `0x13c62000/04/74/78` 才在边界外。

**`mali610.c:4296-4302` 警告**：读一个门控未开的 MTK 外设**不返回错误，访问永不完成，
看门狗复位板子**。所以「先试一次」的代价被低估了。

## 4. 🔴 给下一个 Codex 的警告：DSH 会犯什么错

**今天 DSH 被纠正了至少 8 次。以下是最典型的，请优先怀疑这些：**

| 错误 | 实例 |
|---|---|
| **二进制语义读错** | `regmap_update_bits(map, reg, **mask=w2**, **val=w3**)` 的 mask/value 顺序反了，45 步表一半是错的 |
| **从「没有证据」推因果** | 735 字节 → 「XNU 早期就死了」（实际是 loader 预写） |
| **硬件块搞混** | `0x2508–0x2537` 当成 `AUDDEC`，实际是 `AUDENC` |
| **把清单项当缺口** | 「interconnect votes 缺」—— 主线 GPU 节点根本没有 `interconnects` |
| **镜像对判据虚构** | 7 对「镜像寄存器」实际是独立 `CON` 配置项 |
| **锚点语义错** | `0x231d = 0x06` 不是自检值，是 MFD 按 IRQ 申请置的使能位 |

**共同点：凡是要从二进制或硅片细节推出精确结论，DSH 不可靠。**

**分界（2026-11-15 已定，见 `docs/headset-wip/TEAM-SPLIT.md`）：**

| Codex 独占 | DSH 独占 |
|---|---|
| 二进制反汇编与语义提取 | 广域信息搜集 |
| 寄存器语义 / 位域 / 时序 | 下载物核验 |
| 硬件块归属判断 | 日志取证（提取、sum 校验、字段解析） |
| 驱动代码 | 实验打包（单变量、hash 链） |
| 架构决策 | 设备操作与恢复、判据工具化、文档 |

**关键：DSH 不再「先提取再送 Codex 复核」** —— 那会多花一整轮。
反汇编任务只给 `objdump` 命令和函数地址，Codex 自己提取。

**DSH 仍做交叉验证，但换领域**：查你引用的公开源码是否真存在且是那个版本、
查你说的日志行是否真在日志里、查你改的代码是否真编译过且产物 hash 对不对。
**不验证二进制反汇编和寄存器语义。**

### 刷机七步（已跑 9 次，Android 每次都需要用户手动回 fastboot）

1. 记原厂 `boot_a` md5，与备份比对
2. **清 logbook**：`dd if=/dev/zero of=/dev/block/by-name/xnusys bs=1 seek=2676981760 count=8388608 conv=notrunc`
3. `adb reboot bootloader` → **用 `fastboot flash` 实测，不要只看 `getvar`**
4. `fastboot flash boot_a <img>` → `fastboot reboot`
5. XNU 跑约 150 s，**尽力**链回 Android
6. 回 Android 立刻取 logbook：`HLOG @ 0x9f8f8000`，字段：`len@8`、**`reason@16`**、`sum@64`
7. **无论结果如何都刷回原厂并验证 md5**

**Android 每次都会卡住**（`surfaceflinger` 崩 38 次、`boot_completed` 未置位），
已连续 **九次**。**用户手动回 fastboot 是标准流程。**

### 🔴 logbook 判读（今天踩过坑）

| 现象 | 含义 |
|---|---|
| `reason = 0xfeedface` + `len = 735` | **loader 预写，内核没回来** |
| `reason = 0x0` | **正常返回**，日志是真实内核输出 |
| 日志以 `mtkloader:` / `boot args:` / `clock:` 开头 | **那是 loader 的 boot note，不是 XNU 输出** |
| 日志以 `cpu 0 (phys id 0x0) is a slower core` 开头 | XNU 正常输出了 |

**校验**：body 在 `+4096`，8 位加法和等于 `sum@64`。
