# 里程碑 6a · 主机写入演练（Trial748）

2026-11-21。**全部在主机上，未上机。** 真机仍是原厂。

## 用的是内核自己的写入器

`bsd/miscfs/apfs/apfs_write.c` 里已有 `apfs_write_in_place()`：替换已有文件里的一段字节，
不改长度、不改 extent、不动任何元数据。它已经编进内核，但**没有调用者**——文件里就是这么写的。

阶段 6 要求的"先在可丢弃的主机镜像上演练"，演的就是它，不是另写一个。

## 四项演练

镜像是 `mkapfs.py` 造的 4 MiB 小卷，里面有 12288 字节的 `sub/target.bin`（3 个整块）
和 8192 字节的 `sub/other.bin`。内容用随机字节，因为 `mkapfs` 对可压缩内容会存进属性而不是数据块，
那样就没有数据块可写。

**一、写入**

```
write_in_place -> 0  first=96 blocks=1 bytes=4096 partial=0 calls=1
reread 12288 bytes, head=TRIAL747
verdict: MATCH
```

写 4096 字节，落在第 96 块。回读后前 8 字节是 `TRIAL747`，其余部分与原文件逐字节相同。

**二、只有那一块变了**

把写前写后的 4 MiB 镜像逐块比对：

```
有差异的块: 1 个 -> [96]
```

整个容器里只有那个文件自己的数据块变了。超级块、对象映射、文件系统树、其他文件，
一个字节都没动。这是 `apfs_write.c` 的设计意图，这里量到了。

**三、撕裂**

把第 96 块造成"前 2048 字节新、后 2048 字节旧"，模拟写到一半断电：

```
nx_open -> 0
vol_open -> 0
inode_get -> 0 size=12288
read_stream -> 0, 12288 of 12288 bytes
```

**卷照常挂载，树和校验全过，文件读得出来**，内容是新旧混合。这正是文件里写的那个唯一损失形态，
而不是文件系统损坏。

**四、恢复**

用同一个写入器把原始内容写回去：

```
restore write -> 0 blocks=3
recover 与原始镜像差异块: 无
完全一致: True
```

撕裂的镜像恢复后与原始镜像**逐字节相同**。

## 建主机版的几处障碍

- `apfs_lib.h` 要 `<time.h>`，主机侧加一个 prelude 头解决。
- Ubuntu 的系统头定义了 `ARCH_X86_64`，libdeflate 据此去找 `x86/decompress_impl.h`——那个目录
  在这个内核树里不存在（内核只编 arm64，上游从没生成过）。在临时副本里把那两处 include 换掉，
  走可移植 C 实现。**没有改内核源码。**
- `SHA256` 是内核加密库的符号。用桩顶替，并且刻意选了未密封的卷——真被调用就会打印警告。
- 需要链接 `apfs_deflate.c`、`apfs_zbitmap.c` 和 `-lz`。
