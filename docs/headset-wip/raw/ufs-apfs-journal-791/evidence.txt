The journal header is in host byte order, and that is correct
-------------------------------------------------------------
Read as big-endian the magic looks like 0x784c4e4a, i.e. reversed. It is not a bug:

      hfs_journal.c:783   swap_journal_header() uses OSSwapInt32/64
      hfs_journal.h:201   #define JOURNAL_NEED_SWAP 0x00080000
      hfs_journal.c:1963  jnl->flags |= JOURNAL_NEED_SWAP;

HFS Plus volume headers are big-endian; journal headers use the host's native order and
record which one it was in the endian field (0x12345678). 78 4c 4e 4a / 78 56 34 12 is the
standard ARM64 form.

fsck.hfsplus misreports small journaled volumes
------------------------------------------------
fsck.hfsplus -n on our volume says:

      invalid primary VHB at 2 result 35
      alternate VHB is at block 356350
      ** The volume RedwoodVar was found corrupt and needs to be repaired.

A volume made fresh by the same toolset says the same thing:

      truncate -s 182452224 /tmp/refj.img
      mkfs.hfsplus -v RedwoodVar -b 4096 -J /tmp/refj.img
      fsck.hfsplus -n /tmp/refj.img
      -> invalid primary VHB at 2 result 35

So this is hfsprogs 540.1 misreporting a 174 MiB volume with 4096-byte blocks, not a fault in
the volume. The comparison against that reference volume also showed every volume-header field
matches: signature, version, blockSize, totalBlocks, journalInfoBlock, JIB flags/offset/size,
and the allocationFile, extentsFile, catalogFile and attributesFile forks.

A real bug, left alone: the clock is not calibrated
---------------------------------------------------
The volume header's modifyDate comes out as 0x7c25b095 = 2082844821.
MAC_GMT_FACTOR is 2082844800, so the value being converted was 21 -- seconds since boot,
not calendar time.

      hfs_cnode.c:1962   microtime(&tv);
      hfs_cnode.c:2007   HFSTOVCB(hfsmp)->vcbLsMod = tv.tv_sec;
      MacOSStubs.c:123   to_hfs_time(t) { return (u32)t + MAC_GMT_FACTOR; }

      kern_time.c:243    inittodr() -- "the calendar has already been set up from the
                         platform clock"

Nothing in this port reads a platform clock, so wall time starts at zero. Mount, write,
unmount and journal replay all work; the timestamps are wrong and macOS would call the volume
damaged. mtkloader.c:212 mentions an epoch= argument in a comment but nothing implements it.
