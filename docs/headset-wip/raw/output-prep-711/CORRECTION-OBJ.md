## 更正 1：`DL_GAIN_REG_MASK = 0x0f9f` 不缺位 —— 我算错了

### 我上一轮写的（错误）

> 「`DL_GAIN_REG_MASK` 只匹配 4 位高位段，与 `DL_GAIN_N_40DB_REG = 0xf9f` 在
> `regmap_update_bits` 下会**截断左通道最高位**。」
>
> 「掩码写的是 `0x0f9f`（高位被截到 0x0f）」

### 我自己重算的结果

```
(0x1f << 7) | 0x1f = 0x0f9f        ← 精确相等
```

| 项 | 二进制 |
|---|---|
| `0x1f` | `0000 0000 0001 1111`（bit0-4） |
| `0x1f << 7` | `0000 1111 1000 0000`（**bit7-11**） |
| 或起来 | `0000 1111 1001 1111` = **`0x0f9f`** |

**掩码覆盖位：`[0,1,2,3,4, 7,8,9,10,11]` —— 共 10 位，一个不缺。**
**`bit7` 在内（`0x80`）、`bit11` 在内（`0x800`）。**

### 我错在哪

**我把 `0x0f9f` 的高字节 `0x0f` 当成了"整个高位段"，漏掉了 bit7（`0x80`）。**
正确拆法是 **`0x0f9f = 0x0f80 | 0x001f`**，`0x0f80` 就是 `0x1f << 7`。

**结论：掩码与 `DL_GAIN_N_40DB_REG` 完全匹配，没有截断。我的"缺位"推论错误，撤回。**

## 更正 2：`ZCD_CON3`/`ZCD_CON4` 是两个独立寄存器 —— 不是"一个寄存器内打包左右"

### 我上一轮写的（错误）

> 「ramp 内部写的是 `regmap_update_bits(..., DL_GAIN_REG_MASK, reg_idx)`，
> `reg_idx` 直接当值用（如 30 = 0x1e，单通道 5 位）；
> 而宏 `DL_GAIN_N_22DB_REG` 是 `(30<<7|30) = 0xf1e`（左右打包）。
> **两处写法不同，右通道位在 ramp 路径下是否被设置，我没有设备侧 readback 能区分。**」

### 实际结构

**`mt6368.h:418-419`：**

```c
#define MT6368_ZCD_CON3   0x260b     /* 左声道 */
#define MT6368_ZCD_CON4   0x260c     /* 右声道 */
```

**两个独立地址，各自低 5 位。**

**`headset_volume_ramp`（`mt6368.c:456-464`）分别写两个地址：**

```c
regmap_update_bits(priv->regmap, MT6368_ZCD_CON3, DL_GAIN_REG_MASK, reg_idx);
regmap_update_bits(priv->regmap, MT6368_ZCD_CON4, DL_GAIN_REG_MASK, reg_idx);
```

**所以左右是靠"写两个地址"设置的，不是"一个地址内打包"。**

### 我错在哪

**我把自己在 `DL_GAIN_N_22DB_REG` 里看到的 `(X<<7|X)` 打包形状，
误当成"`ramp` 也该这么写"。实际上 `ramp` 写的是两个独立寄存器，各用低 5 位。**

**"右通道位是否被设置"这个疑问不成立 —— 它靠第二个 `regmap_update_bits` 设置。撤回。**

### 那 `DL_GAIN_N_22DB_REG = (30<<7|30)` 用在哪

**用在 `regmap_write`（整体覆盖写）的场合**，例如：

| 行 | 调用 |
|---|---|
| `mt6368.c:2977-2978` | `regmap_write(ZCD_CON3, DL_GAIN_N_22DB_REG)` / `regmap_write(ZCD_CON4, ...)` |
| `mt6368.c:2982-2983` | mute 分支，同上用 `DL_GAIN_N_40DB_REG` |
| `mt6368.c:4240-4241` | `regmap_write` 同上 |
| `mt6368.c:4387-4388` | 关闭序列，`regmap_write` + `DL_GAIN_N_40DB_REG` |

**注意：这些 `regmap_write` 也是分别写 CON3 与 CON4。**
**此时 `(X<<7|X)` 的含义是"同一个寄存器里 bit7-11 与 bit0-4 各存一份"——
但既然左右已分寄存器，这个打包的确切硬件用途我没有依据判定，属未证实项。**

## 更正 3：真正的矛盾是 **TLV 方向与硬件枚举方向相反**

### 我上一轮说的"矛盾"（定位不准）

> 「kcontrol max = 30，但 `is_valid_hp_pga_idx` 允许 31」→ **这不算矛盾**
>
> **OBJ 指出：UI 的 max=30 不含专用码 31，是正常设计，不是自相矛盾。**
> 我同意：31 是 mute/关闭专用码，不进 UI 范围，合理。

### 真正的矛盾

**TLV 声明（`mt6368.c:604`）：**

```c
static const DECLARE_TLV_DB_SCALE(hp_playback_tlv, -2200, 100, 0);
```

| 参数 | 值 |
|---|---|
| min | **-2200**（-22.00 dB） |
| step | **100**（1.00 dB） |
| **invert** | **0** |

**kcontrol（`mt6368.c:612-616`）：**

```c
SOC_DOUBLE_R_EXT_TLV("Headset Volume",
		   MT6368_ZCD_CON3, MT6368_ZCD_CON4, 0, 0x1E, 0,
		   snd_soc_get_volsw, mt6368_put_volsw,
		   hp_playback_tlv),
```
**参数位：`shift=0`、`max=0x1E`、`invert=0`。**

### 矛盾展开

**按 TLV 线性公式 `dB = min + index*step`：**

| 索引 | TLV 算出的 dB |
|---|---|
| 0 | **-22.00** |
| 30 | **-2200 + 30×100 = +8.00** |

**按硬件枚举（`mt6368.h:5678-5683`）：**

| 索引 | 枚举名 | 含义 |
|---|---|---|
| 0 | `DL_GAIN_8DB` | **+8 dB（最大）** |
| 30 | `DL_GAIN_N_22DB` | **-22 dB（最小）** |

**结果：**

- **TLV 说索引 0 是最小（-22dB）、30 是最大（+8dB）**
- **硬件说索引 0 是最大（+8dB）、30 是最小（-22dB）**
- **两者方向完全相反**

**`invert` 参数的用途正是处理这种反向刻度，但这里 `invert = 0`（未反转）。**

### 这带来什么实际后果（我不下最终结论）

**若 ALSA 按 `invert=0` 直传索引**：
用户在 UI 拉到最大（30）时，硬件实际收到最小增益索引。

**若某处代码做了反向映射**：则 TLV 方向又该配合反转。

**我没有找到驱动里把这个 TLV 方向纠正过来的位置，也没有设备侧 readback 能验证 UI 值与实际寄存器值的关系。
这一点标为待 Codex 判定的真实问题 —— 比我上一轮那两个错判重要得多。**

### 与我上一轮结论的关系

**我上一轮说"TLV 只覆盖 0..30，31 超出声明范围"——这句本身没错，
但我把它当成主要矛盾，而真正的问题是方向反了。定位不准。**
