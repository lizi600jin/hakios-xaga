## 三个候选方向

### 候选 A：定位录音链（为什么录不到 997 Hz）

**做什么**：音量阶梯实验（如 4/8/12/15 各放一遍，录音手机固定位置），
看录音里 997 Hz 从哪档开始清晰。

| 项 | 评估 |
|---|---|
| **改代码** | **不需要** |
| 碰设备 | 需要（但要刷 XNU 吗？**不需要**，Android 侧就能做） |
| 成本 | **极低** |
| 产出 | 知道录音手机需要多大音量；为以后所有声学实验建立基线 |
| 风险 | **无**（纯 Android 侧操作） |

**局限**：**只是测量方法问题，不推进音频功能**。

---

### 候选 B：给 SGEN 一个已知频率（让 23ca 的 FREQ_DIV 有意义）

**做什么**：查 vendor 源码或数据手册，确定 `FREQ_DIV_CH1_CTL`（`0x23ca` bit4:0）
与 `AMP_DIV_CH1_CTL`（`0x23c9` bit3:0）的实际编码，然后用已知设置发一个已知音。

| 项 | 评估 |
|---|---|
| 改代码 | 可能要加参数 |
| 碰设备 | 需要刷写 |
| 成本 | 中 |
| 产出 | **SGEN 频率可预测 —— 录音就能明确验证「录到的是不是我们的音」** |
| 风险 | 低（还是 codec 内部路径） |

**这是我现在最倾向的**：它把「听到声音」变成「听到**预期频率**的声音」，
**声学验证才有可判据的靶子**。

---

### 候选 C：接真正的播放链路（SoC AFE → MTKAIF → codec）

**做什么**：实现 SoC AFE 配置、MTKAIF 传输、PCM/DMA，让 XNU 能播放任意音频。

| 项 | 评估 |
|---|---|
| 改代码 | **大量**（驱动里目前 0 行相关代码） |
| 碰设备 | 需要反复刷写调试 |
| 成本 | **很高** |
| 产出 | 真正的音频播放能力 |
| 风险 | **高**（时钟、DMA、中断都要对） |

**这是终极目标，但现在做太早** —— 没有一个可验证的中间态。

---

## 我的建议排序

| 序 | 候选 | 理由 |
|---|---|---|
| **1** | **B（SGEN 已知频率）** | 把「有声」变成「有可验证频率的声」，是声学判据的前提 |
| 2 | A（录音链阶梯） | 便宜且必要，但可随时做，不阻塞 |
| 3 | C（AFE 通路） | 目标，但需要 B 建立的验证手段 |

**A 和 B 可以并行**：A 纯 Android，B 需要刷写。

## 需要 Codex 判定的问题

1. **`23ca` 的 FREQ_DIV 编码**：vendor 源码里有没有查表或公式？
   （我在 `mt6368.h` 里只找到位域定义，没找到编码表）
2. **`23c9` 的 AMP_DIV 编码**：同上
3. **SGEN 是否支持任意频率**，还是只有几个固定档
4. **trial710/711/712 三次测试里 `23c9=1`/`23ca=0` 是 codec 复位默认值还是驱动选的**
5. **C 方向的可行性**：MT6895 的 AFE 在 XNU 下有没有任何已有基础
