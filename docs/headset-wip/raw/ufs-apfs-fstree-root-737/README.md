## 查找的实际路径

树是四层，两个组件走的不是同一条分支：

```
组件 0：1029(2510,L3) → 1030(2511,L2) → 1032(2513,L1) → 1156(2637,L0)  叶里找到 usr
组件 1：1029(2510,L3) → 1031(2512,L2) → 1152(2633,L1) → 13013(14494,L0) 叶里找到 bin
```

每下降一层用两个块：一个对象映射叶（把虚拟 OID 换成地址），一个树节点。

## 这一轮的实质变化

Trial736 的四个地址是**写死的**。这一轮地址全部由前一步已校验的值推出：

- 分支按 `(对象, 记录类型)` 决定 —— 只比对象 ID 会选错分支，目录自身的记录和它的条目在键序里不在同一段
- 虚拟 OID 必经对象映射转换，映射叶由映射根的键序选出
- 序号白名单从**固定地址表**改成**范围约束**（映射叶 2399..2509、树节点 2510..16383），推导正确性由 codec 保证

## 六个实现错误

每一处都是「编译通过、逻辑自洽、跑真数据才暴露」：

| # | 错误 | 后果 |
|---|---|---|
| 1 | `wanted` 写成「请求数+块数」 | 十块需要 9 步而非 8 步，少一步 |
| 2 | 模式 10 用 `av_next`（stop_after=6） | 第 6 步就拒绝 |
| 3 | 第 4 条命令、`tail` 计算漏了模式 10 | NXSB 没读到，链从错位置开始 |
| 4 | `tree_base = have` | 应为 `have-1`，把树根指到窗口外 |
| 5 | `twoblock_run` 传 `NULL` 窗口 | `done` 不设置，每块都判失败 |
| 6 | 树节点上界设成 4095 | 实际到 14822，查找在最后一层被拒 |

另有：`snapshot[]` 忘了一起放大（与 736 同一个错误）、白名单分支漏改导致 rel=0 走了错误数据源。
