# I2C 通了：读到了 96% 和 4355 mV，还有一个没解决的字节顺序问题

2026-11-26。`boot-953` 到 `boot-961`，九个镜像。

## 已经确定的

### 总线是开的，可以放心碰

```
i2c: IMP_IIC_WRAP_C at 0x11282000 CG_STA 00000000
i2c: IMP_IIC_WRAP_S at 0x11d07000 CG_STA 00000000
```

两个 wrapper 的 `CG_STA` 全是 0。**位是 1 表示时钟关闭**，所以九条总线都开着。
`disp_pwm0` 那次挂死的教训是「时钟没开的块不能写」，这条总线上不存在那个前提。

### i2c-7 是 v3 寄存器布局，`SLAVE_ADDR` 在 `+0x94`

dump 出来的 `+0x94 = 0xaa`，而 `0xaa = 0x55 << 1`——Android 上一次传输留下的从机地址。
`0x55` 就是 `bq28z610` 的七位地址。这一条同时确认了布局和器件。

### 电池数据来自 bq28z610，不是 mt6375

```
/sys/class/power_supply/bms
  → 11d04000.i2c/i2c-7/7-0055/power_supply/bms

POWER_SUPPLY_MODEL_NAME=nfg1000b
```

`i2c-7` 在 `0x11d04000`，400 kHz。所以是 TI 的独立电量计在报数，
副 PMIC `mt6375` 管的是充电。

### 真的读出来了（几笔对的）

```
i2c: gauge: voltage            (0x08) = 4356 mV
i2c: gauge: state of charge    (0x2c) = 96 %
i2c: gauge: current            (0x0c) = 191 mA   （符号待查）
```

`0x2c` 是硬件算好的百分比，`0x08` 是毫伏。**这两个数值和 Android 报的一致**
（Android 那边 98% / 4439 mV，差一点是时间差）。

## 还没解决的：第二个字节读不到

`DATA_PORT` 在 `+0x00`，是 32 位宽。读一次只拿到一个字节：

```
raw 00000003   电压的低字节     （4355 = 0x1103，低字节 0x03 ✓）
raw 000000bf   电流的低字节
raw 000000ff   温度的低字节
raw 00000060   SoC 0x60 = 96 ✓
```

**低字节全部正确。** 但第二个字节要再读一次 `+0x00`，而第二次读回来是 `0xffff`
——FIFO 已经空了。

最初的写法是「读两次，各取低字节拼起来」，得到 `0xFF03` = 65283。
那不是数据错，是**第一次读其实已经拿到了低字节 0x03，第二次读读空返回 0xFF**。
后来改成「读一次，把 32 位当一个字」，得到 `0x00000003`——说明高位字节根本不在同一个字里。

所以要么：
1. 第二次读之前要等 FIFO 再填（但 2 字节应该一起进来）
2. 或者第二个字节在 `+0x01`、`+0x02` 这样的偏移上
3. 或者要读 `DATA_PORT` 的 16 位别名

## 还有一个独立的 bug：连续事务会卡住

第五笔开始：

```
wr 00000080 fifo 00000084
rd 00000000 fifo 00000000
dbg 0000420e
```

`0x80` 不在 mainline 的 `INTR_STAT` 位定义里（那是 MTK 私有的），看起来是超时。
前面四笔都成功，第五笔开始每一笔都这样。

**任何一次「写命令 + 读数据」的两段事务跑多了都会卡在第五笔。** 这个和字节顺序是两件事。

试过并确认无效的：
- 写 `START = 0` 想产生 STOP → **更糟**，四笔全变 `0xFF03`（`boot-958`/`959`）
- 加 `RS` 位 → 同样没用（`boot-960`）
- 加 `RS_MUL_TRIG` → 没用（`boot-956`）

## 九次尝试的清单

| 镜像 | 改了什么 | 结果 |
|---|---|---|
| 953 | 只读 dump | ✅ 拿到全部寄存器状态 |
| 954 | 第一次事务，单连接 WRRD | 2/7，值错 |
| 955 | 8 位地址 + CONTROL 位 + FIFO_ADDR_CLR | 7/7 全 0 |
| 956 | START 加 RS_MUL_TRIG | 7/7 全 0 |
| 957 | 改成两段独立事务 | **1/7，但 4356 mV 是对的** |
| 958 | 事务前写 START=0 | 4/7，值全是 0xFFxx |
| 959 | 去掉 RS | 4/7，同 958 |
| 960 | 去掉 START=0 | 4/7，同 958 |
| 961 | DATA_PORT 读一次取 32 位 | 4/7，raw 只有低字节 |

**957 那次 `4356 mV` 是真的。** 后面所有「值不对」都是我在修别的东西时把它弄坏的。

## 下一步

1. **先解决连续事务卡在第五笔**——这是阻塞性的，字节顺序问题在它后面。
   最可能的办法是每笔事务后做一个真正的控制器复位（`SOFTRESET = 1`
   再写 0），代价是 `TIMING`/`CLOCK_DIV` 会回到默认值，需要重新写回去。
2. 再解决第二个字节：试 `+0x01` 偏移，或者用 `FIFO_STAT` 确认还剩几个字节再读。

**两件都是纯软件问题，不涉及新的硬件风险。**
