# 里程碑 6d · 真机写入成立（Trial751）

2026-11-21。**这台手机上第一次成功向闪存写入数据。** 设备已恢复原厂，`boot_a` 逐字节相同。

## 结果

```
mt6895-ufs-twoblock: zone write 608456 ocs=0 polls=39 restored=1
```

`ocs=0` 是 `OCS_SUCCESS`。块 608456 读回来是：

```
575a3457 ed020000   =  "WZ4W" + trial 749
```

写入前那个块全是零。

## 影响范围精确到一个块

512 块（2 MiB）逐块比对：

```
有差异的块（相对 zone 起点）: [8]      ← 正是 608456
容器末尾 128 块与备份相同: True
```

整个测试区只有被指定的那一块变了，容器末尾（APFS 自己的元数据）一个字节没动。

## 真正的根因：两个方向位

上一轮 `ocs=7`（`INVALID_PRD_TABLE`）。看起来像 PRD 表的问题，其实不是：

| 字段 | 我写的 | 正确的 | 含义 |
|---|---|---|---|
| `upiu[1]` | `0x00` | **`0x20`** | `UPIU_FLAG_WRITE`（读是 `0x40`） |
| `utrd[0]` | `0x0a000000` | **`0x12000000`** | `CT_UFS(1<<28)` + `DD_OUT(1<<25)` |

`0x0a000000` 里带的是 `2<<25`，也就是 **data-in**——我的“写”命令拖着读方向。
控制器收到一个方向与命令自相矛盾的请求，回的就是 PRD 表无效。

`0x00` 更糟：既不是读也不是写。

对照 loader 侧已有的 `ufs_write`（它早就在往日志区写着），宏定义是这样的：

```c
#define UTRD_DD_OUT  (1u << 25)   /* UTP_HOST_TO_DEVICE */
UPIU_FLAG_WRITE  0x20
```

我硬写常量时漏掉了这一层。
