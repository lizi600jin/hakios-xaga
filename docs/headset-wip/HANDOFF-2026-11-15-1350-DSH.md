## 1. 本轮最重要的两个产出

### 1.1 ✅ 日志可以随时从设备取，不用刷机

**设备是 KernelSU root。** `xnusys` 分区尾部 8 MiB 就是 logbook：

```sh
# HLOG 在 xnusys_size - 8 MiB 处
adb shell 'dd if=/dev/block/by-name/xnusys bs=1M 2>/dev/null | grep -abo "HLOG"'
# 偏移 +4096 是正文，长度取 header 的 u64 @8
```

**已验证两次**（trial 695 与 696），校验方式：

| 字段 | header 偏移 | 说明 |
|---|---|---|
| magic | 0 | `0x474f4c48` = "HLOG" |
| len | 8 | 正文字节数（u64） |
| sum | **64** | 8 位加和（u64） |

**正文 8 位加和必须等于 header @64 的 sum。** 两次都对上：
695 = `0x24c8bcc`，696 = `0x24da28c`。

**这条彻底取代了 `fastboot oem expdb`**（那条路会搞死 USB endpoint，只能物理插拔）。

### 1.2 ✅ 厂商固件来源确认

```

我们打包进内核的那份               md5 ddef4ef1802903d3f54259da07605229
sha256（两者）  de22d2fc06bc8a859968499a6e609c27fe838be062bf5c97d92ea9f904f7229a
```

**字节完全相同。没有「固件来源不对」这个问题。**

### 2.1 原始读数

```
mali: witness: vector was sp 0x2040000 reset 0x10018ed
mali: witness: code at 0x1000000, reset vector now 0x1000001
mali: witness: read1 0xff5aa5f0 0 read2 0xff5aa5f0 0 read3 0xff5aa5f0 0 trial 696
mali: witness: verdict trial 696 -- no completed first store observed (not an instruction trace)
```

### 2.2 🔴 能说与不能说（这一节最重要，别读成更强的结论）

| 能说 | 不能说 |
|---|---|
| patch 生效（向量确实变成 `0x1000001`） | 「一条 `str` 都没执行」 |
| **没有观察到已完成的 marker store** | 「MCU 零执行」 |
| CPU 能读写共享页 | 「MCU 侧映射 / cache 全通」 |
| 无 MMU fault（`faultstatus 0`） | 「没有取指发生」 |
| `JOB_INT_RAWSTAT = 0` | 「中断被 mask 挡住」 |

**marker 只有「完成态」，没有中间态**，所以无法区分：
没执行 / 写到了别处 / 写了但 CPU 视图看不到。

### 2.3 为什么 `mmu irq 0` 不能当判据

`panthor_mmu.c:657-661` 原文：

```c
static u32 panthor_mmu_fault_mask(struct panthor_device *ptdev, u32 value)
{
	/* Bits 16 to 31 mean REQ_COMPLETE. */
	return value & GENMASK(15, 0);
}
```

**`bit[31:16]` = `REQ_COMPLETE`（地址空间命令完成事件），不是取指事务计数。**
低位 `bit[15:0]` 才是 fault。

## 3. 已排除的方向（可以不再投入）

| 方向 | 依据 |
|---|---|
| 固件本身有 bug | 32 字节自己的代码也没产生可观察 marker |
| 段布局 / entry table 解析 | GLB 结构解出来与官方固件逐字相同 |
| PROT 段处理错 | witness 完全不碰 PROT 段 |
| 复位向量 patch 未生效 | `reset vector now 0x1000001` |
| AS0 未激活 | `AS0 enabled: root 0x1a6d70000` |
| 页表覆盖不全 | `coverage: every section fully mapped` |
| MMU fault 导致静默停止 | `faultstatus 0`（只看 bit[15:0]，此结论有效） |
| L2 未上电 | `L2 up: ... ready 0x1` |
| `shader ready 0` 是缺陷 | panthor 启动固件前只开 L2，shader 由固件自己开 |
| 「核完全没电」 | XNU 读到 `shader 0x130013` == Android 的 `ShaderPresent 0x00130013` |
| VA0 不可执行是 bug | 我们与 ARM 官方固件的 `va==0` 段都是 `flags 0x9` |
| `JOB_INT_MASK` 极性反了 | 1=使能（vendor + panthor 双向确证） |
| 缺 CSF_CFG 预启动步骤 | panthor/kbase 全树零命中 |

## 4. 🔴 我本轮犯的错误（全部留档，别再引用旧版）

| # | 我错的 | 真相 |
|---|---|---|
| 1 | 手工解码 Thumb-2，说 `f44f 21e0` = `mov.w r1,#0x2e0` | 实为 `#0x70000`；整张表要用 capstone |
| 2 | 「5 个电源域没起来」 | 假失败；`0xF3C = 0x3ffc` 表示 12 域全 up |
| 3 | 「entry words 错位 8 字节」 | 我读错日志，代码打印的是 `vec[2],vec[3],code[0],code[1]` |
| 4 | 「`0x40022000` 无 PTE ⇒ 固件第一条 store 就失败」 | **MMIO 不走页表**，拿 AS0 走查推断可达性是错的 |
| 5 | 「13 个 PPB 常量全在同一字面量池」 | 11 个在池内，`SHCSR@0x2824`、`AIRCR@0x2af4` 独立 |
| 6 | 寄存器名表 | **整张偏 4 字节**：`EF68`=DCCMVAC、`EF6C`=DCCSW、`EF70`=DCCIMVAC、`EF74`=DCCISW |
| 7 | 「这批常量是 M7 独占」 | ARM 官方 `core_cm55.h` 定义了**相同地址和字段** |
| 8 | 「有 DCCMVAC 说明本机 D-cache 存在」 | 静态代码证明不了，**仍未实测** |
| 9 | 「自家驱动注释是第三条独立佐证」 | 循环论证；只能算**实现记录**，不算硬件识别证明 |
| 10 | 「未见 marker ⇒ 一条 str 没执行」 | 只能说**没观察到已完成的 store** |
| 11 | 「CPU 读回哨兵 ⇒ MCU 映射/cache 全通」 | 只证明 CPU 侧；MCU 侧、coherency 都没证明 |
| 12 | 「`mmu irq 0` ⇒ 无取指」 | `REQ_COMPLETE` 不是事务计数 |
| 13 | 「GPUEB 是最强原因」 | `not mapped` 只说明 AP 没映射探针 |
| 14 | 「厂商固件与我们不同」 | 我看错：把 sha256 前 8 位当成 md5；**两者 md5 完全一致** |
| 15 | 「695→696 字符串短 1 字节」 | **两版 `argument_bytes` 都是 463**；我把 loader 里的 464 变体当成完整参数 |
| 16 | 「Android 卡住与 GPU 无关，是独立问题」 | 根因是 `no suitable EGLConfig`，**依赖 vendor kbase 可用**，与 GPU 不可用是同一件事 |

**共同根因**：我多次把「间接证据」推成「直接结论」，以及把别人的转述当成已核事实。
**本轮的教训是：每一次升级结论前，先问「这是观测还是推断」。**

## 8. 🔴 环境坑：代理节点会死（本轮踩过一次）

**症状**：GitHub / kernel.org 全 `000`，Codex 额度查询报 `SSL EOF`，但**百度 200**。

**根因**：Clash `节点选择` 指向 **韩国KR-HY2**，实测 **Timeout**。

**修法**（Clash Verge 用 unix socket，不是 9090）：

```sh

curl -s --unix-socket $SOCK http://localhost/proxies | \
  python3 -c "import json,sys;[print(f\"{k}: {v.get('now')}\") for k,v in json.load(sys.stdin)['proxies'].items() if v.get('type') in ('Selector','URLTest')]"

  "http://localhost/proxies/%E9%9F%A9%E5%9B%BDKR-HY2/delay?timeout=8000&url=http%3A%2F%2Fwww.gstatic.com%2Fgenerate_204"

# 切换（URL 编码的组名 = 节点选择）
curl -s -X PUT --unix-socket $SOCK \
  "http://localhost/proxies/%E8%8A%82%E7%82%B9%E9%80%89%E6%8B%A9" \
  -H "Content-Type: application/json" -d '{"name":"香港WAP-优化3"}'
```

**本轮实测**：

| 节点 | 延迟 | chatgpt 后端 |
|---|---|---|
| 韩国KR-HY2 | **Timeout** | 全断 |
| 香港WAP-优化3 | 34 ms | **403 Forbidden**（Cloudflare 拦，cf-ray 显示 HKG） |
| 美国LA-优化-GPT | 196 ms | **405**（链路通） |
| 英国-优化-GPT | 355 ms | **405**（链路通） |
| 台湾-优化2-GPT | 680 ms | **405**（链路通） |
| 新加坡-优化-GPT | Timeout | — |

### 🔴 关键：普通节点过不了 Cloudflare

**延迟低 ≠ 能用。** 香港WAP-优化3 延迟只有 34 ms，但 chatgpt 后端直接 **403**。

**必须用名字带 `-GPT` 后缀的节点**（`美国LA-优化-GPT` / `英国-优化-GPT` /
`台湾-优化2-GPT` / `新加坡-优化-GPT`）。这些是专门绕 Cloudflare 的。

**判定方法**（用 GET 打一个只收 POST 的端点）：

```sh
curl -s -o /dev/null -w "%{http_code}\n" https://chatgpt.com/backend-api/codex/responses
# 403 = 被 Cloudflare 拦（换节点）
# 405 = 链路通（Method Not Allowed，正常）
```
