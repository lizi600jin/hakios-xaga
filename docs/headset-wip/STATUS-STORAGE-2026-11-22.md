## 三、第 4 步为什么难

### 已经完成的

- `/dev/xnusys_var` 设备注册成功
- ioctl 正常：`DKIOCGETBLOCKSIZE -> 512`，`DKIOCGETBLOCKCOUNT -> 356352`（= 174 MiB，正确）
- 窗口 608512..653055，避开 APFS 容器、三块实验数据、loader 日志
- HFS+ 的空卷已经写进闪存：**10 个卷头块，用 Android 自己的驱动逐字节验证过**

**数据一直都在。** 缺的只是一个能读到它的接口。

### 五次失败与各自的根因

| 次 | 改动 | 结果 | 根因 |
|---|---|---|---|
| 1 | `zone_read` 直连 runner | 卡死 | 块无 reference → `twoblock_fail` → poison |
| 2 | 加 `DATA_WINDOW_MODE` | 卡死 | 读根本没进 strategy，模式无关 |
| 3 | 实现 `d_read`（`kalloc`+`uiomove`） | read 返回 -1 | 节点是 `DEVFS_BLOCK`，`spec_read` 走 VBLK 分支，不碰 `d_read` |
| 4 | 改成 `DEVFS_CHAR` | 卡死 | 未定位 |
| 5 | `d_psize` 修正 + 区分 refuse/poison | 卡死 | 未定位 |

### 已修好的两个真 bug

**一、`d_psize` 返回块数而非块大小**

`set_blocksize()` 把它的返回值直接存进 `v_specsize`，而 `spec_read` 拒绝
超过 `PAGE_SIZE` 的值。我返回 356352，于是每次读都在到达驱动前就 `EINVAL`。

对照 `memdev.c` 的 `mdevsize`（512）和 `virtio_blk.c` 的 `blk_dev_size`（512），
**都返回块大小**。已改。

**二、一次读失败毒化整机存储**

`twoblock_fail` 对所有失败都 `us_poison`，包括命令根本没发出去的情况。
poison 的语义是"命令发了、控制器可能没恢复"，用在没发的情况上就是把
普通失败升级成永久锁死 —— 这是五次手动 fastboot 的由来。

已拆成 `twoblock_refuse`（不 poison）和 `twoblock_fail`（照旧）。
校验和不匹配仍然 poison，因为那是"发了、数据错"。

回归抓到了我第一次拆错（把校验和路径也改成 refuse），38 项测试全过。

## 四、关于 DSU 那条路：实测否掉了

之前分析过"DSU 侧载能提供大块设备"。**实测结果是不能用。**

证据链：

1. `/data` 挂在 `/dev/block/dm-50`，f2fs，挂载选项含 `inlinecrypt`
2. `dm-50` 只有一个从设备：`sdc86`（物理 userdata，103.98 GiB）
3. **块 0 的偏移 1024**（F2FS 超级块位置）：
   - `dm-50` 读到 `10 20 f5 f2` —— F2FS 魔数
   - `sdc86` 同位置读到 `ce bd fc 43 39 b5 49 9c` 等随机字节
4. `ro.crypto.metadata.enabled = true`
5. fstab: `keydirectory=/metadata/vold/metadata_encryption`
6. `/dev/block/sdc20` 挂在 `/metadata`（ext4）

**结论：`dm-50` 不是 `sdc86` 的线性映射。元数据加密（AES-256-XTS，
密钥在 metadata 分区）坐在块层、在文件系统下面。**

这个结论是硬的：不是偏移或单位错了，是字节本身不同。任何地址翻译修正都救不回。

所以 DSU 的镜像文件在物理层是密文，loader 直接读只能拿到密文。

## 五、容量现状（实测）

| 项 | 值 | 用途 |
|---|---|---|
| `xnusys` 数据卷窗口 | **174 MiB** | 正在打通的目标 |
| `xnusys` APFS 容器 | 2.32 GiB | 只读系统卷 |
| `userdata` | 103.98 GiB（空闲 94 GB） | 安卓的，**块层加密** |
| `super` | 8.50 GiB | 安卓动态分区 |
| 内存 | 7.3 GiB | 当前 `/` 和 `/private/var` 都在内存里 |

**当前 XNU 能用的持久存储是 0 字节。** `/private/var` 是内存盘，掉电即失。

174 MiB 是唯一已经打好基础的可写空间。够不够？
启动骨架是 111 目录 8 文件，但**完整 `/private/var` 的体积还没测过** ——
codex 提醒过不能用骨架推断。

## 六、下一步

**先取 HLOG，再改代码。** 这是唯一还没拿到的证据。

连续五次都是"改代码 → 刷机 → 看结果"，而两个真 bug 都是读源码读出来的，
不是测出来的。下一个动作应该是：让设备带着当前代码启动一次，
取回 HLOG，看驱动走到哪一步，再决定改哪里。

如果 HLOG 因为内核早期崩溃写不出来，那就改成在 `init` 里直接调
`hakios_mt6895_ufs_zone_read()` 读一块并打印，绕开整个 VFS 层 ——
这样能立刻区分"驱动读不了"和"VFS 接口没接对"。

## 七、诚实的风险评估

**这条路是通的，但比我最初估计的慢。**

- 驱动层：读写都已验证（阶段 6）
- 文件系统层：HFS+ 现成
- 中间那层（块设备接口）：这是我踩坑的地方，纯粹是 XNU VFS 的接口细节

174 MiB 的容量对"能持久化"是够的，对"当主存储用"是不够的。
真要更大容量，只有两条路：
- 改 GPT 从不加密的新分区拿空间（要处理 f2fs 缩容，高风险）
- 啃完整 APFS 写（8–16 人周）
