# MT6368 耳机模拟通路 · 发声序列

> 目的：在**不接任何数字音频源**的情况下，让 3.5mm 耳机发出声音。
> 对象：`docs/headset-wip/ko/snd-soc-mt6368.ko`（277608 B，not stripped）
> 方法：`aarch64-linux-gnu-objdump -dr` 逐条反汇编
>
> **注意**：本文的序列**没有**真机对拍。原因见 §5。
> 与 `ACCDET-DECODE.md` 不同——那份的 19 个写入全部经过真机验证，这份没有。

---

## 0. 为什么这条路径值得先试

MT6368 内部有正弦波发生器（SGEN），`DAC In Mux` 的一个取值就是 `Sgen`。
真机 kcontrol 实测：`DAC In Mux: >Normal Path Sgen`。

所以最短的发声路径不需要：

- ❌ AFE（`0x1e100000`）上电
- ❌ MTKAIF 校准
- ❌ MT6685 音频时钟芯片
- ❌ DMA / 环形缓冲
- ❌ ASoC / 任何 Linux 音频框架

只需要：

- ✅ SPMI 写事务（本项目按键驱动已验证**读**，写未验证）
- ✅ 耳机模拟前端上电序列（本文 §2）
- ✅ 打开 SGEN（本文 §3）
- ✅ `HPL Mux` / `HPR Mux` 切到播放路径

一旦成功，同时证明了：SPMI 写可用 + MT6368 上电时序对 + 耳机模拟通路通。

## 1. 涉及的事件函数一览

`mt_hp_event` 是耳机模拟前端的 DAPM 事件处理器。它按 `event` 参数（`w21`）
和一个路径选择值（`w20`，来自 `dapm_kcontrol_get_value()`）分支。

| 函数 | 地址 | 触发条件 |
|---|---|---|
| `mt_hp_event` | `0x8be0` | DAPM 事件：`event == 1`（PRE_PMU）/ `event == 4` / `event == 8`（POST_PMD） |
| `mt_hp_mute_event` | `0x93a8` | 静音/去静音 |
| `mt_hp_damp_event` | `0x941c` | 阻尼（把 `0x259c`/`0x259d` 清零） |
| `mt_hp_pull_down_event` | `0x9358` | 下拉（无寄存器写，纯 GPIO/内部开关） |
| `mt_sgen_event` | `0x9b8c` | `event == 1` 开，`event == 8` 关 |

## 2. 耳机上电序列（`mt_hp_event`，event=1，w20=1 分支）

反汇编范围：`0x8c80`–`0x8d3c`。这是"耳机要走内部 DAC"的那条分支。

| 顺序 | 寄存器 | 操作 | 值 | 反汇编地址 |
|---|---|---|---|---|
| 1 | `0x2595` | write | `0x10` | `0x8c84-0x8c8c` |
| 2 | `0x25a0` | update_bits(mask `0x07`) | `0x02` | `0x8c94-0x8cac` |
| 3 | `0x25a1` | update_bits(mask `0x30`) | `0x10` | `0x8cb4-0x8ccc` |
| 4 | `0x2597` | write | `0x00` | `0x8cd4-0x8cdc` |
| 5 | `0x2596` | write | `0x01` | `0x8ce4-0x8cec` |
| 6 | `0x2595` | write | `0x10` | `0x8cf4-0x8cfc` |
| 7 | `0x2595` | write | `0x12` | `0x8d04-0x8d0c` |
| 8 | `0x2595` | write | `0x13` | `0x8d14-0x8d1c` |
| 9 | `0x2609` | write | `0x08` | `0x8d24-0x8d2c` |
| 10 | `0x260a` | write | `0x08` | `0x8d34-0x8d3c` |

**注意第 1/6/7/8 步都写 `0x2595`**，依次是 `0x10` → `0x10` → `0x12` → `0x13`。
这不是笔误：`0x2595` 像一个"逐步上电的使能序列"寄存器，值递增代表不同上电阶段。
**不能合并成只写最后一次**——那样会跳过一个中间状态。

### 2.1 另一条分支（w20 != 1）

反汇编范围：`0x8d40`–`0x8df0`。这是"耳机不走内部 DAC"那条（例如走外部功放）：

| 顺序 | 寄存器 | 操作 | 值 | 反汇编地址 |
|---|---|---|---|---|
| 1 | `0x259f` | update_bits(mask `0x07`) | `?` | `0x8d4c-0x8d70` |
| 2 | `0x25a1` | update_bits(mask `0xc0`) | `?` | `0x8d78-0x8d90` |
| 3 | `0x25a1` | update_bits(mask `0x03`) | `?` | `0x8d98-0x8db0` |
| 4 | `0x259c` | write | `0x87` | `0x8db8-0x8dc0` |
| 5 | `0x2591` | update_bits(mask `0x30`) | `0x10` | `0x8dcc-0x8df0` |

三步的 `w3`（写入值）在反汇编里不是立即数，是从寄存器来的 → **未解出**。

**本机型走哪条分支未知。** `w20` 来自 DAPM 的 kcontrol 值，要在真机上跑才知道。
但**第 4 步的 `0x259c = 0x87` 在主分支和旁支里都出现了**（主分支在别处也写 `0x259c = 0x87`），
这是个好信号：`0x259c = 0x87` 大概率是两条路都要的。

## 3. SGEN 开/关（`mt_sgen_event`）

### 3.1 开（event == 1），`0x9bb4`–`0x9c68`

| 顺序 | 寄存器 | 操作 | 值 |
|---|---|---|---|
| 1 | `0x2396` | write | `0x06` |
| 2 | `0x2393` | write | `0xcb` |
| 3 | `0x2392` | write | `0xa1` |
| 4 | `0x2396` | write | `0x03` |
| 5 | `0x2396` | write | `0x0b` |
| 6 | `0x23c8` | update_bits(mask `0xff`) | `0x00` |
| 7 | `0x23c9` | update_bits(mask `0xff`) | `0x01` |
| 8 | `0x23ca` | update_bits(mask `0xff`) | `0x00` |

同 §2 的模式：`0x2396` 被写三次（`0x06` → `0x03` → `0x0b`），是阶段式的，不能合并。

### 3.2 关（event == 8），`0x9c70` 起

起点是 `0x2396 = 0x00`，后续有对称的一组写入（`0x2393`/`0x2392`/`0x23c8`–`0x23ca`）。
**未完整解出**——只解出第一步。

## 4. 静音与阻尼

### 4.1 `mt_hp_mute_event`（`0x93a8`）

`event` 决定写入值：

| event | 值 | 含义 |
|---|---|---|
| `1` | `0x0f1e`（3870） | 去静音（`0x93e0`） |
| `8` | `0x0f9f`（3999） | 静音（`0x93d8`） |
| 其它 | 不写，直接返回（`0x93d4`） | — |

两个寄存器都写同一个值：`0x260b`、`0x260c`（左/右声道各一个）。

### 4.2 `mt_hp_damp_event`（`0x941c`）

无条件把 `0x259c` 和 `0x259d` 都写 `0x00`。

**注意**：这与 §2.1 里写 `0x259c = 0x87` 冲突——一个是开阻尼、一个是关。
说明 `0x259c` 在耳机上电流程里会被来回改，顺序很重要。

## 5. 这份序列的验证状态（关键）

| 项 | 状态 |
|---|---|
| 反汇编解出 | ✅ 全部带地址 |
| 寄存器值真机对拍 | ❌ **无法对拍** |
| 在真机上执行过 | ❌ 未执行 |
| SGEN 关的完整序列 | ❌ 只解出第一步 |
| `mt_hp_event` 走哪条分支 | ❌ 未知（需运行时 DAPM 值） |

**为什么不能对拍**：Android 关机/待机时不会保持耳机通路开着。
真机 `dump_reg` 只 dump `0x2688`–`0x26d3` 与 `0x2508`–`0x2537`，
而 §2/§3 的寄存器在 `0x2392`–`0x260a`，**不在 dump 范围内**。

→ **这是本项目目前最大的信息缺口**：耳机发声路径的寄存器，一个真机值都没有。

**能补的办法**（都需要真机，但不需要耳机）：
1. 在 stock Android 上，用 `tinymix` 把 `HPL Mux` 切到 `Audio Playback`，
   然后读 `0x2591`/`0x2595`–`0x25a1`/`0x259c`–`0x260a` 的实际值。
   这需要 `set_reg`（驱动有，但只能写单寄存器）或 `dump_reg` 的扩展。
2. 写一个只读的 sysfs 扩展（需要改内核模块，做不到，模块是厂商的）。
3. **直接上裸机试**：按本文序列写，听耳机有没有声音。

第 3 条是唯一可行的，但需要耳机才能听到结果。

### 5.1 现在能做的替代验证

**不需要耳机的部分**：先把 §2/§3 的写序列**读一遍**（这些寄存器可读），
记录**当前值**。将来耳机到手、跑完序列后，再读一遍，两次相比：

- 如果值变了 → 说明写生效
- 如果没变 → 说明写没生效或分支走错

这个"读前读后"的对比，现在就能把**读取代码**写好并验证读通道，只差写。

## 7. 实现建议

### 7.1 顺序

1. **先做只读**（`headset=1`）：读 `0x2688`–`0x26d3` 对拍基线（已写好工具 `accdet-compare.py`）
2. **再做只读扩展**（`headset=4`）：读 `0x2392`–`0x260a` 这批寄存器，**记录当前值**
   ——这批没有基线，但有了第一次读数，将来才有"前后对比"的可能
3. **然后试写**（`headset=5`）：跑 §2 + §3 序列
   - 写之前先读一遍，写之后再读一遍，把差值打印出来
   - 这样即使没有耳机，也能知道"写有没有落到寄存器上"

### 7.2 安全

- 全部在 SID=5（MT6368），不碰 SID=4
- `0x2392`–`0x260a` 都在 MT6368 的合法寄存器范围内，且都不是已知的危险寄存器
  （危险的是 `0x014b` 全局 shutdown、`0x0240` 状态影子）
- 但**这些寄存器的副作用未知**：可能影响充电、可能影响其他模拟块。
  建议第一次只写 SGEN 那一组（`0x2392`/`0x2393`/`0x2396`/`0x23c8`–`0x23ca`），
  不写耳机上电组，看是否有异常

### 7.3 一个更保守的第一步

只读 `0x2319` 和 `0x231d`（`accdet_init_once` 里 toggle 过 `0x2319`）。
真机基线：`0x2319 = 0x00`、`0x231d = 0x06`。

如果裸机读到 `0x231d = 0x06`，说明 **MT6368 保留了 Android 关机前的状态** →
那么 §2/§3 的寄存器也可能保留了状态，可以读出来当基线。

如果读到 `0x00`，说明芯片被复位过 → 所有序列都必须从头跑。

**这一条读，现在就能做，且不需要耳机。**
