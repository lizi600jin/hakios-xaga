# 无耳机条件下的首轮实验设计：SID 5 可读性 + 未插入基线

> **实验正式名称**：SID 5 可读性 + 未插入基线
> **硬约束**：没有 3.5mm 耳机，短期拿不到。全部判据必须在空插座下成立。
> **设备状态**：手机归 Codex（在做 B1+B3）。本文不含任何需要手机的步骤执行记录，只给判据。
> **日期**：2026-11-15
> **配套文件**：
> - `findings/headsetless-checks.json` — 38 条检查项的机器可读定义
> - `headsetless-check.py` — 可执行判定器（`--selftest` 33 条断言，已跑）
> - `accdet-baseline.json` — stock Android 基线（130 项）
>
> 本文所有数字都能在不碰设备的前提下复算。凡标【未验证】的，是没有一手证据的推断。

---

## 0. 结论先行

1. **空插座下能判定的检查项共 38 条**，其中阶段 0（只读、零风险）27 条、阶段 1（最小写）9 条、阶段 2（初始化表后回读）2 条。
2. **SID 5 通不通，无耳机可以判定**，而且是四条互相独立的判据同时成立才算：
   `0x231d==0x06`（stock 自检值）+ 块内 distinct ≥ 12（不是常数填充）+ 块内 0xFF ≤ 12 且 0x00 ≤ 96（不是死总线）+ 7 对镜像寄存器逐对相等（没丢字节、没错位）。
   任何**单独一条**都不足以判定 —— 理由见 §1.2 的 60% 陷阱。
3. **阶段 0 的当前形态只能判定 17 条**。原因不是判据缺，是驱动的 dump 范围不够：
   现有 `headset=1` 只打印 `0x2688..0x26d3` 与 `0x2508..0x2537` 共 124 个地址，
   **不含** `0x230c`（时钟门控）、`0x1cb2`（VAUD18）、`0x0008/0x0009`（芯片身份）。
   把这 4 个地址加进 dump（仍是纯读），阶段 0 可判定项从 17 升到 21。
4. **「无耳机绝对测不了」共 10 项**，单独列在 §3，不混在检查表里。
5. **`0x26b6 == 0xFF` 不能证明 VAUD18 开着。** VAUD18 死掉时 `0x26b6` 读到的是 AB=3 的形状，
   与真空插座同形。两者用 `0x26b6` 无法区分，只能靠 `0x1cb2 bit0` 直读。这是本轮最容易被误判的一处。
6. **基线条件已尽可能钉死**（§4）：基线是「已初始化过、但 SW_EN=0」的状态，不是「冷启动复位态」。
   deb0/deb1/deb3/deb4 与 dtsInfo 打印的 `0x800/0x800/0x20/0x44` 逐位吻合，这是证据。

## 1. 检查项全表

38 条。列含义：

- **判据**：可执行的比较，带具体数值。凡是能写成 `(read8(r) & mask) == value` 的都写成了这个形状。
- **通过意味着什么**：这一条 PASS 时，能对外声称的事实。不写「值合理」这类。
- **失败意味着什么**：FAIL 时的第一条排查方向。**不同失败值指向不同根因**，所以写成了分支。
- **要手机吗**：`否` = 纯离线可判（脚本、源码、基线文件）；`是(一次 boot)` = 需要一次真机 dump 取数，但**不需要耳机**。
  全表没有任何一条需要插耳机。

### 1.2 为什么 A2/A3/A4 不能合并成「一致率」

这是本轮设计里最要紧的一处，因为它决定「死总线会不会蒙混过关」。

用 `accdet-baseline.json` 的 130 项做了一次实测计算：

| 假 dump 形状 | 与 130 项基线相等的个数 | 得分 |
|---|---|---|
| 全 `0x00` | **78** | **60.0%** |
| 全 `0xFF` | 7 | 5.4% |
| 真 stock 值 | 130 | 100% |

**全 0x00 的死总线读回能拿到 60% 一致率。** 因为基线本身就有 74 个块寄存器 + 4 个 misc 寄存器等于 0x00。
所以：

- 不能把「一致率」当唯一判据，否则一根死总线会以「60% 看起来还行」通过；
- 判据必须是**形状**（distinct 数、0xFF 计数、0x00 计数）+ **结构**（镜像对）+ **锚点**（`0x231d==0x06`）三者一起看；
- 脚本里专门为此引入了一个 `VOID` 状态：读通道已死时，「0xFF 不多」「镜像对相等」「期望值本来是 0x00 的三项」即使数值上全对，也判 `VOID` 而不是 `PASS`。
  自检第 17–18 条断言钉住了这一点（全 0x00 输入时 PASS 数必须为 0）。

### 1.3 B 组 · 空插座基线（11 条）

| 项 | 判据 | 通过意味着什么 | 失败意味着什么 | 要手机吗 |
|---|---|---|---|---|
| **B1** | `(read8(0x26b6) & 0xC0) == 0xC0`，即 cur_AB == 3 | 空插座基线正确：AB=3=`ACCDET_STATE_AB_11`（拔出）。同时说明 ACCDET 数字部分读到的是真实状态，不是恒 0 | `==0`（`0x00..0x3F`）：三段耳机形状 —— MICBIAS 没供电、插孔上拉异常，或基线本来就不是空插座；`==1`（`0x40..0x7F`）：四段；`==2`（`0x80..0xBF`）：本平台驱动无此分支，出现即判错（先查位序） | 是(一次 boot) |
| **B2** | `read8(0x26b6) == 0xFF` | 整字节与 stock 相同，包括无文档的低 6 位（stock 低 6 位 = `0x3F`） | bit[7:6]=3 但整字节 ≠ 0xFF：低 6 位无文档，**不算错，只记录**。本条失败不覆盖 B1 的结论 | 是(一次 boot) |
| **B3** | `read8(0x2688) == 0x00` | 未插入态下 AUXADC_SEL/SW 全关，与 stock 一致 | 非 0 ⇒ 有代码或残留状态把 AUXADC 接到了 ACCDET，后面的 ADC 读数不能当空插座基线 | 是(一次 boot) |
| **B4** | `read8(0x26a9) == 0x00` | bit0 `ACCDET_IRQ` 与 bit2 `EINT0_IRQ` 都没挂起。**这是「没有中断」，不是「没有插入」** | 非 0 ⇒ 有中断没清（可能上次 boot 残留）。不影响读通道结论，但阶段 2 之前必须先清（写 `0x26aa` 对应位），否则 IRQ 会一直被当成新事件 | 是(一次 boot) |
| **B5** | `read8(0x26b8) == 0xFF` | 中断上下文的 `0x26b8` bit[7:6] 与 work 上下文的 `0x26b6` 给出同一结论（`ACCDET_EINT0_MEM_IN`=3）。两条独立寄存器路径不矛盾 | ≠0xFF 而 `0x26b6` 正常 ⇒ EINT0 侧模拟通路（`0x2531 EINT0EN`、`0x252f VTH`）状态与 ACCDET 侧不同；阶段 2 要用 EINT0，必须先解释 | 是(一次 boot) |

| **B7** | 与 130 项基线逐项比，一致 ≥ 110/130（84.6%）；分母固定为 130，不是「读到的个数」 | 与 Android 留下的状态一致到可以认为「同一颗芯片、同一段地址、同一个状态」。**差异清单逐条打印，这是本项最有价值的输出** | < 110 ⇒ 不是状态漂移，是地址/字节序/丢字节。阈值取法：死 0 总线天然命中 78（60.0%），必须高于它，再留 32 个字节的漂移余量 | 是(一次 boot) |
| **B8** | 6 个块外寄存器：`0x2319==0x00`、`0x231d==0x06`、`0x2320==0x00`、`0x2323==0x00`、`0x1108==0x00`、`0x11c0==0xFC` | 复位/中断/辅助 ADC 六项与 stock 一致。`0x2319=0x00` 说明 `RG_ACCDET_RST` 已放开；`0x2323=0x00` 说明顶层中断状态干净 | `0x2319` bit1=1 ⇒ ACCDET 仍在复位，块读回全部不可信，先写 0 再重读；`0x2323` 非 0 ⇒ 顶层中断没清，阶段 2 的清 IRQ 会先撞到它 | 是(一次 boot) |

| **B10** | `(0x26b6>>6)&3 == (0x26b8>>6)&3` | 两条独立采样路径（work 上下文 vs IRQ 上下文）对空插座给出同一结论，排除单点读到坏值 | 两者不同 ⇒ 至少一侧读到中间态（ADC 未稳定）或某一侧地址错。**不要用其中任一侧下结论** | 是(一次 boot) |

### 1.4 C 组 · 寄存器可写性（7 条，全部阶段 1）

写通道的验证必须在「不破坏状态」的前提下做。选点原则：**选 vendor 自己在初始化里就会写、且写的是配置位而非电平清除位的字段**。

| 项 | 判据 | 通过意味着什么 | 失败意味着什么 | 要手机吗 |
|---|---|---|---|---|
| **C1** | 写 `0x26aa` bit[6:4]（`ACCDET_EINT_M_PLUG_IN_NUM`）：stock=`0x10`（值 1）→ 写 `0x20`（值 2）→ 读回 `0x20` → 写回 `0x10` → 读回 `0x10`；两次读都不得超时 | PMIF 写路径（WDATA + ACC 的 WR 位）通，且该字段可读回 | 读回仍是 `0x10` ⇒ 写没落地（WDATA 顺序错 / WR 位没置 / 通道非 IDLE）；读回 `0x00` 或 `0xFF` ⇒ 写坏了这一字节，**立刻停** | 是(一次 boot) |
| **C2** | 写后读回的 mask 内值 == 写入值。驱动内建：读旧 → `(old & ~mask) \| bits` → 写 → 再读 → 比 mask 内 | 日志里 `headset: verify failed at ...` 出现 **0 次** | 出现 1 次即定位到具体寄存器与 mask；≥ 2 次说明写通道整体不可用，退回阶段 0 | 是(一次 boot) |
| **C3** | 探针后 `read8(0x26aa) == 0x10`（整字节） | 只恢复了 bit[6:4]，bit0/2/3 没被碰到（这三条是电平清除位） | `0x11` / `0x14` / `0x06` 等 ⇒ 碰到了清除位或 `M_PLUG_IN_NUM` 没恢复；**此时不得进入阶段 2** | 是(一次 boot) |
| **C4** | 对 `0x014b`（全局 shutdown）与 `0x0240`（状态影子，禁 RMW）调用写函数必须返回 false，且**不产生任何总线事务**（PMIF 读计数不变） | 禁写门生效。`0x014b` 写错会关机，`0x0240` 做 RMW 会改掉 buck 状态 | 任一被写出去 ⇒ 立刻停手，这已经不是耳机子项目的问题 | 是(一次 boot) |
| **C5** | 写探针前后各读一次 `0x26a9`，两次都 `== 0x00` | 该字段确实是纯配置位，写它不会被当成事件 | 后一次非 0 ⇒ 该字段不是纯配置位，立即恢复并放弃这条探针，改用 C6 | 是(一次 boot) |
| **C6** | 备用探针：`0x26d0` bit[6:4]（`ACCDET_EINT1_M_PLUG_IN_COUNT`，本平台只用 EINT0）：stock=`0x00` → 写 `0x10` → 读 `0x10` → 写回 `0x00` → 读 `0x00` | C1 失败时的替代路径，同样证明写通道通 | 同样不落地 ⇒ 写通道整体不可用，不是选点问题 | 是(一次 boot) |
| **C7** | 读 PMIF `STA`(`0x08a8`)，取 `(v>>1)&0x7`，== 0（`SWINF_IDLE`） | 探针事务干净收尾，没有遗留的 WFVLDCLR | `== 6`（`WFVLDCLR`）⇒ 有读事务没 ACK，**下一次事务的 IDLE 等待永远不会成功**；必须先写 VLDCLR=1 再继续 | 是(一次 boot) |

**绝对不能碰的寄存器**（不是「不推荐」，是「碰了会关机或改掉电源状态」）：

| 地址 | 是什么 | 为什么绝对不碰 |
|---|---|---|
| `0x014b` | PMIC 全局 shutdown | 写入即关机。已有实测记录在 `DANGER-spmi-access.md` |
| `0x0240` | buck 状态影子 | 只读状态位，**任何 RMW 都禁止**（开关要走 `+1`/`+2` 别名）。`GPUEB-analysis.md:279` 记录过写完读回仍然 `enabled 0` |

另外两条硬约束（来自 `SPMI-PMIF-SPEC.md`）：
- 不访问 PMIF 偏移 `≥ 0x900`（那是 `spmi_pmif_mpu`，另一个设备，访问会 bus abort → 整机重启，已实测 3 次）；
- 所有事务只走 SWINF_2 的 `0x0880..0x08a8`。

### 1.5 D 组 · 前置项探测（6 条）

| 项 | 判据 | 通过意味着什么 | 失败意味着什么 | 要手机吗 |
|---|---|---|---|---|
| **D1** | `read8(0x230c) & 0x01 == 0` | `RG_ACCDET_CK_PDN=0`，ACCDET 时钟开着 → 整张初始化表与块读回都有效 | `==1` ⇒ 时钟被 gate，ACCDET 整段会读回 0（与 A4 的「全 0」互为因果）。**不要盲写 `0x230d`/`0x230e`**（这两个 SET/CLR 地址只有命名推断、源码无使用点，属【未验证】），先记录整字节并上报 | 是(一次 boot) |
| **D2** | 记录 `read8(0x230c)` 整字节 | 第一次观测到该地址。stock dump **不含**它，基线里也没有 | 永不 FAIL；但它是后续所有「时钟是否被关」判断的唯一依据 | 是(一次 boot) |

| **D4** | 若 D3 读到 0，初始化日志里必须出现 `0x1cb2` 由 0 变 1 且读回 1 | MICBIAS/VREF 有供电，阶段 2 之后的 cur_AB 读数才有解释力 | 没写 ⇒ 阶段 2 之后所有 cur_AB 读数都不能解释，**包括「看起来正确」的 AB=3** | 是(一次 boot) |
| **D5** | `read8(0x2319) == 0x00` | `RG_ACCDET_RST`(bit1)=0，ACCDET 逻辑可用 | bit1=1 ⇒ 复位没放开，块读回全部无效。先写 0 再重读，**不要直接跑初始化表** | 是(一次 boot) |
| **D6** | AUDDEC 块 48 个寄存器全部读到 | 第二个块边界（`0x2508..0x2537`）正确，48 个都在自旋上限内完成 | 缺 ⇒ `0x2537` 之后的地址可能不属于该从设备，或 dump 在这里停了 | 是(一次 boot) |

### 1.6 E 组 · 可以用「自身回环」验证的逻辑（6 条）

这一组要说明一个边界：**空插座下，涉及「状态变化」的逻辑大多只能做反向断言**。

| 项 | 判据 | 通过意味着什么 | 失败意味着什么 | 要手机吗 |
|---|---|---|---|---|
| **E1** | `headset=2` 每 50 ms 采样一次，连续 ≥ 10 条 sample 行的 `AB` 字段全 == 3 | 采样路径幂等，没有把噪声当插入 | 出现 0/1/2 ⇒ 要么 ADC 在动（模拟前端不稳），要么读通道间歇丢字节。用 A8 的两次全量 dump 交叉验证 | 是(一次 boot) |
| **E2** | 同上，`EINT0` 字段全 == 3 | EINT0 侧与 AB 侧同时稳定，排除单侧漂移 | 非 3 ⇒ EINT0 模拟通路在动；阶段 2 的插入门控依赖它，必须先解释再跑 | 是(一次 boot) |
| **E3** | 写 `0x26aa` bit0=1 再写 0，之后 `read8(0x26a9) == 0x00` | **这是整个 E 组唯一能覆盖 IRQ 通道的检查**。空插座下 `0x26a9` 本来就是 0，「清一个已经为 0 的标志」在观测上等于什么都没发生，所以只能做反向断言 | `0x26a9` 变 1 ⇒ 写 CLR 位本身被芯片当成事件，或地址错位到 `0x26a9` | 是(一次 boot) |
| **E4** | 写 `0x26aa` bit0=1 后立刻读，`bit0 == 1`；写回 0 后读，`bit0 == 0` | 该位是电平保持型（可写可读、非自清），`clear_irq()` 里「先置 1 等 IRQ 落下再释放」的逻辑成立 | 写 1 读回 0 ⇒ 该位被硬件立即自清（行为与文档描述不同），C1/C3 的恢复逻辑要改，且 E3 的结论无效 | 是(一次 boot) |
| **E5** | 整段日志里 `headset: cable ` 出现 **0** 次、`headset: microphone button` 出现 **0** 次 | 门控逻辑正确：`check_cable_type()` 在 `eint_sync=false` 时直接 return，AB=3 走 PLUG_OUT 分支不产生事件 | 出现 ⇒ 门控被绕过（`eint_sync` 被误置 true，或 `startup_plug` 把 `eint==0` 当成插入）。**这是空插座就能抓到的真实 bug** | 是(一次 boot) |
| **E6** | 只记录 `(STATE, AB)` 组合，stock 为 `(0, 3)` | 将来插耳机后的对照数据 | **永不 FAIL**：STATE 语义未验证，不能作判据 | 是(一次 boot) |

### 1.7 关于 `cur_AB` 的「读两次」能不能验证门控逻辑

任务里问到这一条，直接回答：**不能**。

`check_cable_type()`（`mt6368-accdet.c:2003-2120`）的门控是：

```c
if (!accdet->eint_sync) return;          // 前态门
switch (detector) { ... }                 // 前态 + eint_sync_flag
```

两个门控变量 `accdet->eint_sync` 与 `accdet->detector` 都是**驱动内部状态**，不是寄存器。
空插座下 `eint_sync` 恒为 false（只有 `handle_eint(plugged=true)` 才会置 true，而那需要 EINT0 事件）。
所以「读两次 `0x26b6`」得到的是两个 3，走的是同一个 `if (!eint_sync) return;` 分支，
**没有进入 switch，也没有触碰任何前态比较**。

能验证的替代品是 E5（反向断言：不能出现 cable 变更打印）与 E1（幂等：AB 恒 3 不抖）。
真正的前态迁移验证被归入 §3 的 F 组（需要耳机）。

- **必须全 PASS**：A1、A2、A3、A4、A6、A7、B1、B2、B3、B5、B7、B8、B9、B10、D1、D5、D6
- **必须全 INFO**（只记录）：B6、D2、D3

- **A8 需要第二次 boot 或第二次调用**：`--second` 比对必须 0 差异
- **B4**：`0x26a9 == 0x00` 必须 PASS。若 FAIL 不阻断阶段 0 结论，但阻断阶段 2

| 失败项 | 下一步 |
|---|---|
| A1 = `0x00` | 芯片被复位。基线作废，但可以继续做 A2/A6（形状判据不看基线）。不要进阶段 1/2 |
| A1 = `0xFF` | 通道没通。查 SID 是否真的是 5、PMIF 仲裁是否已由 LK 配好、MPU 是否拒绝。**不要改任何寄存器** |
| A2 ≤ 3 distinct | 死总线。同上 |
| A4 ≥ 120 个 0x00 且 D1 = 1 | ACCDET 时钟被 gate。这是**唯一**需要用 `0x230d/0x230e` 的场景，而这两个地址属【未验证】，先只记录、上报，不盲写 |
| A6 有对不等 | 地址错位。**先修地址，别看 B7** |
| A7 有 timeout | 定位到日志里 `read timeout at 0x....` 的地址。若是固定的一个地址，怀疑该寄存器不存在或需要不同访问宽度 |
| B1 ≠ 3 | 分三种：AB=0 → 查 D3（VAUD18）；AB=1 → 异物或基线非空插座；AB=2 → 查位序 |
| B7 < 110 | 打印的差异清单就是答案。若差异集中在某一段连续地址 → 地址偏移；若散落 → 状态漂移（可能真有人动过寄存器） |

### 2.2 阶段 1 · 最小写入验证

#### 写什么

**首选探针：`0x26aa` 的 bit[6:4]**（`ACCDET_EINT_M_PLUG_IN_NUM`）

| 步 | 动作 | 期望读回 |
|---|---|---|
| 1 | 读 `0x26aa`，记录原值（stock 应为 `0x10`） | `0x10` |
| 2 | 读 `0x26a9`（前置：必须 `0x00`） | `0x00` |
| 3 | 写 `0x26aa = (old & ~0x70) \| 0x20` = `0x20` | — |
| 4 | 读 `0x26aa` | `0x20` |
| 5 | 写回 `0x26aa = (old & ~0x70) \| 0x10` = `0x10` | — |
| 6 | 读 `0x26aa` | `0x10` |
| 7 | 读 `0x26a9` | `0x00` |
| 8 | 读 PMIF `STA` | `(v>>1)&7 == 0` |

选这个点的理由：

- 该字段 vendor 自己在初始化第 43 步就写（值 1），属**设计上可写的配置位**；
- 同一字节的 bit0/2/3 是**电平清除位**，本探针不碰；
- 整字节只有 4 个 bit 有效，剩下的 bit[7] 与 bit[3:0] 在 stock 里是 0，不会误伤。

**备用探针：`0x26d0` bit[6:4]**（`ACCDET_EINT1_M_PLUG_IN_COUNT`）。C1 失败时用它区分「选点问题」与「写通道问题」。

#### 读什么

每一步的读回都要打出来，并且**整字节比较**，不只比 mask 内：

```
headset: probe 0x26aa read 0x10
headset: probe 0x26aa write 0x20 (mask 0x70, saved 0x10)
headset: probe 0x26aa read 0x20 expect 0x20 -> ok
headset: probe 0x26aa restore 0x10
headset: probe 0x26aa read 0x10 expect 0x10 -> ok
headset: probe 0x26a9 read 0x00 expect 0x00 -> ok
headset: probe pmif sta 0x%08x fsm 0 -> ok
headset: probe result PASS (2 writes, 5 reads)
```

失败时：

```
headset: probe 0x26aa read 0x10 expect 0x20 -> FAIL (write did not land)
headset: probe 0x26aa restore 0x10
headset: probe result FAIL; stopping before init table
```

#### 怎么恢复

1. **每一步失败都必须先恢复再返回**：写回 `saved & ~mask | original_bits`；
2. 恢复时用**整字节写**（`0x26aa = 0x10`），不用 RMW —— 读-改-写在失败路径上会再引入一次读依赖；
3. 恢复后**必须再读一次**确认 `0x26aa == 0x10`（C3）；
4. 若恢复失败，**不要重试**。重试会在一个已经不确定的字节上叠加写入。直接上报，让人决策。

#### 判据

C1、C2、C3、C4、C5、C7 全 PASS。C6 只在 C1 FAIL 时才跑。

若 C5 FAIL（写探针引起 IRQ）→ 换 C6；若 C6 也 FAIL → 写通道整体不可用，**不进阶段 2**。

### 2.3 阶段 2 · 跑初始化表，然后回读全块

**这一阶段有风险，先说风险。**

| 风险 | 具体后果 | 缓解 |
|---|---|---|
| 写 `SW_EN`(`0x268a` bit0)=1 | ACCDET 模拟前端上电，MICBIAS 输出，插孔上的偏置电压变化。空插座下无害，但**会改变几十个寄存器的读回值**，让 B7 的「0 差异」预期失效 | 明确选定一版表：**驱动当前实现不写 `SW_EN`**（只在 EINT 插入分支写），50 项表的第 48 步写。两者预期差异不同（见 B11） |
| 写 `0x1cb2`=1（VAUD18） | LDO 上电，电流增加。**若该 LDO 已被别处以不同电压配好，可能冲突** | 先读 D3：若已是 1，跳过；若为 0，这是必须的，但也只在阶段 2 做 |
| 写 `0x2319` bit1（ACCDET 复位）脉冲 | 复位瞬间 ACCDET 状态机归零。空插座下无害 | 已有 vendor 序列，先置 1 再置 0，中间无延时（源码就是这样） |
| 写 `0x26aa` bit0/2（电平清除） | 若 `0x26a9` 本来有 pending，会被清掉 —— 而清掉之后**无法恢复**（W1C 性质） | 阶段 2 开始前必须先读 `0x26a9` 并记录（B4）。若本来非 0，**先不进阶段 2** |
| 整表 44 写串行 69.9 ms | 期间若 keys 驱动插进来抢 SWINF_2，事务会互相破坏 | 现有实现把 headset 跑在 keys worker 里、与 keys 事务串行（`hakios.mt6895_keys.c:508/655`）。这一点必须保持 |
| 恢复逻辑本身出错 | 写完不恢复，或恢复顺序错（`save[]` 反序回放） | C2 的 verify 已覆盖单点；整体恢复看日志 `headset: restored %u configuration bytes: ok` |

#### 写什么

按 `findings/accdet-init-table.json`（50 项）或驱动现有 `accdet_init_once()`（34 个寄存器 / 29 次 `configure()`）。
**两者不是一回事**，差异见 §4.3。

#### 预期输出

```
headset: mode 2 on SID 5, serialised in keys worker
headset: 0x2688 = 0x00
... （124 行块 dump，与阶段 0 同格式）
headset: init step  1/44 0x1cb2 mask 0x01 val 0x01 -> 0x01
headset: init step  2/44 0x26aa mask 0x01 val 0x01 delay 400us
headset: init step  3/44 0x26aa mask 0x01 val 0x00
headset: init step  4/44 0x268a mask 0x02 val 0x02 delay 3000us
headset: init step  5/44 0x268a mask 0x02 val 0x00 delay 1500us
...
headset: init step 44/44 0x268a mask 0x01 val 0x01 delay 65000us
headset: init done 44 writes, 4 verify checks, elapsed 69900 us
headset: sample IRQ 0x00 AB 3 EINT0 3 FSM 0 sync 0
headset: sample IRQ 0x00 AB 3 EINT0 3 FSM 0 sync 0
...
headset: post-init block accdet read 76/76 distinct 23 zero 40 ff 7
headset: post-init diff vs baseline: 0 bytes
headset: mode 2 initialised, polling every 50 ms; PCM playback not implemented
```

#### 判据

- B11：post-init 的 124 个块寄存器与基线 **0 差异**（或用 50 项表时恰 1 个字节 `0x268a` = `0x41`）；
- D4：若 `0x1cb2` 原为 0，日志里必须看到它变 1；
- C2：`verify failed` 出现 0 次；
- E1/E2：10 条以上 sample 行，AB 与 EINT0 恒 3；
- E5：`headset: cable ` 出现 0 次。

#### 失败时的下一步

| 现象 | 下一步 |
|---|---|
| 某步 `verify failed at 0xXXXX mask 0xYY wanted 0xA got 0xB` | 该寄存器的某位**写不进去**（可能是只读位或需要先解复位）。只这一条失败时，把该项降级为「只读校验」，其余继续 |
| 整张表跑完，块内出现大量差异 | 恢复逻辑（`restore_configuration()`）没跑或跑错。看 `headset: restored %u configuration bytes` 那行 |
| AB 变成 0 或 1 并稳定 | **先怀疑 D3/VAUD18**，不是「插了耳机」。空插座下 AB 不该是 0 |
| `headset: IRQ clear timeout, mask 0x%02x` | `0x26a9` 的对应位清不掉。可能是该位不是电平保持、或顶层 `0x2323` 没跟着清 |
| 板子重启 | 最可能是写到了 `≥0x900` 或 `0x014b`。**下次 boot 先只做阶段 0**，确认基线还在 |

## 3. 「无耳机绝对测不了」清单（10 项）

这些项不混在 §1 的表里，也不在 `headsetless-checks.json` 的 `checks` 数组里，
单独放在 `not_testable_without_headset`。

| # | 项 | 为什么空插座下测不了 | 拿到耳机后第一件事 |
|---|---|---|---|
| **F1** | 插入识别 | 需要 EINT0 由拔出态翻到插入态、`0x26a9` bit2 置位。空插座下这两个事件不会发生 | 插一次，看 `0x26a9` bit2 是否置 1、`0x26b8[7:6]` 是否离开 3 |
| **F2** | 三段 vs 四段判定 | AB=0 与 AB=1 只能由插头接地环决定，无法伪造 | 两种插头各插一次，记录 `0x26b6[7:6]` 与 `cable` 打印 |
| **F3** | 按键 hook/volume | 按键靠 MICBIAS 下 AB=0 加 ADC 毫伏分档（xaga 3-key：80/220/400 mV），必须有实体线控 | 按三个键，记录 ADC 读数与 `microphone button pressed` |
| **F4** | 阻抗 / LineOut 判定 | `R≥5000Ω` 走 `mt6368_accdet_read_audio_res()`，需要真实负载 | 用已知阻抗的负载（或直接用一个 ≥5kΩ 电阻串在 MIC 与 GND）验证 `RET_GT_5K` |
| **F5** | 出声 | 需要负载才能确认 HPL/HPR 有输出；且当前驱动无 PCM 通路 | 先补 PCM，再用耳机听 |
| **F6** | 拔出消抖实际时间 | DT 值 `accdet-plugout-debounce=1` 只有配置，空插座下没有可观测的拔出沿 | 插拔各一次，量 `EINT0 plug out` 打印的时间差 |
| **F7** | 插入后 HPL/HPR mux 切换时序 | 空插座下 mux 停在 `Open`，切换序列不会发生（`DEVICE-PROBE-STOCK.md:3.7` 记录 `mux_select[MUX_HP_L]==0`） | 插一次，逐拍读 HPL/HPR mux |
| **F8** | 四段 MIC 录音通道 | 需要耳麦 mic 才能验证 `AIF1_RX → ADC` 通路 | 用耳麦录一段，看是否有 PCM |
| **F9** | `eint_sync` 状态迁移与 6 秒 micbias 计时器 | 两者都以插入事件为起点，空插座下永不进入 | 插上后等 6 秒，看 `six-second timer disabled mic bias` 是否出现 |
| **F10** | IRQ 由 1 落 0 的真实清除过程 | `0x26a9` bit0/bit2 在空插座下恒为 0，W1C / 电平保持的完整握手无法触发。E3/E4 只能做**反向断言**（清一个本来就 0 的标志不会变 1） | 插入让 bit 置 1，再走完整清除序列，观察 `clear_irq` 的轮询是否在 16×25 µs 内成功 |

**共同点**：这 10 项全部依赖一个**物理事件**（插头接入改变插孔阻抗），而软件无法伪造。
能伪造的只有「寄存器值」，但伪造寄存器值验证不了「芯片从物理事件里推断出了什么」。

## 4. baseline 条件不确定性的说明

`accdet-baseline.json` 的 `source` 字段写的是：

```json
"source": "stock Android dump_reg, no headset plugged, 2026-11-14"
```

这句话只钉住了两件事：**来自 stock Android 的 `dump_reg`**、**当时没插耳机**。
下面三件事是**未知**的，必须写清楚，否则会把「状态差异」误判成「读通道坏了」。

### 4.1 已知的：采集时刻芯片处于什么状态

用基线自身的数值反推，可以确定三件事：

**① 基线是「已初始化过」的状态，不是冷启动复位态。**

vendor 的 `dump_register()` 会打印 dtsInfo：

```
accdet_dts:deb0=0x800,deb1=0x800,deb3=0x20,deb4=0x44
```

而基线里对应的 debounce 寄存器是：

| 字段 | dtsInfo 期望 | 基线实测 | 合成值 |
|---|---|---|---|
| deb0 | `0x800` | `0x2697=0x00`、`0x2698=0x08` | `0x0800` ✅ |
| deb1 | `0x800` | `0x2699=0x00`、`0x269a=0x08` | `0x0800` ✅ |
| deb3 | `0x20` | `0x269d=0x20`、`0x269e=0x00` | `0x0020` ✅ |
| deb4 | `0x44` | `0x269f=0x44`、`0x26a0=0x00` | `0x0044` ✅ |

四个都逐位吻合。`0x2697..0x26a0` 这一段的复位值不可能是这组数（DEBOUNCE 复位值无文档，
但四个字段同时命中 dts 配置的概率极低）。结论：**`accdet_init()` 已经跑过**。

**② 但 `SW_EN` 是 0。**

```
0x268a = 0x40 → SW_EN(bit0)=0  SEQ_INIT(bit1)=0  EINT0_inv(bit6)=1
0x268b = 0x00
0x26ad = 0x00  → HWMODE_EN(bit0)=0（S/W 模式）
```

`0x2694 = 0x41`、`0x26a3 = 0x35`、`0x26a4 = 0x5e`、`0x26aa = 0x10` 也都与 dts 展开值吻合
（见 `ACCDET-INIT-SEQUENCE.md` §2 的 headset-mode-setting 15 项表）。

**③ 所以基线的准确描述是**：

> 「Android 跑过 `accdet_init_once()`，之后某次拔出事件把 `SW_EN` 关掉了，
> 停在『配置已写入、检测未使能』的状态。插孔空着。」

这个描述**不是** `"no headset plugged"` 这几个字能表达的，但它对判据有直接影响：
**阶段 2 跑完初始化后，若实现也把 `SW_EN` 关掉（或本来就不写），块内应当 0 差异**（B11）。

### 4.2 未知的三件事

| # | 未知 | 影响 | 怎么处理 |
|---|---|---|---|
| 1 | **采样时刻距关机多久** | 若中间有别的电源事件（充电器插拔、PMIC 复位），部分寄存器可能漂移 | B7 的阈值取 110/130 而不是 130/130，就是给这个留余量。**逐项差异清单必须打印**，漂移会表现为少数几项不同且集中在电源相关地址 |
| 2 | **是否曾有 moisture 检测触发过** | `0x268b` bit4、`0x2688`（AUXADC）会被 moisture 路径改动。基线里 `0x268b=0x00`、`0x2688=0x00`，说明**至少采样时 moisture 是关的** | 若实测 `0x2688 ≠ 0`，先查是不是 moisture 残留，而不是怀疑读通道 |
| 3 | **帧同步的 `0x26b6` 是不是稳态** | `dump_register()` 除了 probe 时调用，**每次中断处理完也会调用**（`mt6368-accdet.c:2414`）。所以基线可能是「某次事件刚处理完」的快照 | `0x26b6=0xFF`、`0x26b8=0xFF` 是两个独立寄存器给同一结论，且 `0x26a9=0x00`（无 pending）。三者一致说明快照是稳态。若实测三者不一致，先看 B10 |

### 4.3 基线不覆盖的 4 个地址

`accdet-baseline.json` 有 130 项 = 124 个块寄存器 + 6 个 misc。
**不含**这 4 个在初始化表里出现、或本轮必须探测的地址：

| 地址 | 为什么不在基线里 | 本轮的处置 |
|---|---|---|
| `0x230c` | vendor 在 `dump_register()` 的 `pr_notice` 里**确实打这一行**（`mt6368-accdet.c:524-532`，格式 `(0x0)=0x0 (0x230c)=0x%x (0x2319)=0x%x (0x231d)=0x%x`）。但本仓库存档的基线来自 `cat_register()` 那条路径（`[0x..]=..` 格式，`:605-640`），那条路径**不含 `0x230c`**。全仓库没有任何一次捕获记录到它的值 | D1/D2 必须新增读取。**这是「时钟是否被关」的唯一依据，属【未验证】** |
| `0x1cb2` | vendor 根本不 dump 它 | D3 必须新增读取 |
| `0x248c` | 初始化表第 38 步写它（`RG_NCP_PDDIS_EN`），vendor 不 dump | 只在阶段 2 回读 |
| `0x0008` / `0x0009` | vendor 在 probe 时打过一次 `(0x8)=0x30 (0x9)=0x68`（`DEVICE-PROBE-STOCK.md:799`），但那是 **init 时刻**的单次观测，不是稳态 | A5 用来做地址译码交叉验证，**属【未验证】** |

另外 `0x2529` / `0x252d` 在原始 dump 文本里**出现了两次**（既在 AUDDEC 块里，又在 `[0x2529]=0x4,[0x252d]=0x8f` 单独一行）。
`accdet-baseline.json` 里各只存一次，值相同。这解释了「130 项 vs 原始 132 行」的差。

### 4.4 基线与两份 dump 文本的自洽性（已核对）

| 核对 | 结果 |
|---|---|
| `accdet-baseline.json` 的 130 个值与 `accdet-baseline-dump.txt` 逐项比 | **0 处不一致** |
| `accdet-baseline-dump.txt` 与 `accdet-after-round20.txt` | **md5 相同**（`f5b3a1f437e0696d1053eeb785a1cb99`），说明两次 dump 是同一份数据，不是两次独立采集 |
| JSON 有、dump 文本没有的 6 个 | `0x1108` `0x11c0` `0x2319` `0x231d` `0x2320` `0x2323` —— 这 6 个在 dump 文本里是 `[0x231d]=0x6` 这种格式，提取脚本单独处理过 |
| dump 文本有、JSON 没有的 | 无 |

**最后一句**：`accdet-after-round20.txt` 与基线 md5 相同这件事，意味着**「两次独立采集得到相同结果」这个结论在本轮并不成立** ——
它是同一份文本的两份拷贝。所以 A8（两次 dump 一致）**必须在真机上重新做一次**，不能引用这条 md5。

## 5. 脚本与自检

`headsetless-check.py` 是本文的可执行版本。

```bash
# 自检（33 条断言，不碰设备）
python3 docs/headset-wip/headsetless-check.py --selftest

# 判定一份 dump
python3 docs/headset-wip/headsetless-check.py dump.txt

# 带上第二次 dump 做 A8
python3 docs/headset-wip/headsetless-check.py dump1.txt --second dump2.txt

# 阶段 2：dump 取自初始化之后
python3 docs/headset-wip/headsetless-check.py dump.txt --post-init
```

exit code：`0` 无 FAIL ／ `1` 有 FAIL ／ `2` dump 本身不可用（空、全 0x00、全 0xFF）／ `3` baseline 读不了。

自检覆盖的边界：空文件、全 0xFF、全 0x00、只有 3 个寄存器、4 种格式错误行、
横幅行不计坏行、单点差异、超时行、AB=0、两侧 AB 不一致、10 次采样恒 3、
混入一次 AB=0、`--post-init` 的 0 差异与 1 差异、两次 dump 相同/差一字节/覆盖范围不同、
只有提示行。

### 5.1 用真 stock 数据跑出来的结果

把 `accdet-baseline-dump.txt` 转成驱动的行格式后跑：

```
PASS 17   FAIL 0   SKIP 18   VOID 0   INFO 3

按阶段（可判定 = PASS+FAIL；SKIP/INFO 不计入分母）：
  阶段 0 只读零风险          可判定 17 项：PASS 17  FAIL  0  其余 10
  阶段 1 最小写验证          可判定  0 项：PASS  0  FAIL  0  其余  9
  阶段 2 初始化表后回读        可判定  0 项：PASS  0  FAIL  0  其余  2
```

17 项 PASS 是：A1/A2/A3/A4/A6/A7/B1/B2/B3/B4/B5/B7/B8/B9/B10/D5/D6。
SKIP 的 10 项是 A5（缺 `0x0008`）、A8（没给 `--second`）、B11（没加 `--post-init`）、
D1/D2/D3/D4（缺 `0x230c`/`0x1cb2`）、E1/E2（无 sample 行）、E3/E4（无写路径）。
这说明**当前形态的 `headset=1` 只能判定 17 条**，与 §1.8 的数字一致。

### 5.2 死总线的处理（这一节是设计要点）

跑全 0x00 的假 dump：

```
PASS 0   FAIL 9   SKIP 18   VOID 8   INFO 3
...
VERDICT: 124 个块寄存器全部读回 0x00。
         这是死总线，不是芯片状态：正常读回会逐寄存器不同。
         注意它对本基线能拿到 78/130 相等（60.0%），占比看起来像进展，其实不是。
```

`VOID 8` 就是 A3/A6/A7/B3/B4/B10/D6 这些「数值上对但没信息量」的项。
**没有 VOID 机制的话，死总线会拿 8 个 PASS**，其中 A6（镜像对相等）看起来还特别有说服力。
