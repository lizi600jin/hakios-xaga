## 1. 怎么做到的：把内核 msgbuf 从 128 KiB 提到 1 MiB

### 之前为什么看不到

| trial | msgbuf | 日志起点 | `headset` 输出 |
|---|---|---|---|
| 695 | 128 KiB | 28.08 s | **无** |
| 696 | 128 KiB | 28.85 s | **无** |
| 697 | 128 KiB | 24.21 s | **无** |
| 698 | 128 KiB | 24.18 s | **无** |
| **699** | **1 MiB** | **19.66 s** | **✅ 129 项** |

**`headset: mode 1` 打印在 19.97 秒** —— 正好落在 128 KiB 窗口（24 秒起）**之外**。

`subr_log.c:570` 的 msgbuf 是环形缓冲，写满归零覆盖。128 KiB 只保留最近约 24 秒，
而 `headset` 初始化在 20 秒左右，**一直被吞掉**。

### 改动

`config/MASTER:286`（`msgb_small` 那一行）：

```diff
-options   CONFIG_MSG_BSIZE_DEV=131072
+options   CONFIG_MSG_BSIZE_DEV=1048576
```

| 项 | 值 |
|---|---|
| `MAX_MSG_BSIZE`（`bsd/sys/msgbuf.h:68`） | 1 MiB，**符合上限** |
| BSS 增长 | **917504 = 896 KiB**，与缓冲增长**精确相等** |
| `smsg_bufc` 的 VA | **未变**（`0xfffffff007cf389c`） |
| 三个驱动源码 | 与 695 基线 `6a51ef2` **逐字节一致** |

> BSS 增长恰好等于缓冲增长，说明链接器腾出了空间，**没有覆盖其他 BSS 对象**。

### 单变量保证

boot-args 与 695 **完全一致**（`witness=0`、`cohnone=0`、`headset=1`），
只改 `mali_trial` 标签。**这次只动内核的 msgbuf 大小，不动任何行为参数。**

## 2. 判据结果（用 `docs/headset-wip/tools/accdet-check.py` 跑）

工具自检 **5/5 通过**（能正确拒绝全 `0x00` 死总线、全 `0xFF` 无应答、坏镜像对）。

### 2.1 形状 ✅

| 项 | 阈值 | 实测 | 结果 |
|---|---|---|---|
| distinct | ≥ 12 | **16** | ✅ |
| `0xFF` 计数 | ≤ 12 | **7** | ✅ |
| `0x00` 计数 | ≤ 96 | **91** | ✅ |

### 2.2 结构 ✅ —— 这是最强的一条

**7 对镜像寄存器全部相等：**

| 对 | 值 |
|---|---|
| `0x2697` / `0x2699` | `0x10` / `0x10` |
| `0x2699` / `0x269b` | `0x10` / `0x10` |
| `0x26a3` / `0x26a4` | `0xee` / `0xee` |
| `0x26c4` / `0x26c6` | `0xff` / `0xff` |
| `0x26c6` / `0x26c8` | `0xff` / `0xff` |
| `0x26c8` / `0x26ca` | `0xff` / `0xff` |
| `0x26c5` / `0x26c7` | `0x1f` / `0x1f` |

**7/7 相等同时排除了两件事**：死总线（不会产生成对结构）、读错地址（镜像不会同时错）。

### 2.3 锚点 ❌（但有明确解释）

```
0x231d = 0x00    期望 0x06
```

`HEADSETLESS-TEST-PLAN.md:49` 早就写明这个值的含义：

> `0x00` = **芯片被复位过**（基线作废，**通道未必坏**，看 A2）
> `0xFF` = 从设备无应答（SID 错 / PMIF 仲裁没起 / MPU 拒绝）

**读到 `0x00` 而不是 `0xFF`，本身就证明 SID 5 通道是通的。**

XNU 启动时 MT6368 不在 Android 那种已初始化状态，所以 `0x231d` 不是 `0x06` 是合理的。

## 3. 关键寄存器读数

### 3.1 耳机检测相关

| 寄存器 | 值 | 含义 |
|---|---|---|
| `0x26b6` | **`0xff`** | `cur_AB = 3` = **拔出**（符合预期，没插耳机） |
| `0x26b8` | `0xff` | `EINT0_MEM_IN = 3` = 拔出 |
| `0x26b7` | `0x00` | `ACCDET_STATE = 0` |
| `0x26a9` | `0x00` | 无 ACCDET IRQ |
| `0x26aa` | `0x00` | IRQ_CLR 无待清 |
| `0x1cb2` | **`0x01`** | **VAUD18 已开启** |

### 3.2 `0x1cb2 = 0x01` 解除了判据约束 (c)

判据约束原文：

> 若 `0x1cb2` bit0 == 0（VAUD18 未开），`cur_AB` 读数不能作为检测成功的证据

**实测 `0x01`，bit0 = 1，VAUD18 是开的。所以 `0x26b6` 的读数有判据价值。**

### 3.3 ACCDET 块的真实结构（非零读数）

```
0x26a3 = 0xee    0x26a4 = 0xee    0x26a5 = 0x0e
0x26a6 = 0xbf    0x26a7 = 0x0a
0x2697 = 0x10    0x2699 = 0x10    0x269b = 0x10    0x269d = 0x10
0x269f = 0x05    0x26a1 = 0x04
0x26c2 = 0x10
0x26c4..0x26cb = ff/1f 交替 4 对
```

**这些值不可能来自死总线。**

## 5. 🔴 一个必须说清的限制（6.1-Sol 提过，我核实成立）

`mode 1` 完成一次只读 dump 就 return（`hakios.mt6895_headset.c:495-497`）：

```c
if (!dump_block(AUDDEC_ANA_LO, AUDDEC_ANA_HI) || mode == 1) {
    return;
}
```

**所以 `headset=1` 永远不会启动检测轮询。** 带耳机运行 `headset=1`
只能取得**那一刻的寄存器快照**，不能据此验收插拔、按键或出声。

**要验证插入检测，必须用 `headset=2`。**

## 6. 下一步（已可直接执行）

### 实验 700：`headset=2` + 插耳机

| 项 | 值 |
|---|---|
| 基线 | 699（同一内核，`msgbuf` 1 MiB 已就位） |
| 改动 | `headset=1` → `headset=2` |
| 动作 | **插着实体耳机刷机并运行** |
| 关键读数 | `0x26b6`（`cur_AB`）、`0x26b8`、`0x26a9`（IRQ）、`0x26b7`（状态机） |
| 判据 | `cur_AB` 从 3 变成 0（三段）或 1（四段）；或 `0x26a9` bit0 置位 |

**`headset=2` 会执行约 30 次寄存器写**（`accdet_init_once()`），
比 `mode 1` 风险高，但这是唯一能做插入检测的模式。

**风险控制**：`mode 2` 有 `restore_configuration()` 路径，失败会还原。
且内核 msgbuf 现在是 1 MiB，**任何失败都会被完整记录**。

### 对照：先拔耳机跑一次 700，再插耳机跑 701

这样能拿到**同一内核、同一参数下的两组读数**，直接对比 `cur_AB` 的变化。
**今晚有实体耳机，这个对比是可行的。**
