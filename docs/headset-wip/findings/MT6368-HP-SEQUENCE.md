## 0. 一句话（已按 Codex 复核修正）

## 1. 提取方法

```bash
readelf -sW snd-soc-mt6368.ko | grep FUNC | grep -i hp_
aarch64-linux-gnu-objdump -dr --start-address=0x8be0 --stop-address=0x9358 snd-soc-mt6368.ko
```

`mt_hp_event`（`:0x8be0`，1912 字节）是上电主函数。
它的调用表：

| 调用 | 次数 |
|---|---|
| `regmap_write` | **46** |
| `regmap_update_bits_base` | **20** |
| `usleep_range` | 4 |

**提取到的常量写入 45 条**（其余是条件分支里的重复写）。

## 1.5 🔴 本表已修正（Codex 2026-11-15 复核，我核实成立）

**原表有四处硬错误，不能照抄：**

| # | 错误 | 实际 |
|---|---|---|
| 1 | **`update_bits` 的 mask/value 搞反了** | `regmap_update_bits_base(map, reg, **mask=w2**, **val=w3**, ...)`。反汇编 `mov w2,#0x7` / `mov w3,#0x2` 是「mask=0x7, val=0x2」，我原来写成「mask 0x02 ← 0x07」 |
| 2 | 把 **HPSPK**、阻抗检测、PRE_PMD 混进普通 HP | 这些是不同分支，普通耳机不走 |
| 3 | 普通 HP 的 `0x2589` 终值 | **应为 `0x3a`（低四位 `0xa`）**，不是 bit0/1/3 全 1 |
| 4 | 把 `0x2508–0x2537` 当 `AUDDEC` | **那是 `AUDENC` 区**，不是 `0x2588` 起的 `AUDDEC` |

**修正后的 `0x2589` 推演**（三种 update 叠加）：

```
write 0x30                      -> 低四位 0x0
update mask 0x03 val 0x01       -> 低四位 0x1
update mask 0x03 val 0x02       -> 低四位 0x2
update mask 0x0c val 0x08       -> bit2-3 = 0b10  -> 低四位 0xa
最终 0x3a
```

**与 Codex 给出的 `0x3a` 一致。**

### 分三段看

| 段 | 步骤 | 作用 |
|---|---|---|
| **A. 时钟与偏置** | 1-13 | `0x2595/96` 时钟、`0x25a0/01/02` 上电时序、`0x2609/0a` 左右偏置 |
| **B. 参考与 DAC 数字** | 14-25 | `0x2589` 参考、`0x2588` 启动、`0x258a` 数字渐升（`0x0c→0x3c`） |
| **C. 模拟输出使能** | 26-45 | `0x2588` 升到 `0xff`、`0x258a` 经 `0xfc/0xff/0xcf/0xc3/0x03`、最终 `0x2589` 三处置位 |

**关键终值（修正后）**：
- `0x2588 = 0xff`（DAC 模拟全开）
- `0x258a = 0x03`（DAC 数字就绪）
- **`0x2589 = 0x3a`**（不是 bit0/1/3 全 1 —— 见 §1.5 的推演）

**但这张表仍不能直接照抄**：它把 HPSPK / 阻抗检测 / PRE_PMD 几个分支混在一起，
普通三段耳机只走其中一部分。**Codex 正在按完整 CFG、循环和 helper 恢复普通 HP 的
独立上/下电序列。**

## 4. 这些寄存器在哪

全部在 **`MT6368_AUDDEC_ANA`** 区（`mt6368.h:370` 起）：

```c
#define MT6368_AUDDEC_ANA_CON0   0x2588
#define MT6368_AUDDEC_ANA_CON1   0x2589
#define MT6368_AUDDEC_ANA_CON2   0x258a
...
```

### 🔴 一个我搞错的区段（Codex 指出）

**`0x2508–0x2537` 是 `AUDENC`（录音编码）区，不是 `AUDDEC`（播放解码）区。**

我原来说「headset=1 已经 dump 过整个 AUDDEC_ANA 区 48 项」，
**实际那 48 项在 `AUDENC` 区。**

**含义**：`0x2588` 起的 `AUDDEC_ANA` **我们从未读过**，
所以「读写通路已验证」这个结论对 `AUDDEC` 不成立。

**这是必须在 `headset=3` 里先验证的事**：读 `0x2588/0x2589/0x258a`，
确认能读到合理值，再开始写。

## 5. 还缺什么（这才是出声的真正门槛）

### 5.1 已验证的

| 项 | 状态 |
|---|---|
| SPMI 读 `AUDDEC_ANA` | ✅ trial 699/700/701 读过 48 项 |
| SPMI 写 `AUDDEC_ANA` | ✅ `configure()` 路径已实现并被 701 的初始化验证 |
| 插入识别 | ✅ trial 701 PASS |

### 5.2 缺的

| # | 缺什么 | 难度 |
|---|---|---|
| 1 | **把 45 步写进驱动** | 小（照抄） |
| 2 | **AFE 路由到 I2S 而非 TDM** | **大** |
| 3 | **MT6368 数字接口（I2S format/clock）配置** | 中 |
| 4 | 音量 / 静音 | 小 |

**第 2 条是真正的门槛**：`hakios.sound.c` 现在走 `PRI_TDM_RX_0` → AW88261（外放），
耳机需要 AFE 输出到 I2S，再进 MT6368 的 DAC。

**`grep mt6368 hakios.sound.c` = 0 命中** —— 声音驱动完全不认识 MT6368。

## 6. 建议的两步走

### 第一步：`headset=3` —— 只上电 DAC，不出声（可今晚做）

执行 45 步序列，然后回读验证。

**判据**：
| 寄存器 | 期望 |
|---|---|
| `0x2588` | `0xff` |
| `0x258a` | `0x03` |
| `0x2589` | bit0/1/3 置起 |
| PMIF 错误 | 0 |

**意义**：证明 DAC 真的上电了。这是出声的必要前提。
**风险低** —— 全是 codec 内部寄存器，不碰电源门控。

### 第二步：AFE → I2S 路由（单独一轮）

工作量大，需要改 `hakios.sound.c` 的 AFE 参数、加 MT6368 I2S slave 配置、调时钟。

## 7. 证据边界

| 层级 | 结论 |
|---|---|
| **已证明（反汇编）** | 这 45 步和 11 步是 Android 驱动在耳机事件里写的 |
| **已证明（源码）** | 这些地址在 `AUDDEC_ANA` 区，我们的读写通路已通 |
| **未证明** | 这 45 步单独执行能否让 DAC 出声（还需要数字侧数据） |
| **未证明** | 序列里的 `usleep_range` 延时值（我只提取了写，没提取延时点） |
| **未证明** | 是否有条件分支导致某些步在特定耳机类型下才执行 |
