## 2. 提取方法（可复现）

从 `hakios.mali610_fw.h` 抽出字节：

```python
import re
d = open('drivers/gpu/hakios.mali610_fw.h').read()
m = re.search(r'\{([^}]+)\}', d[d.find('kMaliFirmware'):], re.S)
data = bytes(int(x,16) for x in re.findall(r'0x([0-9a-fA-F]{2})', m.group(1)))
# -> 258048 bytes, sha256 de22d2fc... （与头文件声明一致）
```

entry 表解析按 panthor 的位域（`panthor_fw.c:96-97`）：
```c
#define CSF_FW_BINARY_ENTRY_TYPE(ehdr)  ((ehdr) & 0xff)
#define CSF_FW_BINARY_ENTRY_SIZE(ehdr)  (((ehdr) >> 8) & 0xff)   /* 注意是 >>8，不是 >>16 */
```
entry 从 offset 20 开始，type=0 的是 IFACE 段。

## 5. 🔴 最大差异：可执行段的位置和向量表

### 5.1 可执行代码段

| | 0.1（我们） | 0.3 |
|---|---|---|
| EX 段 VA | **`0x1000000-0x1010000`**（64 KB 区间，63560 B 数据） | **`0x800000-0x820000`**（128 KB 区间，82948 B 数据） |

### 5.2 VA 0 的向量表（**决定 MCU 从哪开始执行**）

| 字段 | 0.1（我们） | 0.3 |
|---|---|---|
| MSP | `0x02040000` | `0x02030000` |
| **Reset** | **`0x010018ed`** | **`0x00801fbd`** |
| NMI / HardFault / MemManage / BusFault / UsageFault | 全 `0x010019b1` | 全 `0x00802081` |

**两份各自自洽**：
- 我们的 Reset `0x010018ed`（奇数 = Thumb，真实地址 `0x010018ec`）落在 `0x1000000-0x1010000` EX 段内 ✅
- 0.3 的 Reset `0x00801fbd` 落在 `0x800000-0x820000` EX 段内 ✅

### 5.3 启动 stub 相同

| | 首 4 字（EX 段起始） |
|---|---|
| 0.1 @ `0x1000000` | `d00cf8df f832f002 47004800 01002aed` |
| 0.3 @ `0x800000` | `d00cf8df fbf4f002 47004800 00803719` |

前两条指令完全相同：`dff80cd0` = `ldr.w sp,[pc,#0xc]`，`00480047` = `bl` + `bx r0`。

**→ 同一套启动 stub，只是装载地址不同。两份固件都是完整可启动的。**

## 6. VA 0 段的内容性质完全不同

| | 0.1（我们） | 0.3 |
|---|---|---|
| VA 0 区间 | `0x0-0x1000`（**4 KB**） | `0x0-0x10000`（**64 KB**） |
| 数据量 | **2836 B** | **124 B** |
| 内容 | 向量表 32 B + 跳转表 + **config 数据 + 调试字符串** | **纯向量表 + 跳转表** |
| ASCII 字符串 | **有**（见下） | **零** |

我们 VA 0 段里的调试字符串（实测）：
```
'%s ITERATOR %d'
'CSHWIF%d register file'
'CSHWIF_JASID=0x%0x'
'ITER_FAULT_SCOREBOARD=0x%0x'
'CSHWIF_EVENT_IRQ_ENABLE=0x%0x'
'CSHWIF_EVENT_HALT_ENABLE=0x%0x'
'CSHWIF_ITER_COMPUTE=0x%0x'
'ITER_CONFIG=0x%0x'
```

而 0.3 把 config 数据移到了 `0x400000-0x420000` 那两段（124 B + 4900 B），
其中 `0x400000` 段的 124 B **与我们 VA 0 段的前 124 B 逐字节相同**。

**→ [观测] 0.3 把我们 VA 0 段的 2836 B 拆成了三段：向量表留 VA 0、其余搬到 0x400000 区。
这是架构演进，不直接说明 0.1 有错。**

## 7. 0.1 独有的 `0x2800000` 只读影子段

| 项 | 值 |
|---|---|
| VA | `0x2800000-0x2840000`（256 KB） |
| flags | `0x80000009` = ZERO \| **R** \| CACHED（**无 W**） |
| 数据 | 180752 B |
| 与 `0x2000000` 段的关系 | **数据逐字节相同**（实测 `da == db` 为 True） |

0.3 **完全没有这一段**。

**→ [观测] 这是 `0x2000000` 段的只读镜像。** 用途未查明。

## 8. ZERO 标志：我们与 panthor 行为等价

panthor（`panthor_fw.c:456-458`）：
```c
if (!section->data.size && !(section->flags & CSF_FW_BINARY_IFACE_ENTRY_ZERO))
    return;                     /* 只有「无数据」且「非 ZERO」才跳过 */
```

即：**有数据就拷；无数据但带 ZERO 就 memset 补零。**

我们的驱动 `SEC_ZERO`（`:990`）定义了但**全文件无引用**，一律「有数据就拷、无数据留空（`KMA_ZERO` 分配已是零）」。

逐段验证等价性：
| 段 | 数据 | ZERO | panthor 行为 | 我们行为 | 等价 |
|---|---|---|---|---|---|
| `0x2000000` | 180752 B | 有 | 拷数据 | 拷数据 | ✅ |
| `0x203e000` | 0 B | 有 | memset 零 | KMA_ZERO 零 | ✅ |
| `0x203f000` | 0 B | 有 | memset 零 | KMA_ZERO 零 | ✅ |
| `0x3000000` | 0 B | 无 | 跳过（不映射？） | ? | ⚠ 待查 |

**→ ZERO 处理不是问题。** 但最后一行 `PROT` 段（0 数据、无 ZERO、有 PROT）panthor 会 `return` 跳过，
我们**会映射**（`:1069-1072` 注释说 "mapped with ordinary memory"）。这是 §5.1c 那条已记录的差异。

## 9. 这些差异能不能解释「MCU_STATUS=1 但不执行」

**不能直接解释，原因如下：**

1. **0.1 自身是自洽的**：向量表、Reset 地址、EX 段位置三者对齐，启动 stub 也正确。
2. **两份固件的 EX 段大小分别是 63560 B 和 82948 B**，都在各自声明的 VA 区间内。
3. **固件版本不同不等于错**：0.1 是更老的架构，xaga 原厂在 r32p1 时代用的可能就是 0.1。

**但有三条值得单变量验证（每条都是「换掉一个变量，其他不动」）：**

| # | 假设 | 判定方式 |
|---|---|---|
| F1 | 固件 0.1 → 0.3（上游 `a27847ea`） | 换固件、其他不动，看 MCU 是否起来 |
| F2 | `0x2800000` 只读影子段可能需要 W 权限 | 改 flags 为 `0x8000000b` 试一次 |
| F3 | PROT 段映射方式 | 改成跳过（对齐 panthor），试一次 |

**三条都必须一次只动一个。** 而 F1 的前提是确认 0.3 与我们的 GPU 兼容
（同 arch10.8，但 0.3 要求的 `CSF_IFACE_VERSION` 可能更高——这一点未核实）。

### D.1 三条此前没注意的实质差异

**（1）`0x1000000` 的 EX 位不同**

| | flags | 含义 |
|---|---|---|
| 我们 | `0x0d` | RD + **EX** + CACHED（**可执行**） |
| 0.3 | `0x80000009` | ZERO + RD + CACHED（**不可执行**） |

0.3 的可执行段只有 `0x800000`（`0x0d`），我们的是 `0x1000000`。
两份各自的 Reset PC 都落在自己声明的 EX 段内，**各自自洽**。

**（2）`0x2000000` 区间宽度差 8192 B**

我们 `va 253952 B`（`0x2000000-0x203e000`）+ 两个 4 KB 零段（`0x203e000`、`0x203f000`）；
0.3 是一个 `va 262144 B`（`0x2000000-0x2040000`）。

**数学上等价**：`253952 + 4096 + 4096 = 262144`。只是 0.1 拆成三段、0.3 合并成一段。
同理 `0x3000000`：`253952 + 4096 + 4096 = 262144`。

**→ 这两处不是差异，是同一种布局的不同切分。**

**（3）`0x4000000`（shared）声明区间差近 10 倍**

| | va 区间 | 数据 |
|---|---|---|
| 我们 | `0x4000000-0x4094000`（**606208 B**） | 8192 B |
| 0.3 | `0x4000000-0x4010000`（**65536 B**） | 8192 B |

数据量相同（8192 B），但我们声明的 VA 区间大得多。**MCU 可写的共享窗口大小不同。**
这条**未验证**影响。

## F. 结论（不含推断）

1. **三份固件边界校验全部通过，无结构损坏。**
2. **三份都是完整可启动的**：向量表、Reset 指向的 EX 段、入口指令三者自洽。
3. **`0x2000000` / `0x3000000` 的区间宽度差异是切分方式不同，数学等价**（`253952+4096+4096=262144`）。
4. **唯一实质 flags 差异是 `0x1000000`**：我们 EX，0.3 不是（0.3 的 EX 在 `0x800000`）。
5. **唯一独占段是 `0x2800000`**（我们独有，只读 ZERO，数据与 `0x2000000` 逐字节相同）。
6. **`0x4000000` 共享窗口**：我们声明 606208 B、0.3 声明 65536 B，数据量都是 8192 B。
7. **PROT 段数**：我们 3 条、0.3 1 条。当前三者都映射普通页。

**以上都不能单独解释「MCU_STATUS=1 但不执行」。** 唯一能立判定的是单变量实验。

### F.1 我先前一条说法搞错了：type=1 不是 IFACE 版本

我原先写「需解析 type=1 CONFIG 段确认 `CSF_IFACE_VERSION` 兼容性」。**这是错的。**

实测 type=1 的内容是**运行时可变配置项**，不是版本号：

| | type=1 条目 |
|---|---|
| 我们 | `Compute iterator suspend`、`Fragment iterator suspend`、`Tiler iterator suspend`、`Log verbosity` |
| 0.3 | `Log verbosity`、`WA_CFG0`（值 `0xffffffff`） |

`CSF_IFACE_VERSION` 实际在**共享内存的 global control 区**（`version` 字段），
由固件在启动后写入 —— **要等 MCU 真的跑起来才能读，离线阶段根本无法判定。**

→ 所以「0.3 与我们是否兼容」这条**在换固件之前无法离线确认**，只能靠实测。
这是一个真实的前置风险，不是可以预先排除的项。
