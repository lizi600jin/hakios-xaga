# 重大发现：可能是 19 轮 GPU 困境的答案

> 时间：2026-11-14 22:15
> 来源：子代理联网调研 + 主控独立核实（两处调用点都抓了原始文件确认）

---

## 0. 一句话

**在 MT6895 上，GPU 的电源由 GPUEB（独立的协处理器）拥有。panthor 在写 `MCU_CONTROL=AUTO` 之前必须先向 GPUEB 发 IPI 请求上电。我们没有做这一步。**

这直接对应我们的症状：MCU 收到 AUTO 后一条指令都不执行、哨兵 `0xff5aa5f0` 从未被改写。

### 1.3 dtsi 的佐证（`raw/mt6895.dtsi`，我已下载到本地）

**GPU 节点没有 `power-domains`**，注释原文（`:2744-2745`）：

> Real power management stays with gpueb; **no power-domains**.

**那句直接点名我们症状的注释**（`:2726-2731`）：

> The MT6895 GPU MTCMOS is split into MFG1..MFG12. Downstream attaches all twelve domains to the GPU node and powers them through PM runtime; the PDCv2 registers then let the GPU control the finer shader/stack domains. **Without MFG2-12 the shader cores never become ready (shader_ready stays 0) and the MCU firmware hangs before writing the shared interface version.**

**GPUEB 节点**（`:2650`）：

```dts
gpueb: gpueb@13c40000 {
    compatible = "mediatek,gpueb";
    reg = <0x13c40000 0x22000>, <0x13c5fd80 0x280>,
          <0x13c62004 0x4>, <0x13c62074 0x4>,
          <0x13c62000 0x4>, <0x13c62078 0x4>;
    interrupts = <GIC_SPI 516 IRQ_TYPE_LEVEL_HIGH 0>;
    gpueb_mem_table = <0 0x1000>,      /* MEM_ID_GPUFREQ, 4KB */
                      <1 0x180000>;    /* MEM_ID_LOG, 1.5MB */
```

IPI 通道 8 个：`FAST_DVFS_EVENT / GPUFREQ / SLEEP / TIMER / FHCTL / CCF / GPUMPU / FAST_DVFS`

## 3. 这为什么能解释「MCU 不执行」

我们的 symptom 清单：
- `JOB_INT_STATUS(0x100c)` bit31 从不升起
- 哨兵 `0xff5aa5f0` 原样读回
- `MCU_STATUS` 恒 1，写 DISABLE 也不动
- `AS_FAULTSTATUS` 恒 0（没有 fault）
- `debug_top` 从 idle 变 busy 且不回落

**一个自洽的解释**：MCU 所在的电源域（或它依赖的某个 rail/时钟）没有被真正放行。
我们能读能写 GPU 寄存器（因为 GPU 主寄存器块所在的域是开的），
但 MCU 核本身没上电 → 写进去的 `AUTO` 命令躺在那里，核不执行。

这同时解释了为什么：
- 没有 fault（`AS_FAULTSTATUS = 0`）—— 没执行就不会有 fault
- 哨兵不变 —— 固件第一条指令都跑不到
- **35 条已排除的尝试全部失败** —— 它们都在 AP 侧调 GPU/SPM/时钟，而电源的真正的 owner 是 GPUEB

### 与 dtsi 注释的关系

dtsi 那句说的是 **MFG2-12**（shader core 域），它导致 `shader_ready = 0`，进而「MCU firmware hangs before writing the shared interface version」。

而我们的项目记录里把「MFG7..12 未上电是 PDCv2 设计」当成已否掉的结论。
**这条与 dtsi 注释冲突**，需要重新审视。

两条路径可能都对、也可能是同一条：GPUEB 上电时会自己把 MFG1-12 按正确顺序拉起，
我们手工只开 MFG1、MFG2（`MFG_0_1_PWR_MASK=0x6`）**正是"绕过 GPUEB 手工控制"**，
而 dtsi 明说「direct DT clock/power-domain control conflicts with the EB and can hang shader jobs」。

## 4. 建议的验证方案（单变量，一次刷机）

**不要一次做全套。按下面顺序，每步单独验证。**

### 第 1 步：先确认 GPUEB 还活着

我们的 `gpueb_watch()` 已经能做这件事。先跑一次，确认：
- `WDT_KICK` 在变（说明 GPUEB 固件在跑）
- 还是死值（说明 LK 已经把 GPUEB 停了）

**这一步决定后续所有方案。**
- 如果 GPUEB 活着 → 走第 2 步（IPI 握手）
- 如果 GPUEB 死了 → 要么在 loader 里把它重新拉起来，要么必须自己全权控制电源

### 第 2 步：打开 GPUEB 的时钟门

我们的注释说「GPUEB 在自己的时钟门后面，不去开这个门读它会挂死板子（`mali_gpueb=1` 才映射）」。

所以要先找到并打开那个门，才能访问 `0x13c40000`。

**这条要查**：时钟门在哪（topckgen？infracfg？）哪个 bit？

### 第 3 步：发 IPI

按 `mt6895_gpueb.h` 的 API，需要：
1. `CMD_INIT_SHARED_MEM` —— 把 `MEM_ID_GPUFREQ` 保留区的 phys 地址/大小告诉 EB
2. `CMD_POWER_CONTROL(POWER_ON)`

**共享内存地址要从 dtsi 的 `reserved-memory` 里找 `MEM_ID_GPUFREQ`**（子代理在查）。
