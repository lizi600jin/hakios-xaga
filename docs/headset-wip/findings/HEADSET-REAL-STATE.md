# 耳机线真实状态诊断（2026-11-15 15:10）

> DSH。**离线分析 + 四次真机日志交叉核对**，未新增设备操作。
> 本文档回答一个具体问题：**耳机驱动到底跑到哪一步了。**

---

## 0. 一句话

**`headset=1` 传进去了，但这四次真机运行里，耳机驱动一条输出都没有 —— 而
`keys` 驱动的轮询循环却在正常工作。**

**所以不是「耳机还没实现」，是「代码路径在某处静默返回了」。**

---

## 1. 先排除三种「不是原因」的可能

### 1.1 不是日志被截断

我原以为日志只从 28 秒开始、早期输出被环形缓冲覆盖。**这个判断是错的。**

实际日志结构（trial 698，475725 B）：

| 段 | 字节 | 内容 |
|---|---|---|
| 无时间戳头 | 344718 | loader 自己的控制台输出（内核启动早期） |
| `--- kernel message buffer ---` | — | loader 打印的分隔符 |
| 带时间戳段 | 131007 | 内核 msgbuf |

**全文没有 `was dropped` 标记**（`loader_return.c:162` 那条截断提示），
说明 `loader_log[1536 KB]` **没有环绕**，**日志是完整的**。

（`LOADER_LOG_HEAD = 256 KB`、`LOADER_LOG_RING = 1 MB`：只有超过 1536 KB 才会丢弃中间段。
475 KB 远未触及。）

### 1.2 不是内核没编进去

| 检查 | 结果 |
|---|---|
| 内核里 `headset: mode %u on SID 5` 字符串 | **1 处** |
| 内核里 `took a baseline` | **1 处** |
| 内核里 `polling every` | **2 处** |
| 刷进设备的内核（从 payload 里解出来）| `a5719c5a…` == 刚编译的那个 |

**而且 698 新加的 L2 探针确实输出了**（`l2 pre_t/r/t 0/0/0 post_t/r/t 0/0/0`），
**证明这个新内核在跑。**

### 1.3 不是编译宏没开

| 项 | 值 |
|---|---|
| `.config:39` | `CONFIG_HAKIOS_MT6895_HEADSET=y` |
| 编译命令里 | `-DHAKIOS_MT6895_HEADSET` 在 `CONFIG_DEFINES` 中 |
| `stubs.c:71-76` 的空实现 | 被 `#ifndef HAKIOS_MT6895_HEADSET` 守卫，**不会生效** |

**所以真实驱动是编进去的，空桩没启用。**

## 2. 真正的问题：初始化段零输出，但循环在跑

### 2.1 应有的输出 vs 实际

`keys_thread`（`hakios.mt6895_keys.c:346`）在进入轮询循环（`:461`）**之前**，
按代码顺序应该打印这些：

| 源码位置 | 应该打印 | 四次日志里实际 |
|---|---|---|
| `:369` `pmif_init` 失败时 | `the arbiter ... will not map` | **0** |
| `:373` `pmic_scan("boot")` | **`took a baseline of 0x1e..0x2a`**（无条件打印） | **0** |
| `:377` PMIC key register 成功 | `the PMIC's key register ... reads ...` | **0** |
| `:397` 同上的 else 分支 | `the arbiter did not answer ...` | **0** |
| `:411` | `SWINF_2 sta ... ` | **0** |
| **`:420`** | **`hakios_mt6895_headset_init()` 调用** | — |
| `:481`（headset） | **`headset: mode 1 on SID 5 ...`** | **0** |
| `:433` | `the keypad ... is not a block that is running` | **0** |
| `:451` 或 `:458` | `the keypad reads ... every 20 ms`（**带 `every N ms` 后缀那条**） | **0** —— 注意日志里 14 条 `the keypad reads` 全部来自 `:564` 的循环内版本，不是这两条 |
| `:459` | **`polling every 20 ms; PMIC bit ...`** | **0** |
| **`:564`（循环内）** | `0 changes so far; the keypad reads ...` | **✅ 14 条** |

### 2.2 时间戳把矛盾钉死了

轮询每 10.4 秒一次（`tick % (10000/poll_ms)`，`poll_ms=20` → 500 tick）：

```
[   30.850933]   ← 第一次
[   41.219047]
[   51.645895]
...
[  166.285156]   ← 第 14 次
```

**第一次 30.85 秒，而日志从 24.18 秒开始。**
初始化打印本该发生在**刚进循环之前**（约 30.8 秒），**完全落在日志范围内**。

**所以它们不是被日志吞了，是真的没打印。**

### 2.3 唯一的静默返回点

`hakios_mt6895_headset_init()`（`hakios.mt6895_headset.c:464-481`）里，
`:481` 之前只有**一处**不打印就返回：

```c
if (!PE_parse_boot_argn("headset", &mode, sizeof(mode)) || mode == 0) {
    return;                      /* <- 静默 */
}
```

其余失败都会打印（`unsupported mode` / `cannot map PMIF`）。

**boot-args 里明明有 `headset=1`，但这里却像是解析失败。**

> 但这条**不能单独定案**：`keys_thread` 自身的初始化（`pmic_scan` 的 baseline 打印）
> 也没有出现，而那与 `headset` 参数无关。**所以问题可能在更前面。**

## 4. 这对今晚插耳机的实验意味着什么

**`headset=1`（纯只读）现在拿不到任何数据。**
`headset=2`（含初始化）也拿不到，因为同样卡在静默返回。

**今晚要能用上实体耳机，必须先修这个「初始化段无输出」的问题。**
这不是加功能，是让已有代码的输出现形。

### 建议的最小诊断改动（未实施）

在 `keys_thread` 开头加**一条无条件打印**，证明函数真的从那里开始执行：

```c
printf("mt6895-keys: thread entered\n");
```

以及 `headset_init` 的入口加一条，区分两种静默：

```c
if (!PE_parse_boot_argn("headset", &mode, sizeof(mode))) {
    printf("headset: no headset= boot-arg\n");   /* 参数没解析到 */
    return;
}
if (mode == 0) {
    printf("headset: headset=0, disabled\n");    /* 参数是 0 */
    return;
}
```

**三条打印，零风险，能把「代码没跑到」和「参数没解析」彻底分开。**

## 6. 🔴 第 6 节作废：6.1-Sol 指出两个真实漏洞，我原来错了

> 2026-11-15 15:20。**这一节推翻我在 §1.1 和 §6 里的核心结论。**

### 6.1 我的错误：把「导出长度一致」当成「内容完整」

我原来的论证：

> 「内核屏幕报告 475725 = 提取文件 475725 = header len 475725，三者一致，
> 所以从内核到 flash 零丢失，日志完整。」

**这只证明了「导出过程没有丢字节」，没有证明「内核记录的历史完整」。**

6.1-Sol 给出的真实拆分（我复算了，**完全正确**）：

```
344623（loader 控制台段）
+     30（分隔符 "--- kernel message buffer ---"）
+ 131072（内核 msgbuf 段）
= 475725
```

**内核段恰好 131072 字节 = 128 KiB = `CONFIG_MSG_BSIZE_DEV`。**
**缓冲区是满的。**

`subr_log.c:570` 原文：

```c
mbp->msg_bufc[mbp->msg_bufx++] = c;
if (mbp->msg_bufx >= mbp->msg_size) {
    mbp->msg_bufx = 0;          /* ← 写满就归零覆盖 */
}
```

**msgbuf 是 128 KiB 环形缓冲，满了直接从头覆盖。**
`loader_return.c:344` 只复制当前缓冲区内容。

### 6.2 决定性证据：内核段从半行开始

日志第 2700 行（内核段第一行）：

```
g7  ST0T0 no ack after 2000000 reads (0x111e), continuing anyway
```

**行首是 `g7`，而原文应该是 `mali: mfg7`。** 前面被切掉了。

**这就是回卷的物证：早期内容已经被覆盖。**

### 6.3 第二个错误：30.85 秒不是初始化时刻

我原来推理：

> 「轮询第一次输出在 30.85 秒，说明刚进循环，初始化打印就在那之前，落在日志范围内。」

**错。** `:564` 的心跳是 `tick % (10000 / poll_ms) == 0` 才打印，
`poll_ms = 20` → 每 **500 轮**（约 10 秒）才打一次。

**第一次心跳在 30.85 秒，说明循环可能在 20 秒甚至更早就开始了。**
而内核段起点是 **24.18 秒** —— **初始化完全可能发生在 24 秒之前，被覆盖了。**

### 6.4 所以正确的结论是什么

| 我之前说的 | 正确的是 |
|---|---|
| `:346-460` 整段没执行 | **不能这么推**。它可能执行了，输出落在被覆盖的早期历史里 |
| 日志完整 | **导出完整，但内核只保留了最近 128 KiB** |
| 三个长度一致 = 内容完整 | 只证明导出没丢字节 |

**`pmif_init` 两条分支都没打印这件事，现在的解释是「发生在 24 秒之前」，
不是「代码没跑」。**

### 6.5 那么还剩什么可说的

**能说的**：
- 内核输出只保留最近 128 KiB（约 24 秒起），**更早的必然丢失**
- `headset` 与 `keys` 的初始化输出**不在这 128 KiB 里**
- 单纯加三条 `printf` **可能仍然被覆盖**（6.1-Sol 的提醒，成立）

**不能说的**：
- 代码没执行
- 参数没解析
- 存在某个静默返回点

### 6.6 真正该先解决的是什么

**「让早期输出活下来」比「加打印」更根本。**

6.1-Sol 的原话：「建议先解决早期日志保留，再安排实机。单加这三条 printf 仍可能再次全部被覆盖。」

**这条我接受。** 加打印解决不了覆盖问题。
