## 第一条：DSH 说「6 条寄存器写就能让耳机响」

**Codex 原文**：6 条只是 SGEN 配置；其第 0 节写完整通路 **71 笔**且含未验证 SID 9 时钟；第 7 节明确先做 SDM 和 HP 上电才接 SGEN。

**核实结果：Codex 正确。**

| 出处 | 原文 |
|---|---|
| `AUDIO-PATH-MINIMAL.md:11` | 「路径 (a) 共 **70 笔写**（69 笔 SID 5 + 1 笔 SID 9）」 |
| 同文件 `:410` | 「本文件全部 **75 笔** SPMI 事务」 |
| 同文件 `:7` | 「机器可读版本 `audio-path-table.json`（**92 条**）」 |
| 同文件 `:435`（步骤 4） | 「SDM 链（§4.1 的 10 条）… **不做这步后面写什么都不会响**」 |
| 同文件 `:440`（步骤 5） | 「SGEN 参数（§5.1 前 4 条，**不含** `0x238e`）… **此时无声音**」 |
| 同文件 `:443`（步骤 6） | 「HP 上电（§4.2 的 3 条 + §4.3 的 **35 条**）**一步都不能省**（尤其 CON2 的 `0x0c→0x3c→0xfc→0xff→0xcf→0xc3→0x03` **七次写**）」 |
| 同文件 `:452`（步骤 7） | 「**最后一笔**：`0x238e bit0 = 1`」 |

**DSH 的错误**：把 §5.1 表格里 SGEN 那 6 条（`0x238e`/`0x23c8`/`0x23c9`/`0x23ca` + 两个 widget）当成了整条通路。

**数字对齐**（三处说法不同不是矛盾，是口径不同）：
- **70 笔**：路径 (a) 的写笔数（§0）
- **75 笔**：含路径 (a) 的读基线等全部 SPMI 事务（§7）
- **92 条**：JSON 表里的条目（含层 5 的判据等非 SPMI 项）

## 第二条：DSH 暗示「改绝对地址就解决了 GPUEB 门控问题」

**Codex 原文**：GPUEB 第 13 节改绝对地址也不证明门控安全，引用 mailbox 启动仍有 `clk_enable`。

**核实结果：Codex 正确，且 DSH 从未声称门控安全 —— 但 DSH 的表述让 Codex 合理怀疑。**

`GPUEB-IPI-PROTOCOL.md:1160-1173` §13 十步清单里**没有任何一句**说门控安全。相反：
- `:1167` 步骤 4：「**不要** map `0x13c40000`」
- `gpueb-ipi.h:56` 注释：「⚠ `0x13c40000` (gpueb_base) **严禁触碰** —— 门控未确认」

**但 Codex 指出的技术点成立**：即使把 `MALI_GPUEB_MBOX_RECV 0x22078` 改成绝对地址 `0x13c62078`，**只解决了「不碰禁区」这个约束问题，没有解决「GPUEB 时钟是否已使能」这个功能问题**。panthor 在调用 mailbox 前有 `clk_enable`（MT6895 mainline GPUEB 驱动），而我们的裸机没有对应步骤。

→ **这构成 GPUEB 路线的第三个未验证前提**（前两个是：GPUEB 固件是否在跑、共享内存是否可用）。

## 第三条：DSH 未指出 `gpueb-ipi.h` 的屏障/延时默认值不可用

**Codex 原文**：草稿默认屏障和延时也需替换后才能集成。

**核实结果：Codex 正确。**

`findings/gpueb-ipi.h:34-44`：

```c
/* 内存屏障。写 SRAM 之后、写 IRQ_SET 之前必须有。 */
#ifndef GPUEB_BARRIER
#  define GPUEB_BARRIER()   __asm__ __volatile__("" ::: "memory")
#endif

/* 微秒延时。轮询间隔 10 µs */
#ifndef GPUEB_UDELAY
#  define GPUEB_UDELAY(us)  do { (void)(us); } while (0)
#endif
```

两个默认值的问题：

| 宏 | 默认值 | 问题 |
|---|---|---|
| `GPUEB_BARRIER` | `__asm__ __volatile__("" ::: "memory")` | **只是编译器屏障，不是硬件屏障**。缺 `dsb sy`。而头文件自己的注释写「写 SRAM 之后、写 IRQ_SET 之前必须有」——默认值做不到这件事 |
| `GPUEB_UDELAY` | `do { (void)(us); } while (0)` | **空操作**。超时轮询会退化成零延时忙等，最坏 10 s × 全速自旋 |

**DSH 之前只验证了「编译零警告」和「sim 4/4 全过」，没有验证默认宏的语义正确性。** 这是我的验收漏洞。

## 裁定

1. **DSH 全部接受 Codex 的三条反对。**
2. **两项暂不加入首轮 124 项只读实验** —— 同意。首轮实验的唯一目的是「验证 ACCDET 能不能读到插入」，塞进 70 笔音频写会让失败无法归因。
3. **集成 `gpueb-ipi.h` 前的强制前置**：必须替换 `GPUEB_BARRIER` 为 `dsb sy`、`GPUEB_UDELAY` 为真实 `delay_us()`，且这两个替换要写进集成清单。
4. **音频通路的正确表述**（此后所有文档统一用这个）：

> 耳机出声需要 **70 笔 SPMI 写**，分 5 层：层2 上电 16 条 → SDM 链 10 条 → SGEN 参数 4 条 → HP 上电 38 条 → 最后 `0x238e` bit0 接入。
> 其中 1 笔是 MT6685（SID 9）的 DCXO 缓冲，**未验证**。

## DSH 的验收方法缺陷（自我修正）

这次错误暴露一个系统性问题：**我把「子代理报告里的某个表格」当成了「该报告的结论」**，跳过了报告的 §0 总述和 §7 操作手册。

修改后的验收规则（写进 `COLLAB-PROTOCOL.md`）：
- 引用子代理报告时，**必须读该报告的「一句话结论」节和「操作手册 / 步骤」节**，不能只读中间某张表
- 任何「只需要 N 步就能 X」的表述，必须核对 N 是否等于报告总述里的总数
- 转述给 Codex 前，**自己先回答「这个数字是不是全量」**
