## 1. 撤回一：那 7 对不是镜像寄存器

### 我原来写的

```python
MIRROR_PAIRS = [
    (0x2697, 0x2699), (0x2699, 0x269B), (0x26A3, 0x26A4),
    (0x26C4, 0x26C6), (0x26C6, 0x26C8), (0x26C8, 0x26CA),
    (0x26C5, 0x26C7),
]
```

我以为这些地址「接的是同一块存储，正确读取必须返回同一个字节」。

### 实际不是

`raw/mt6368.h:448-458`：

```c
#define MT6368_ACCDET_CON13   0x2695
#define MT6368_ACCDET_CON14   0x2696
#define MT6368_ACCDET_CON15   0x2697     <- 我当成「镜像之一」
#define MT6368_ACCDET_CON16   0x2698
#define MT6368_ACCDET_CON17   0x2699     <- 同一个「镜像对」的另一半
#define MT6368_ACCDET_CON18   0x269a
#define MT6368_ACCDET_CON19   0x269b
...
```

**`CON13`..`CON23` 是连续编号的独立配置字段，两字节一个。**
`0x2697`（CON15）和 `0x2699`（CON17）**中间隔着 `0x2698`（CON16）**，是两个不同的
debounce 字段。

**它们之所以读到相同值（`0x10`/`0x10`），只是因为初始化恰好把两者设成了同一个值。**

**所以「7 对全等」不是「读得对」的证据。** 这条撤回。

> 6-Astra 的原话：「这些是可独立配置的值，不是硬件镜像地址。」

## 2. 撤回二：`0x231d` 的 `0x06` 不是自检值，是 IRQ 申请的产物

### 我原来的推断（也是错的）

我在 `ANCHOR-231D-EXPLAINED.md` 里写：

> `0x00` = 芯片被复位过；`0xFF` = 通道坏了；所以 `0x00` 说明通道通但芯片被复位。

**这个「复位历史」的解释是错的。**

### 实际来源

6-Astra 找到了设置者：**MFD 的 IRQ 层**。

`mtk-spmi-pmic.c` 的 `mtk_spmi_pmic_irq_sync_unlock()`：

```c
for (i = 0; i < chip_data->num_pmic_irqs; i++) {
    ...
    regmap_update_bits(core->regmap, en_reg, BIT(shift),
                       core->enable_hwirq[i] << shift);
```

**每申请一个 IRQ，就把对应的使能位置 1。**
`0x231d` 的 `0x06` = **bit1（ACCDET）+ bit2（EINT0）都被申请了**。

**所以 `0x06` 是「两路中断已使能」，不是芯片 ID、不是自检结果、不是复位历史锁存。**

### 连带撤回

| 我说的 | 实际 |
|---|---|
| `0x231d == 0x06` 才基线可比 | **轮询模式下不需要它** |
| `0x231d == 0x00` 表示芯片被复位过 | **只表示顶层中断没使能** |
| `0x231d != 0xFF` 就说明通道正常 | **错误**。`0xFF` 不是唯一的失效签名 |

**这条也撤回。** 我在 `ANCHOR-231D-EXPLAINED.md` 里把 `!=0xFF` 当成通道判据，
6-Astra 明确否了：「`0x00` 不能推复位，`!=0xff` 也不能当通道通过。」

## 4. 6-Astra 另外三条纠正（也都成立）

### 4.1 初始化不是「完全不可观察」

我写「mode 2 那 30 次寄存器写的效果完全看不到」。**不准确。**

`hakios.mt6895_headset.c:130-171` 的 `update_bits()` **每笔写后都会读回校验**
（检查 `(got & mask) == bits`）。所以：

- 准确的说法是「**整段初始化结束后的配置保持情况**看不到」，不是「写效果看不到」；
- 另外**实际写次数不是固定 30 次** —— `value == old` 时会跳过写，只做读回检查；
- 展开 `write16()` 后一共 **41 次配置操作，覆盖 34 个不同字节**，含重复写和脉冲两阶段。

### 4.2 现有 dump 的时序成本是实测的

| 区段 | 条数 | 首末时间差 |
|---|---|---|
| 全部 | 129 | **120.029 ms** |
| ACCDET | 76 | 34.772 ms |
| 模拟 | 48 | 9.767 ms |

**这些含打印与调度开销，不是纯 SPMI 总线时间。** 新增 dump 会**延后 keys/headset 服务**。

### 4.3 `dump_block(0x2688,0x26d3)` 是 76 字节，不是 129

它**不包含模拟配置**。而且即便重做原 129 项，**也会漏掉已配置的 `0x2319` 和 `0x248c`**。

## 5. 结论：不为 post-init dump 单独刷机

**6-Astra 的建议我采纳：先等耳机做 701。**

理由：
1. 701（插耳机跑 `mode 2`，看 `cur_AB` 变不变）**才是真正的判据**；
2. post-init dump 只回答「初始化改了什么」这个**次要问题**；
3. 现有 `update_bits()` 已有逐笔读回校验，缺口比我原来描述的小；
4. 若 701 没进入正确状态或失败，**再根据日志决定是否加受限快照**。

**受限快照方案**（若将来要做）：读初始化涉及的 **34 个配置字节**，
按目标 mask 比较，附供电/时钟/EINT 状态；**动态状态不与静态配置做全字节等值**。
采样点必须在 `accdet_init_once()` 成功后、**首次 `poll_sample()` 之前**
（现在 `mode 2 initialised` 打印前已经跑过一次 `poll_sample()`）。
