# 共享区对账：692 读到的每个值都是镜像初值（2026-11-14 01:10）

**手机零访问。** 这一份做的是 6.1sol 建议的那件事：把固件既有共享区写入与 692 日志逐条对账。

---

## 1. 结论先说

**692 读到的 GLB 与 CSG0 全部字段，除了我们自己写的哨兵，其余每一个都与固件镜像的初值完全一致。**

| 字段 | 映像初值 | 692 读数 | 判定 |
|---|---|---|---|
| GLB version `@0x4000000` | `0x00000000` | `0xff5aa5f0` | 我们写的哨兵 |
| GLB features `@0x4000004` | `0x0` | `0x0` | 同初值 |
| GLB input_va `@0x4000008` | `0x04002000` | `0x4002000` | 同初值 |
| GLB output_va `@0x400000c` | `0x04003000` | `0x4003000` | 同初值 |
| GLB group_num `@0x4000010` | `0x8` | `0x8` | 同初值 |
| GLB group_stride `@0x4000014` | `0xa0` | `0xa0` | 同初值 |
| GLB perfcnt_size `@0x4000018` | `0x0` | `0x0` | 同初值 |
| GLB instr_features `@0x400001c` | `0x71` | `0x71` | 同初值 |
| CSG0 features `@0x4001000` | `0x0` | `0x0` | 同初值 |
| CSG0 input_va `@0x4001004` | `0x04004000` | `0x4004000` | 同初值 |
| CSG0 output_va `@0x4001008` | `0x0400c000` | `0x400c000` | 同初值 |
| CSG0 suspend `@0x400100c` | `0x0` | `0x0` | 同初值 |

→ **没有一条是固件写进去的。** 这坐实了 §1 的读法：`0x1002fd6` / `0x1003012` 那几条共享区写入
**一次都没有发生**。

---

## 2. 这条为什么比"版本字没变"更强

版本字只有**一个**观测点。而这里是 **15 个字段**，覆盖 GLB 和 CSG0 两个控制块，
每一个都是固件在 `0x1002ff2` / `0x1002ff8` 那两段（8 组 × 8 个 `0xc` 步长）里会改写的位置。

**15 个字段全部等于初值**，说明那段"填 CSG/stream 元数据"的循环一轮都没跑。

不过要小心 —— **它们会不会本来就不该变？** 见 §3。

---

## 3. 一个必须排除的替代解释

固件在 `0x1002ff8` 写的是 `str r1,[r2,r6]`，其中 `r1` 在 `0x1002fe6` 被算成
`orr r1,r1,#0x70000` 之类的东西。**如果它算出来的值恰好等于初值，那"没变"就不能证明"没执行"。**

要排除这一点，需要知道 `r1` 在运行时的值。它在 `0x1002fd8..0x1002fe6` 由 `sl` 和 `sb` 算出，
而 `sl`/`sb` 又是从 GPU 硬件寄存器读来的（`0x1002b9a` 附近）。

→ **我无法静态确定 `r1` 的数值。** 所以：
- **能确定的**：这 15 个字段现在等于初值。
- **不能确定的**：固件如果执行过那段循环，写进去的值是否恰好也等于初值。

→ 这条观测**削弱但不排除**"固件执行过 `0x1002ff2`"这个可能。

## 4. 一处我自己差点写错的地方（记下来）

我在核对时一度认为驱动读 CSG0 用错了偏移（`kva + 0x1000`），理由是"`0x4001000` 看起来像
glb_input 块"。**这是错的**：

`panthor_panthor_fw.c:215` 明确写着

```c
#define CSF_GROUP_CONTROL_OFFSET  0x1000
```

而 `panthor_init_csg_iface()`（`:954-957`）：

```c
u64 iface_offset = CSF_GROUP_CONTROL_OFFSET +
                   ((u64)csg_idx * glb_iface->control->group_stride);
```

→ `csg_idx = 0` 时就是 `0x1000`。**驱动的 `+0x1000` 完全正确。**
而 `0x4001000` 的内容按 `struct csg_control` 解出来，与 692 打印的 7 个字段**逐字段吻合**。

我差一点就凭空造出一条"驱动有 bug"的结论。这次是查了 panthor 才拦住的。

## 5. 下一步能做什么（不需要刷机）

要排除 §3 那个替代解释，最直接的办法是**在驱动里打印 `r1` 的预期值** ——
但那需要运行固件，也就是刷机。

**不刷机能做的**：
1. 把 `0x1002fd8..0x1002fe6` 那段的 `sl` / `sb` 来源追到底（从哪个 GPU 寄存器来），
   如果能确定它们的取值范围，就能判断 `r1` 是否可能恰好等于初值。
2. 检查 CSG1..CSG7 的 7 个块（`0x40010a0`、`0x4001140`…）是否也都是初值 ——
   如果固件跑过循环，8 组会被一起写。**这一条我还没做。**

第 2 条是纯粹的多读几个字，如果能确认 8 组全是初值，"循环一次都没跑"的强度会再上一档。

## 6. 致命补充（01:20）：这个方法本身失效了

我做完 §1 的 15 字段对账后，去做 §5 说的"多读几个字"。结果发现一个更根本的问题：

**固件镜像里已经预先填好了固件本来要写的那些值。**

`CSG0` 控制块（`0x4001000`）的完整非零字：

```
+0x1004 = 0x04004000   input_va
+0x1008 = 0x0400c000   output_va
+0x1014 = 0x00000008   stream_num
+0x1018 = 0x0000000c   stream_stride
+0x1044 = 0x04014000    stream0 in         +0x1048 = 0x04054000    stream0 out
+0x1050 = 0x04015000    stream1 in         +0x1054 = 0x04055000    stream1 out
...（8 个 stream，每个 0xc 步长，全部预先填好）
```

而固件在 `0x1002ff2` / `0x1002ff8` 那段循环里要写的，**正是这些位置、正是这种值**。

### 这意味着什么

| 观测 | 能推出什么 |
|---|---|
| 字段等于初值 | **不能推出**"固件没执行" |
| 因为初值本身就已经是"正确结果" | 固件执行了也是这个值 |

→ **§1 的 15 字段对账，作为"固件没跑到那里"的证据，是无效的。**

我之前把它写成"坐实了那几条共享区写入一次都没有发生"—— **这句话要撤回。**

### 唯一还有区分度的，是我们改过的字

| 字 | 为什么还有效 |
|---|---|
| `GLB version @0x4000000` | 我们写了哨兵 `0xff5aa5f0`，映像初值是 `0x0`，固件要写 `0x01010000`。**三个值互不相同**，所以"还是哨兵"确实说明固件没写它。 |

**只有这一个字。** 其余 14 个都是"映像初值 = 固件要写的值"，没有区分度。

## 7. 那 Kbase 为什么还要运行期填这些字段？

因为 **kbase 用的固件不是我们这一个 build**。

icecream95 的 RK3588 dump（`PUBLIC-REF-CROSSCHECK` §2）显示：RK3588 的 `.shared` 段
**在镜像里是零长度数据**（`data 0x2c8-0x2c8`），所有字段全靠 kbase 运行期
`kbase_csf_update_firmware_memory()` 填。

**我们的镜像有 8192 字节预置内容** —— 是另一种 build 形态，或者说被预填过。

→ 这解释了为什么 kbase 要写：它面对的是空 shared 段。
→ 也解释了为什么我们的对账无效：我们的镜像把这些值写死在文件里了。

## 9. 修正 §8：其实有 **两个** 有效判据，不是一个（01:35）

§8 我说"只有 version 一个字有区分度"。**这句话漏了第二个。**

### `0x4000018`（glb_control.perfcnt_size）也是有效判据

它的映像初值是 **0**，而固件在 `0x1002fd6` 写的值是这样算出来的：

```
0x1002f96  ldr.w r0,[r8]          ; r0 = *r8
0x1002f9a  ldr.w r1,[r8,#0xf4]
0x1002f9e  ldr.w r2,[r8,#0xf0]
0x1002faa  clz   r3,r2
0x1002fae  cmp   r1,#0
0x1002fb0  add.w r3,r3,#0x20
0x1002fb6  clzne r3,r1            ; r3 = clz(r1) 或 clz(r2)+32
0x1002fba  ubfx  r0,r0,#8,#4      ; r0 = (*r8) 的 bits 11:8
0x1002fc0  rsb.w r3,r3,#0x40      ; r3 = 64 - r3
0x1002fc6  addne r0,r3            ; r0 += r3
0x1002fca  adds  r0,#3
0x1002fcc  uxth  r1,r0
0x1002fd6  str   r1,[0x4000018]
```

`r8` 来自 `0x10017d4  ldr.w r8,[sl,#0x14]`，是**从 GPU 硬件寄存器表算出来的**，
几乎不可能恰好等于 0。

而 **692 恰好读过这个字**：

```
mali: shared probe GLB: groups 8 stride 0xa0 perfcnt 0 instr 0x71
                                              ^^^^^^^^^
```

`perfcnt` 就是 `glb_control+0x18` = `0x4000018`，读到 **0**。

→ **固件没写这个字。** 而它的初值是 0、固件会写非零值，所以这是**有效判据**。

### 现在有两个有效判据

| 字 | 映像初值 | 我们/固件 | 692 读数 | 判定 |
|---|---|---|---|---|
| `0x4000000` version | `0x0` | 我方哨兵 `0xff5aa5f0`，固件 `0x01010000` | `0xff5aa5f0` | 固件没写 |
| `0x4000018` perfcnt_size | `0x0` | 固件写 `f(GPU regs)`，几乎必非零 | **`0`** | **固件没写** |

两者互相独立（一个是我们改过的，一个是完全原装的），结论一致。

### 但仍然不能推出"没执行"

见 `FINDING-version-word-path-2026-11-13.md` §9：store 可能在 AS0 翻译或总线上失败。
**"没观测到写" ≠ "没执行到写"。**

不过现在有**两个独立观测点**同时指向同一结论，比只有一个强。

## 10. 定稿（01:50，接受 6.1sol 的三处修正）

它三条都对，逐条核实：

### 10.1 perfcnt 的区分度是**严格**的，不是"几乎必非零"

我写"几乎不可能恰好等于 0"，它给了精确算式：

```
0x1002fba  ubfx r0,r0,#8,#4      ; r0 = (*r8 >> 8) & 15      范围 0..15
0x1002faa  clz  r3,r2            ; low word
0x1002fb0  add.w r3,r3,#0x20
0x1002fb6  clzne r3,r1           ; high word
0x1002fc0  rsb.w r3,r3,#0x40     ; r3 = 64 - clz(...)
0x1002fc6  addne r0,r3           ; 仅当 hi != 0 才加
0x1002fca  adds r0,#3            ; ★ 恒 +3
0x1002fcc  uxth r1,r0
```

- `hi != 0`：`r3 = 64 - clz(hi) = 32 + bit_length(hi)` → `3 + ((u>>8)&15) + 33..64` = **36..82**
- `hi == 0, lo != 0`：`r3 = 64 - (clz(lo)+32) = bit_length(lo)` → **4..50**
- `hi == 0, lo == 0`：`addne` 不执行 → **3..18**

→ **整体范围 3..82，最小值 3，永不等于 0。**

> **更正**：我最初写成"hi≠0 → 4..50；hi=0 → 3..18"，把 `addne` 的判据当成 `hi != 0`。
> 实际 `0x1002fbe` 的 `orrs r1,r2` 会重设标志，`addne` 判的是 `(hi|lo) != 0`。
> 6.1sol 指出后按三支重算，范围是 3..82。"永不等于 0"这个结论不变。

### 10.2 「两个独立证据」这个说法要改

它说得对：version 和 perfcnt **共用同一条启动路径、同一个共享页、同一条采样链**。
它们是**两个不同字段的佐证**，不是两份独立的执行证据。

→ 改成："两个字段均不符合正常初始化的预期写入结果"。

### 10.3 第三个候选：`stream0.features @0x4001040`

它指出我把 `+0x1044`/`+0x1048`（预填的 in/out 指针）和 `+0x1040`（features，初值 0）混成一个字段了。

核实：

| 地址 | 映像初值 | 固件写什么 |
|---|---|---|
| `0x4001040` **features** | **`0x0`** | `r1`，且 `0x1002fe6` 有 `orr r1,r1,#0x70000` → **必非零** |
| `0x4001044` stream0 in | `0x04014000` | 预填值 |
| `0x4001048` stream0 out | `0x04054000` | 预填值 |

→ **`0x4001040` 是第三个有效候选，而 692 从未读过它。**

### 10.4 交接定稿表述（采用它的建议）

> 692 中 version 仍为哨兵，perfcnt_size 仍为 0，两者均不符合正常初始化的预期写入结果；
> **尚未观测到这些更新，不能据此判断 MCU 是否执行过对应指令**。
> 另有 `stream0.features @0x4001040` 可作为候选观察字，目前没有其读数。

### 10.5 三个候选的汇总表（供下一轮用）

| 字 | 映像初值 | 固件写入值 | 692 读数 | 状态 |
|---|---|---|---|---|
| `0x4000000` version | `0x0` | `0x01010000` | `0xff5aa5f0`（哨兵） | 已读，不符合 |
| `0x4000018` perfcnt_size | `0x0` | `3..82`（必 ≥3） | `0x0` | 已读，不符合 |
| `0x4001040` stream0.features | `0x0` | `x \| 0x70000`（必非零） | **未读** | **待读** |

第三个是**下一轮唯一值得加的读取**，成本是一行 printf。

## 11. 追加（02:05）：第四个候选，但它的值无法静态确定

`0x1002ff2` / `0x1002ff4` 写的是 **`r4`** 到 `CSG0 + 0x1010`（`protm_suspend_size`）
和 `CSG0 + 0x100c`（`suspend_size`）。

| 地址 | 映像初值 | 692 读数 |
|---|---|---|
| `0x400100c` suspend_size | `0x0` | **`0x0`** |
| `0x4001010` protm_suspend_size | `0x0` | **`0x0`** |

**驱动已经读了这两个字**（`shared probe CSG0: ... suspend 0 protected_suspend 0`）。

### 但 r4 的值追不到底

`r4` 在这段里唯一一次写入是：

```
0x1002f1e  add.w r4, r3, r7
```

而 `r3` 和 `r7` 来自：

```
0x1002efe  ldm  r7, {r3, r6, r7}    ; 从内存加载三个寄存器
```

`r7` 在此之前是什么、指向哪里，需要完整的数据流，而这已经超出静态分析的可靠范围。

→ **如果 `r4 != 0`，这两个字"仍为 0"就是有效判据，而且已经被测量过。**
→ **如果 `r4 == 0`，则无信息。**
→ 我无法静态判断，所以这个候选**只能记录，不能当判据**。

### 四个候选的最终状态

| # | 字 | 初值 | 固件写入 | 692 读数 | 可用性 |
|---|---|---|---|---|---|
| 1 | `0x4000000` version | `0x0` | `0x01010000` | `0xff5aa5f0` | ✅ 可用 |
| 2 | `0x4000018` perfcnt_size | `0x0` | 必 ≥3 | `0x0` | ✅ 可用（算式严格） |
| 3 | `0x4001040` stream0.features | `0x0` | `x \| 0x70000` 必非零 | 未读 | ✅ 可用，待读 |
| 4 | `0x400100c`/`0x4001010` | `0x0` | `r4`（未知） | `0x0` | ⚠️ 取决于 r4，不可用 |

**下一轮加读第 3 个就够了。** 前两个已经读过且都不符合预期。
