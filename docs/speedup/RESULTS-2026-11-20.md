# 交接：xaga 启动加速（2026-11-20）

本分支从 `hakios-mtk` 主线独立，目标只有一个：**从按下菜单确认到进 iOS 桌面，尽量快**。
手机 `GAJZ4HIN99AQ69Y9`（xaga / MT6895）。当前 `boot_a` 刷的是 `boot-menu-FINAL.img`。

---

## 一、结论先说

| 版本 | 到苹果 logo | 到桌面 |
|---|---|---|
| 原 `boot-menu-quick.img`（有 60 秒报告页） | 约 30 s | 约 77 s |
| **`boot-menu-FINAL.img`（本轮成果）** | **12 s** | **60 s** |

**提速 17 秒**，且方法全是零风险的编译期开关。剩下 60 秒的构成已经测清楚：

```
loader 自身        3.2 s   ← 已优化到接近极限
  其中 system 读盘  1.6 s   （2.32 GiB / HS-G4，约 1.4 GB/s，接近链路上限）
XNU 初始化到 logo   8.8 s   ← CPU 单核 1 GHz，涉及内核启动路径
XNU 跑用户态       48 s    ← launchd 起 20 个 daemon + SpringBoard 首帧
```

## 二、本轮做了什么（全部已验证）

### 1. 去掉 60 秒报告页（省 60 s）

`mtkloader.c` 里 `BOARD_REPORT_SYSTEM_IMAGE` 打开时会画一屏 `SYSTEM IMAGE` 并
`dbg_delay_ms(60000)` 等拍照。新增开关：

```c
#ifndef XNU_SYSTEM_REPORT_HOLD_MS
#define XNU_SYSTEM_REPORT_HOLD_MS   0u
#endif
```

**这是最大的一笔**，而且对主线直接有用——任何"日常使用"的构建都该关掉它。

### 2. 启动路径完全不写屏幕（省约 18 s）

这是最反直觉的一条，也是最重要的发现。

`mtkdbg.h` 的 `fb_px()` 每画一个像素就是一次 device memory 写（MMU 关闭）。一个字符
= `8*scale × 16*scale` 次写；**一次全屏清屏 = 2,662,800 次写**。启动路径上一连串
`fb_rect(0,0,PANEL_W,PANEL_H,...)` 加每行文字，实测吃掉近 20 秒。

新增运行时开关（不能编译期开关，因为菜单必须画）：

```c
static int fb_silent;
#define FB_SILENT_NOW   fb_silent
```

`fb_px()` / `fb_rect()` / `fbcon_putc()` 都加早退，但**保留光标状态更新**并用 volatile
触一下，否则编译器会把整段文字循环优化删除——这会连菜单标题一起删掉（本轮踩过）。

`boot_choice()` 返回后立刻 `fb_silent = 1`。

### 3. 内核段只清 BSS 尾部（省约 0.4 s）

```c
/* 原来：清 19.3 MB，然后用 14.7 MB 覆盖其中大部分 */
memset(dst_pa, 0, sg->vmsize);
memcpy(dst_pa, kernel + fileoff, sg->filesize);

/* 现在：只清文件没覆盖的 4.6 MB */
if (sg->vmsize > sg->filesize)
        memset(dst_pa + sg->filesize, 0, sg->vmsize - sg->filesize);
memcpy(dst_pa, kernel + fileoff, sg->filesize);
```

### 4. 符号查找先比长度（省约 0.3 s）

`find_syms()` 是 51,418 个符号 × 31 个名字的全量 `strcmp`。加长度预筛后绝大多数直接跳过。
名字长度预先算一次存进 static 数组。

### 5. 分支计时器（诊断用，默认不显示）

`struct stage_times` + `stage_mark()`，8 个时间戳。默认 `STAGE_SHOW_MS=0` 不显示；
给 `-DSTAGE_SHOW_MS=12000u` 会画一屏毫秒数，用来复现本轮的测量。

## 四、试过但失败的（重要，别重犯）

### A. 多核 7 核 → 更慢

`cpus=4` → `cpus=7`：12 s → **17 s** 到 logo，60 s → **68 s** 到桌面。

原因与 `board.h` 记录一致：999 MHz~1 GHz 的低频下，加核主要在加 rendezvous 等待。
**结论：4 核是这台机的最优值，除非主频先抬上去。**

### B. 抬 BL (A78) 到 2000 MHz → 更慢

`BL 1399 → 1999 MHz` 写入成功（回读确认），但 12 s → **21 s**，60 s → **71 s**。

推测原因：A78 上去了而 **DSU 仍在 1339 MHz**，频率差拉大后跨核同步更慢。
**结论：单抬一个 PLL 有害；要动必须是 BL + DSU 同步。**

### C. 把 XNU 搬到 A78 上启动 → 黑屏

做完了实现，验证了三个阶段，仍未通：

| 轮次 | 现象 | 根因 | 状态 |
|---|---|---|---|
| 1 | 黑屏 | **PSCI 不传 context**：实测 A78 入口 `x0 == 0`，代码 `ldr x16,[x0]` 读地址 0 | 已修：改读固定地址 `0x601f0000` |
| 2 | 黑屏 | **核编号不匹配**：唤醒 `core_order[1]`(=core 5)，但设备树 `cpu@0` 是 `core_order[0]`(=core 4)。XNU 用 `ml_get_cpu_number(MPIDR & Aff1|Aff0)` 查表得 1 ≠ `master_cpu`(0)，死等一个不会来的 master | 已修：改唤醒 `core_order[0]` |
| 3 | 黑屏 | **EOImode 未清**：`ICC_CTLR_EL1 = 0x8402`（bit1=1），且 `gic_fix_eoimode()` 只清执行 C 代码的那颗核 | 已修：在 A78 入口汇编清 bit1 —— **但这版的清除代码因汇编标签 `7:`/`8:` 与文件前面重名，实际没编进去** |
| 4 | 黑屏 | 修正标签冲突后清除代码确认真在（`msr ICC_CTLR_EL1,x11` 在 `0x400`），**仍黑屏** | **未解决** |

第 3 轮踩的坑值得记：同一 `.S` 文件里 `7:` / `8:` 是局部标签，重复定义会让汇编器
绑定到前面那个，**新代码被静默跳过**。验证方法：用
`objdump` 或直接搜机器码（`msr icc_ctlr_el1, x11` = `0xd518cc8b`）确认真的在二进制里。

**第 4 轮之后未排查的方向**（按可能性排序）：
1. XNU 早期在 boot CPU 上读 `TPIDR_EL1` 或走 CPU-specific 路径，A78 上的值不对
2. GIC redistributor 的每核 enable：PSCI 起来的核可能没有 enabled PPI
3. `SCTLR_EL1` / 缓存的某位在 A78 上默认值不同
4. A78 与 A55 的 cluster 电源/时钟状态不同，`cntfrq_el0` 之类的基值不同

### D. 改 DSU 频率 → 立刻卡死（第 1 轮抬频时）

第一次 `armpll_raise()` 试图同时改四个 PLL，实际写入的是 **BL 和 DSU**。
板子停在 `raising (rails untouched)` 那一行。

根因两条：
1. **写寄存器时用了 `(1u<<31) | (post<<24) | pcw` 覆盖式写**，把 bit27、bit25 清掉了
   （LL 是 `0x0b133b13`，BL 是 `0x011aec4e`，位分布不同）
2. **DSU 是 A55 访问内存的必经之路**，改它而配置没跟着改，取指还能出缓存，第一次
   内存访问就回不来了

正确写法（已实现）：`before & ~((7u<<24)|0x3fffffu) | (post<<24) | pcw`，只动两个字段。

### E. PCW 超出范围会静默跳过

`pcw = (mhz << post) * 16384 / 26`，必须 ≤ `0x3fffff`（22 位）。所以：

| PLL | POSDIV | 最大可表示频率 |
|---|---|---|
| LL | 3 | 831 MHz |
| BL | 1 | 3327 MHz |
| B | 2 | 1663 MHz |
| DSU | 1 | 3327 MHz |

**LL 想上 2000 MHz 必须先改 POSDIV**，否则 `pcw` 溢出被 `pll_set_mhz()` 拒掉。
这是本轮"以为改了 LL 其实没改"的原因，一度误导了归因。

## 六、复现构建

```bash
cd /home/lizi/IOS/xnu-quick/build     # 独立目录，不碰主线
B=$(pwd)/mtk/mt6895/loader/board.h
ARGS='cpus=4 buttons=2 touchscreen=3 keylog=0 key_scan=0 fbwidth=1080 fbheight=2460 \
fb_disp=1 mali=0 mali_trial=734 headset=0 mtk_ufs_twoblock=0 mtk_ufs_vfs=0 \
mtk_ufs_varread=0 mtk_ufs_probe=0 mtk_ufs_read=0 mtk_ufs_service=0 mtk_ufs_capacity=0'

clang --target=aarch64-linux-gnu -ffreestanding -nostdlib -fno-builtin \
  -mgeneral-regs-only -mstrict-align -Os -Wall -Wextra \
  "-DBOARD_HEADER=\"$B\"" -DXNU_VERBOSE=0 -DXNU_DISPLAY=1 -DXNU_CORES=4 \
  -DXNU_WATCH_SECONDS=0 -DXNU_WDT_SECONDS=0 '-DXNU_RETURN_AFTER="0"' \
  "-DXNU_EXTRA_ARGS=\"$ARGS\"" \
  -c mtk/loader/start.S -o /tmp/s.o
clang ...同上... -c mtk/loader/mtkloader.c -o /tmp/m.o

ld.lld -T mtk/loader/link.ld --oformat binary /tmp/s.o /tmp/m.o -o /tmp/loader.bin

cd /home/lizi/IOS/xnu-quick
python3 /home/lizi/IOS/hakios-mtk/mtk/tools/chainboot.py \
  /home/lizi/IOS/hakios-mtk/backup/boot_a_magisk.img \
  /tmp/loader.bin out.img payload-from-menu.img --partition-size 64M
```

`payload-from-menu.img` 从 `boot-menu-quick.img` 里解出来的 XNUP
（内核 + ramdisk，19.5 MB）。**不要用主线的 `build-payload.bin`**，那份不同、
且没验证过能进桌面。

解 payload 的方法：
```python
import gzip, struct
d = open('boot-menu-quick.img','rb').read()
k = struct.unpack_from('<I', d, 8)[0]
gz = gzip.decompress(d[4096:4096+k])
res3 = struct.unpack_from('<Q', gz, 0x30)[0]
open('payload-from-menu.img','wb').write(gz[res3:])
```

## 七、下一步建议（按收益/风险比排序）

| # | 做法 | 预期 | 风险 |
|---|---|---|---|
| 1 | **只读调查 DSU 的 `clk-div` 与安全时钟切换流程**，搞清楚为什么改 DSU 会死（是不是要先把 A55 切到 26 MHz 晶振） | 为 BL+DSU 同步抬频铺路 | 无（只读） |
| 2 | **A78 迁移的第 5 轮**：查 `TPIDR_EL1` 与 GIC redistributor per-core enable | 成功则启动核快 5.6 倍 | 中（黑屏，能救） |
| 3 | **裁剪用户态 job**：那 48 秒里 launchd 起 20 个 daemon。本机没有 `system.apfs` 的完整重建链路，要先摸通 | 直接砍桌面时间 | 低（不动 loader） |
| 4 | 参考 `ShuiLan114514/SLNeko-XNU` 的 `root_apfs=ufs_iosroot`：不把 2.32 GiB 读进内存，省 2.3 GB 内存 | 可能让内核整体更快 | 中（要写 UFS block service） |

**注意 3 和 4 都不在 loader 里**——本轮的测量已经说明 loader 只剩 3.2 秒，继续优化
loader 的收益上限很低。

## 八、与主线的关系

改动只在 `xnu-quick/build/`（独立副本），**主线的
`/home/lizi/IOS/hakios-mtk/mtk/loader/` 没有任何改动**，无需 `git checkout` 恢复。

主线若要用本轮成果，拷这三个改动即可：
1. `XNU_SYSTEM_REPORT_HOLD_MS`（`mtkloader.c`）

第 1 条和第 2 条是任何"日常使用版"都该有的；第 3 条对 bring-up 调试版无害。
