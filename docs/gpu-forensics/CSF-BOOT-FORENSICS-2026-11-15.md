## §1 debug_top：它是 MTK MFG 的总线空闲指示，不是 Mali 寄存器

### 1.1 它是什么

`0x13FBF178` 在 MTK 的 **mfg_top_config** 块里（`g_mfg_top_base` / `g_mfg_base`），
是 `MFG_DEBUG_TOP`：`MFG_DEBUG_SEL (0x13FBF170)` 选中某条调试通道后，
该寄存器报告那条通道的状态。选通由 `MFG_QCHANNEL_CON (0x13FBF0B4) bit0 = MFG_ACTIVE_SEL` 配合。

[S] `drivers/gpu/mediatek/gpufreq/v2/gpufreq_mt6895.c:1249-1274`（Xiaomi xaga-s-oss 分支）:

```
1253	/* MFG_QCHANNEL_CON 0x13FBF0B4 [0] MFG_ACTIVE_SEL = 1'b1 */
1258	/* MFG_DEBUG_SEL 0x13FBF170 [1:0] MFG_DEBUG_TOP_SEL = 2'b11 */
1266	 * polling MFG_DEBUG_TOP 0x13FBF178 [0] MFG_DEBUG_TOP
1267	 * 0x0: bus idle
1268	 * 0x1: bus busy
1270	do { val = readl(g_mfg_top_base + 0x178); } while (val & 0x1);
```

调用点 [S] `gpufreq_mt6895.c:265, 280`（`.check_bus_idle = __gpufreq_check_bus_idle`），
被 `__gpufreq_dump_infra_status()` 调用两次、被 `__gpufreq_gpm_control()` 两侧各调一次。
**它是诊断读，不是电源门控** —— vendor 自己也只是在 dump 时读它。

### 1.2 0x4 和 0x1b 的位含义：**vendor 源码互相矛盾，且本 SoC 上与实测不符**

| 来源 | 位定义 |
|---|---|
| `gpufreq_mt6895.c:1266-1268`（v2，本 SoC） | **bit0**：0=idle, 1=busy |
| `gpufreq_mt6893.c`（Motorola fork，同代） | 同 v2：bit0 |
| `gpufreq/v1/mt6853/mtk_gpufreq_plat.c:771-775` | **bit2**：1=idle, 0=non-idle |
| `gpufreq/v1/mt6873/mtk_gpufreq_plat.c:816-820` | bit2：1=idle |
| `gpufreq/v1/mt6885/mtk_gpufreq_plat.c:650-653` | bit2：1=idle |

[S] v1 原文：
```
/* polling register MFG_DEBUG_TOP (0x13fb_f178) bit 2 = 0x1 */
/* => 1 for bus idle, 0 for bus non-idle */
do { val = readl(g_mfg_base + 0x178); } while ((val & 0x4) != 0x4);
```

**[I] 关键推论：这两套定义在同一硬件上不可能都为真，而实测证明在 MT6895 上 bit0 才是 busy。**

你的实测值（`docs/round-10-support/trial-675..678-mali.txt`、`round-11-support/trial-679-mali.txt`、
`round-13-support/trial-686-mali.txt:108,119,252,257-258`，共 227 条采样）**只有两个值：0x4 和 0x1b**。

- 若按 v2（bit0=busy）：`0x4` = `0b00100` → bit0=0 = **idle**；`0x1b` = `0b11011` → bit0=1 = **busy**。
  **完全自洽**，且与日志文字 "(idle after 0 spins)" / "(still busy after 100000 spins)" 一致 ——
  因为 driver 的 `mfg_bus_idle()` 就是按 bit0 判的（`hakios.mali610.trial-686.c:2275`）。
- 若按 v1（bit2=idle）：`0x4` 的 bit2=1 → idle（巧合一致），但 `0x1b` 的 bit2=**0** → non-idle（也一致）。
  **两套定义在"0x4=idle / 0x1b=忙"这个结论上碰巧同向**，所以你的 driver 结论没有受这个矛盾影响。

**[I] 但 0x4 和 0x1b 不是"一个标志位"，是两条不同的通道读数。**
0x4 = bit2；0x1b = bit0|bit1|bit3|bit4。如果只是一位 busy 标志，无法解释为什么
"idle 时 bit2 亮、busy 时 bit2 灭且 bit0/1/3/4 亮"。最简解释：`debug_top` 是
**多路复用状态字的低 5 位**，AUTO 前后 `MFG_DEBUG_SEL` 虽然都读 `0x3`
（`trial-686-mali.txt:108,252` 均为 `debug_sel 0x3`），但被监视通道的**内部状态机换了档**，
所以整个字变了 —— 不是"busy 拉高"，是"通道状态整体切换"。

**[I] 决定性判据：0x1b 在 MCU 关掉之后仍然保持。**
`trial-686-mali.txt:252`（失败后）`0x1b`，`:257`（`MCU_CONTROL=0` 之后）**仍然 `0x1b`**，
`:258` 四毫秒四次读 `0x1b 0x1b 0x1b 0x1b`。
`docs/GPU-ROUND-12.md:38` 记录 DISABLE 后等 100000 次仍 `0x1b`。

→ **这个字不跟随 MCU 状态机。** 如果它是 MCU 的 AXI 取指通道 busy 标志，MCU 被禁用后
总线必然在若干周期内排空并回到 idle。它没有。所以 **[I] `debug_top` 的变化不是"MCU 在取指"的证据，
而是 GPU 子系统从"未启动/未使能"进入"已使能但卡住"这个更粗粒度的状态**；
关 MCU 只关掉了 MCU 的状态机，没关掉让它保持 busy 的那个东西（时钟/电源域仍在、或另一主控仍在驱动总线）。

### 1.3 对"MCU 卡在 AXI"假说的评价

你的 driver 注释（`hakios.mali610.trial-686.c:2246-2256`）把它当作
"MCU 无法通过一个永不 idle 的 AXI 端口取指"的证据。**[I] 这个推论不成立**，因为：

1. 因果方向未知：可能是 MCU 卡住导致总线忙，也可能是总线忙导致 MCU 卡住，还可能是
   第三方（GPUEB）把总线占住而 MCU 从没被允许发起事务。关 MCU 后仍忙，**排除了第一种**，
   留下后两种。
2. `docs/GPU-ROUND-12.md:38` 与 `trial-686-mali.txt:257` 已经证明它与 MCU 使能无关。

**§1 结论：`debug_top` 在本平台上是一个"GPU 子系统级"的状态字，
能说明"子系统在 AUTO 之后进入了不同的活动状态且不可回退"，不能说明 MCU 在取指。
它是一条有用的旁证，不是判据。**

## §2 0x3034 / 0x3020 / 0x3090 / 0x3098：**全部已识别，是 GPU_CONTROL 的 MCU 侧镜像**

### 2.1 0x3000 块的名字

[S] `mali_gpu_csf_control_registers.h:30`（ARM 自动生成头，标注 "This header was autogenerated"，
在 Xiaomi xaga-s-oss、Motorola kernel-mtk、rockchip、nxp-imx、mu300 各仓一致）：

```c
/* GPU_REGISTERS register offsets */
#define GPU_CONTROL_MCU 0x3000 /* () MCU control registers */
```

[S] `mali_kbase_regmap_legacy_csf.h:25-26` 与 `mali_kbase_gpu_regmap_csf.h:32-36`（新版权威版）：

```c
/* GPU_CONTROL_MCU base address */
#define GPU_CONTROL_MCU_BASE 0x3000
/* MCU_SUBSYSTEM base address */
#define MCU_SUBSYSTEM_BASE 0x20000
```

[S] `mali_kbase_gpu_regmap_csf.h:86`：`#define GPU_CONTROL_MCU_REG(r)  (GPU_CONTROL_MCU + (r))`
—— 即 **`GPU_CONTROL_MCU_REG(x)` 与 `GPU_CONTROL_REG(x)` 是同一套偏移，落在 0x3000 基址上**。
[S] 该镜像存在的直接用例：`mali_kbase_gpu_regmap_csf.h:353`
`/* GPU_CONTROL_MCU.GPU_IRQ_RAWSTAT */` + `#define PRFCNT_SAMPLE_COMPLETED (1 << 16)`
—— 性能计数器完成中断是**从 MCU 侧**轮询的。

[S] kbase 把这一整个区间列为"不可从 AP 随意访问"：
`mali_kbase_device_hw_csf.c:193-200`
```c
if (((offset >= MCU_SUBSYSTEM_BASE) && (offset < IPA_CONTROL_BASE)) ||
    ((offset >= GPU_CONTROL_MCU_BASE) && (offset < USER_BASE))) {
        WARN(1, "Invalid register offset 0x%x", offset);
        return false;
}
```
（仅 `CONFIG_MALI_DEBUG` 下生效的警告，但意图明确：**这是另一个消费者的寄存器视图**。）

### 2.2 逐个识别

| 偏移 | = GPU_CONTROL 的 | 你的实测 | 判读 |
|---|---|---|---|
| `0x3020` | `GPU_IRQ_RAWSTAT (0x020)` | `0x600` before/after 恒定 | **[S]** `0x600` = BIT(9)\|BIT(10) = `GPU_IRQ_POWER_CHANGED` + `GPU_IRQ_POWER_CHANGED_ALL`（`panthor_gpu_regs.h:37-38`）。MCU 侧看到的挂起电源变化中断，AP 侧已清、MCU 侧未清。**独立目的端锁存，不是漏写。** |
| `0x3034` | `GPU_STATUS (0x034)` | before `0x0` → after `0x1` | **[S]** `GPU_STATUS_ACTIVE = BIT(0)`（`panthor_gpu_regs.h:44-45`）。AP 侧 `0x034` 同期也读 `0x1`（`trial-686-mali.txt:237,254` "gpu status 0x1/0x1"）。**同一个 GPU_STATUS，只是两个视图。** |
| `0x3090` | `GPU_CYCLE_COUNT (0x090)` | 递增 | **[S]** 已由你的"包络"实测证实：AP 两次读把 MCU 视图夹在中间（`trial-686-mali.txt:256-257` "enclosed 1"），`docs/GPU-ROUND-2.md:31`。**同一个自由运行计数器。** |
| `0x3098` | `GPU_TIMESTAMP (0x098)` | 递增 | 同上。 |
| `0x3030` | `GPU_CMD (0x030)` | 读 `0` | **[I]** 反证性证据：GPU_CMD 是 WO（`panthor_gpu_regs.h:41-47` 只有写侧语义），读回 0 正确。若是"另一个窗口"它就该有值。**布局对齐由此得到独立确认。** |

**[I] 由此推出：0x3000 块不携带任何 AP 侧看不到的新信息。** 它唯一的额外价值是
**"MCU 自己眼里 GPU 是什么样"**。而 `0x3034` 在 AUTO 之后从 0 变 1，说明
**GPU_STATUS_ACTIVE 是 MCU 侧被置位的**（不是 AP 侧 power-on 顺手置的，因为 before_AUTO 是 0）。

这是你手上**唯一一个能证明"MCU 至少执行了某段代码"的寄存器证据**——
尽管它也可能只是 MCU 上电握手的硬件副作用，而非取指 [I]。

**[?] 未找到**：0x3020/0x3034/0x3090/0x3098 这四个**具体的 GPU_CONTROL_MCU 子偏移**
在任何公开寄存器图里的逐条列出。kbase 只给了基址 + `GPU_IRQ_RAWSTAT` 一个用例，
其余靠"与 GPU_CONTROL 同布局"推得。ARM 的 Mali-G610 TRM 是保密文档
（NXP AE 在 [community.nxp.com 帖](https://community.nxp.com/t5/Zephyr-Project/HDMI-Configuration-Support-in-Zephyr-for-i-MX95-FRDM-EVK/m-p/2399832)
里明确说 "This document is Arm confidential IP. NXP is not permitted to forward it"）。

## §3 公开先例：**部分 YES，但不是完全同形**

### 3.1 直接同形（MCU_STATUS=ENABLED 但没 boot）—— **NO**

检索了 lore.kernel.org（dri-devel / linux-mediatek / linux-arm-msm）、
LWN 的 panthor 全系列 patch 讨论、freedesktop dri-devel 归档、
NXP community、Arm community 检索结果、panthor/panfrost GitLab。
**没有找到任何一份公开报告说"MCU_STATUS 读到 1/ENABLED，但 JOB_INT_GLOBAL_IF 永不置位"。**

原因很可能很简单 **[I]**：panthor 的错误信息是
`Failed to boot MCU (status=%s)`，正常用户看到 `status=enabled` 时**不会意识到这是个异常组合**，
而 panthor 自己也不会额外警告。所以这类案例即使发生过，也不会以可检索的形式出现在邮件列表里。

### 3.2 相邻但不同的先例 —— **YES，两条，都很有价值**

**(a) MT8196（同厂、同 CSF 架构、G925）：ASN_HASH 未编程 → AS0 VA 0 页 fault → `Failed to boot MCU (status=fatal)`**

[Chia-I Wu, `[PATCH v2 2/2] drm/panthor: add custom ASN_HASH support for mt8196`](https://lore.kernel.org/lkml/20250913002155.1163908-3-olvaffe@gmail.com/)
原文日志：
```
panthor 48000000.gpu: [drm] *ERROR* Unhandled Page fault in AS0 at VA 0x0000000000000000
panthor 48000000.gpu: [drm] *ERROR* Failed to boot MCU (status=fatal)
```
修法是写 `GPU_ASN_HASH(0..2) = {0xb, 0xe, 0x0}` 并置 `GPU_L2_CONFIG_ASN_HASH_ENABLE`。

**对你的意义 [I]**：MTK 的 Mali 实现**需要私有 ASN_HASH**，且缺了它**正好表现为 VA 0 访问失败**。
你的现象是 VA 0 侧**毫无动静**（无 fault、`AS0 faultstatus=0`），比 MT8196 更"安静"。
这是一个**必须先排除的同类项**：你的 `GPU_L2_CONFIG (0x048)` / `GPU_ASN_HASH (0x2C0..0x2C8)`
有没有写过？如果没有，MTK 平台上这是**已知会导致 FW 启动失败**的配置缺口。
注意 G610 是 arch major 10，而 patch 里判断 `< 11` 就报"不支持自定义 ASN hash"，
所以 MT8196 的做法**不能直接照搬到 G610**，但"MTK 需要查这一项"这个结论成立。

**(b) i.MX95 / Mali-G310（Zephyr 裸机，无 Linux）：MCU enable 后 status 停在 disabled，无错误无中断**

[NXP Community 帖](https://community.nxp.com/t5/Zephyr-Project/HDMI-Configuration-Support-in-Zephyr-for-i-MX95-FRDM-EVK/m-p/2399832)，
提问者原话："After we enable it, its status stays **disabled** and it never starts running.
There is no error and no interrupt - it simply does not boot."

**对你的意义 [I]**：这是**公开可查的"裸机自写驱动启动 CSF MCU 失败"案例**，症状族相同
（无 fault、无中断、静默），但具体读数不同（他是 status=disabled，你是 status=enabled）。
NXP AE 的回复值得抄下来当方法论文档：
> "The complete boot flow is available in the following two public sources:
> Panthor — mainline driver, the main one to look at (it actually boots the MCU and supports i.MX95);
> kbase — Arm's official driver, for cross-checking."

即：**没有 TRM，唯一权威就是 panthor + kbase 的代码**。这与你正在做的事一致。

### 3.3 与本板最接近的"已知会静默失败"的项

**[I] 你项目自己已经踩过并修复的 16K/4K 页表步进 bug**（`docs/BREAKTHROUGH-16K-PAGE-BUG.md`）
在当时的表现就是"无 fault、无中断、状态机接受 AUTO 写、一个字都没执行"。
这说明**这块板上"静默失败"是常态而非异常** —— 每一次都必须靠覆盖率/自检数字来排除，
不能靠"没有 fault 所以映射没问题"。

## §4 MCU_STATUS 语义：**ENABLED 确实会撒谎，而且 panthor 就是这么设计的**

### 4.1 位定义：**是枚举，不是 one-hot**

[S] `panthor_fw_regs.h:14-18`（我拉到的 master 版，29 行全文）：
```c
#define MCU_STATUS					0x4
#define   MCU_STATUS_DISABLED				0
#define   MCU_STATUS_ENABLED				1
#define   MCU_STATUS_HALT				2
#define   MCU_STATUS_FATAL				3
```
[S] 同一文件的 control 侧 `:9-12`：
```c
#define MCU_CONTROL					0x0
#define   MCU_CONTROL_ENABLE				1
#define   MCU_CONTROL_AUTO				2
#define   MCU_CONTROL_DISABLE				0
```

**[I] 这是 2 位枚举（0..3），不是位掩码。** 所以"MCU_STATUS=1"只能是 ENABLED，
不存在"bit0 是 enable、bit1 是 halt 所以 1 和 2 可以并存"的读法。
你任务描述里那句"the enum is 0=DISABLED, 1=ENABLED, 2=HALT, 3=FATAL"是对的，
`panthor_fw_regs.h:14-18` 的引用也准确。

**但 kbase 的旧头文件给了一个会误导人的名字：**
[S] `mali_kbase_gpu_regmap_csf.h:126`（r32p1）/ `mali_gpu_csf_control_registers.h` 同族：
```c
#define MCU_STATUS_HALTED        (1 << 1)
```
`(1<<1)` = `2` = HALT，与 panthor 一致。**但它的写法长得像位掩码**，
容易让人以为 `MCU_STATUS & MCU_STATUS_HALTED` 是合法判据。对 0/1/2/3 枚举，
**必须用 `==`，不能用 `&`**。你 driver 里用的是 `==`（`hakios.mali610.trial-686.c:3955` 附近），正确。

### 4.2 panthor 到底检查什么 —— **只看中断，完全不看 MCU_STATUS**

[S] `drivers/gpu/drm/panthor/panthor_fw.c:1132-1164`（master，`panthor_fw_start()`）：

```c
1132	static int panthor_fw_start(struct panthor_device *ptdev)
1133	{
1134		struct panthor_fw *fw = ptdev->fw;
1135		bool timedout = false;
1136
1137		ptdev->fw->booted = false;
1138		panthor_irq_enable_events(&ptdev->fw->irq, ~0);
1139		panthor_irq_resume(&ptdev->fw->irq);
1140		gpu_write(fw->iomem, MCU_CONTROL, MCU_CONTROL_AUTO);
1141
1142		if (!wait_event_timeout(ptdev->fw->req_waitqueue,
1143					ptdev->fw->booted,
1144					msecs_to_jiffies(1000))) {
1145			if (!ptdev->fw->booted &&
1146			    !(gpu_read(fw->irq.iomem, INT_STAT) & JOB_INT_GLOBAL_IF))
1147				timedout = true;
1148		}
1149
1150		if (timedout) {
1151			static const char * const status_str[] = {
1152				[MCU_STATUS_DISABLED] = "disabled",
1153				[MCU_STATUS_ENABLED] = "enabled",
1154				[MCU_STATUS_HALT] = "halt",
1155				[MCU_STATUS_FATAL] = "fatal",
1156			};
1157			u32 status = gpu_read(fw->iomem, MCU_STATUS);
1158
1159			drm_err(&ptdev->base, "Failed to boot MCU (status=%s)",
1160				status < ARRAY_SIZE(status_str) ? status_str[status] : "unknown");
1161			return -ETIMEDOUT;
1162		}
1163		return 0;
1164	}
```

**三个关键点：**

1. **成功判据只有一个**：`booted` 为真。而 `booted` 只在中断处理里被置位 ——
   [S] `panthor_fw.c:1098-1110` `panthor_job_irq_handler()`：
   ```c
   1109	if (!ptdev->fw->booted && (status & JOB_INT_GLOBAL_IF))
   1110		ptdev->fw->booted = true;
   ```
   `JOB_INT_GLOBAL_IF = BIT(31)`（`panthor_fw_regs.h:21`），基址 `JOB_INT_BASE = 0x1000`（`:20`），
   即硬件偏移 `0x1000` 的 bit31。

2. **`MCU_STATUS` 只在失败之后被读，且只用于打印**。
   `:1145-1147` 的二次确认读的是 `INT_STAT`（中断状态），**不是** `MCU_STATUS`。
   `:1157` 那次读发生在 `timedout == true` 之后，纯粹为了生成错误串。

3. **因此 `status=enabled` 是 panthor 的一个合法失败输出**。
   `:1153` 的 `[MCU_STATUS_ENABLED] = "enabled"` 存在的唯一目的，
   就是让你看到 `Failed to boot MCU (status=enabled)` 这一行。
   **上游作者知道这个组合会发生。**

**[S] 交叉验证 —— drm/tyr 的演进正好证明了这一点：**

- 早期版本用 `MCU_STATUS` 单独判成功（[freedesktop dri-devel, 2026-Feb, PATCH 12/12](https://lists.freedesktop.org/archives/dri-devel/2026-February/549569.html)）：
  ```rust
  regs::MCU_CONTROL.write(dev, &self.iomem, regs::MCU_CONTROL_AUTO)?;
  if let Err(e) = poll::read_poll_timeout(
      || regs::MCU_STATUS.read(dev, &self.iomem),
      |status| *status == regs::MCU_STATUS_ENABLED,
      time::Delta::from_millis(1), time::Delta::from_millis(100),
  ) { ... pr_err!("MCU failed to boot, status: {}", status); return Err(e); }
  ```
- 后续版本改成**两个条件**，并**先清 stale 中断**（[PATCH v9 7/7](https://mail-archive.com/dri-devel@lists.freedesktop.org/msg623783.html)）：
  ```rust
  // Discard any stale global interrupt.
  io.write_reg(JOB_IRQ_CLEAR::zeroed().with_glb(true));
  io.write_reg(MCU_CONTROL::zeroed().with_req(McuControlMode::Auto));
  ... |(mcu_status, irq_rawstat)| {
      mcu_status.value() == McuStatus::Enabled && irq_rawstat.glb()
  }
  ```

**[I] 结论：tyr 从"只看 status"改成"status AND 中断"，本身就是上游承认
"`MCU_STATUS == ENABLED` 单独不足以证明启动成功"的书面记录。**
（注意 tyr 那行 `JOB_IRQ_CLEAR ... with_glb(true)` 还顺带解决了一个你可能会踩的坑：
**AUTO 之前必须清掉 JOB_INT 的 stale bit31**，否则你会读到上一次残留的"成功"。）

### 4.3 所以"ENABLED 但什么都没发生"意味着什么

**[I] 最保守、且与所有证据一致的判读：`MCU_CONTROL` 的状态机接受了 AUTO 请求并把状态推到 ENABLED，
但 MCU 核心没有跑到"初始化完成 → 写 global iface → 拉 GLOBAL_IF"这一段。**

`MCU_CONTROL`/`MCU_STATUS` 是**请求/应答状态机寄存器**，不是"CPU 在跑"的证据。
你在 `hakios.mali610.trial-686.c:3955-3970` 的注释已经把这个道理写对了
（"MCU_STATUS only reports the state machine we poked with MCU_CONTROL; it is one if the
request was taken, not proof that a single instruction ran"）。

**而且它还是粘滞的 [I]**：`docs/GPU-ROUND-15.md:3` 记录 `MCU_CONTROL=0` 之后
`status` 仍为 1，额外 10000×10µs 有界观察也没离开 1。
panthor 的 `panthor_fw_stop()`（`:1167-1175`）用 `status == MCU_STATUS_DISABLED` 轮询并
`drm_err("Failed to stop MCU")` —— **你这个板子会稳定命中那条错误路径**。
这与"MCU 核心没在跑、状态机停在最后一个被接受的状态"完全吻合；一个真在跑的核会响应 DISABLE。

### 5.3 你的代码在这条路上的位置

[S] `hakios.mali610.trial-686.c:1082-1086`：每段 `memcpy` 之后紧跟 `mem_flush(&s->mem)`。
[S] `:773-779` `mem_flush()`：uncached 页只 `dsb sy`，cached 页 `FlushPoC_DcacheRegion()` 再 `dsb sy`。
[S] `:1403` 还有一次全段 `mem_flush`。

`FlushPoC_DcacheRegion` 是 clean+invalidate（`:54-59` 注释），对 non-snooped 平台是正确的一对。

**但还有两个没有排除的变体 [I]：**

1. **MMU 页表本身的 cache**：`pt_map()` 在 `gPtUncached == false` 时会
   `FlushPoC_DcacheRegion`（`:941-953`），而 `gPtUncached` 取决于分配到的页是否 uncached（`:886, 913`）。
   如果某轮页表页是 cached 且 flush 时序不对，MCU 的 walk 就会读到**旧 PTE**。
   你已经用 `mali_fwnc` / `mali_ptvendor` 测过一部分（见 5.4），但**页表属性这一条没有单独做过单变量。**

2. **`mem_flush` 之后再写**：`:3648`（sentinel）、`:3760`、`:3928`、`:4175` 都在 shared 段上做
   read-modify-flush。如果 sentinel 写入与 `mem_flush` 之间有任何路径**跳过了 flush**，
   MCU 起来后会看到旧值 —— 但那会表现为"sentinel 没被改"，而你的实测是
   "sentinel 在 CPU 侧读回仍是 sentinel"，**这反而是 flush 生效的证据 [I]**。

## §6 判决

### 6.1 先确立几条硬事实（我实测/解析，不是推测）

**(A) 你的固件是 v0.1，不是 ARM 参考的 v0.3。**
解析 `/home/lizi/IOS/work-xaga/codex/out/round-18-support/mali_csffw.bin`（258048 B）：

```
magic 0xc3f13a6e  major 0  minor 1  hdr.size 0x300
```

对比 ARM 官方 arch10.8（282624 B）：`major 0 minor 3 hdr.size 0x318`。
**两者都叫 mali_csffw.bin，但差两个 minor 版本、差 24576 字节、差 5 个 section。**

**(B) 两份固件的段布局完全不同 —— 你的那份根本没有 0x800000 段。**

| 你的真机 v0.1 | ARM 参考 v0.3 |
|---|---|
| `0x9` va `0x0-0x1000` | `0x9` va `0x400000-0x410000`、`0x410000-0x420000`、`0x0-0x10000` |
| `0xd` va `0x1000000-0x1010000` (EX) | `0xd` va `0x800000-0x820000` (EX) |
| `0x8000000b` va `0x2000000-0x203e000` 等 3 段 | `0x8000000b` va `0x2000000-0x2040000` |
| `0x80000009` va `0x2800000-0x2840000` | `0x80000009` va `0x1000000-0x1040000` |
| `0x2b` va `0x3000000-0x303e000` 等 3 段 (PROT) | `0x2b` va `0x3000000-0x3040000` |
| `0xc000001b` va `0x4000000-0x4094000` (shared, cm=3) | `0xc000001b` va `0x4000000-0x4010000` (shared, cm=3) |

**(C) VA0 不可执行是 ARM 的**标准做法**，不是你的 bug。**
两份固件的 `va start == 0` 段**都是 `flags=0x9`（rd + cm=1 CACHED，无 EX）**。
向量表只被**数据读取**（MCU 读 VA4 拿 reset PC），取指发生在 EX 段。
→ **§6 的"VA0 必须可执行吗"答案是：不需要。ARM 自己的参考固件就不标。**
→ 你的 `mali_fwx=1`（全段可执行，trial 605）在坏映射下测的，不能作为反证（`GPU-ROUND-7.md:161`）。

**(D) reset PC 指向真指令。**
`VA0 = 0x02040000`（这**不是** version 字段，是 sec0 里本来就有的常量）。
`VA4 = 0x010018ed` → sec1 数据偏移 `0x18ed` → 字节 `b6 26 48 4f f0 0b 01 01`（合法 Thumb-2）。

**(E) 你日志里 "version 0xff5aa5f0 in 0x4002000" 那行的 `0x4002000` 是 `input_va`，不是 version 地址。**
真机固件 shared 段 `+0x00` 是 version（**镜像初值 0**）、`+0x08` 是 `0x04002000`（input_va）、
`+0x0c` 是 `0x04003000`（output_va）、`+0x10` = 8（group_num）、`+0x14` = 0xa0（group_stride）。
`hakios.mali610.trial-686.c:4063-4065` 打印的是
`raw->version, raw->input_va, raw->output_va, raw->group_num, raw->group_stride`，
所以 `0xff5aa5f0` 确实是 **version（在 `0x4000000`）**，`0x4002000` 是紧邻的 input_va。
**判据本身没错，但任务描述里的地址是错的 —— 后续任何"读 0x4002000 看 version"的探针都会读错。**

**(F) `0x3034` 在 AUTO 之后 0→1（`0x3030` 恒 0 作为布局反证）。**
这是唯一一个"MCU 侧状态确实变了"的寄存器证据，且它镜像的是 `GPU_STATUS_ACTIVE`。

### 6.2 排名

#### ① **[proven by source] `MCU_STATUS=ENABLED` 在本场景下**不构成**"已启动"的证据，你的观测是自洽的失败态。**

`panthor_fw.c:1132-1164` 的成功判据只有 `JOB_INT_GLOBAL_IF`，`MCU_STATUS` 仅用于打印错误串，
且 `"enabled"` 是它明确列出的失败状态之一（`:1153`）。tyr 从只查 status 改成
`status AND glb`（§4.2）是上游承认这一点的书面记录。
**→ 不要再把 `MCU_STATUS=1` 读成"矛盾"或"部分成功"；把它读成"请求被接受，核没跑"。**

#### ② **[proven by source] `debug_top` 的 0x1b 与 MCU 使能无关，不能作为"MCU 在取指"或"AXI 卡死"的判据。**

`MCU_CONTROL=0` 之后 100000 次轮询仍 `0x1b`（`docs/GPU-ROUND-12.md:38`、
`trial-686-mali.txt:257-258`，四次采样全同）。一个跟随 MCU 状态机的总线标志不可能这样。
**[I] 它反映的是 GPU 子系统级的、不可回退的状态切换。**

#### ③ **[plausible，且是唯一还没被真正试过的强候选] MTK 私有初始化项缺失 —— 首要怀疑 `GPU_L2_CONFIG.ASN_HASH_ENABLE` + `GPU_ASN_HASH(0..2)`。**

**依据（同厂同架构的公开失败案例）**：MT8196 在**没有**这套私有 hash 时，
panthor 的报错正是 **`Unhandled Page fault in AS0 at VA 0x0` + `Failed to boot MCU (status=fatal)`**
（§3.2a）。修好就正常 probe。
**你的现象比它更安静**（无任何 fault），但"MTK 需要私有 ASN_HASH"是**已被上游接受的平台事实**。
注意 [I]：该 patch 里 `GPU_ARCH_MAJOR < 11` 会走"不支持"分支，G610 是 major 10，
所以**不能照抄 {0xb,0xe,0x0}**，但**必须去查你板子上这两个寄存器当前是什么值、有没有被写过**。
这是一条**零风险、只读**的探针，且此前 82 条 store trace 里没有它（`docs/GPU-ROUND-1.md:185-187`
只列了 0x3020/0x3090/0x3098 的"四份 history 全无访问"）。

#### ④ **[plausible] 页表页的缓存属性（不是段数据的）**

673（全段 NON_CACHEABLE）已排除**段数据**层面的 cached-but-noncoherent（§5.4）。
但 `mali_ptvendor` 改的是 SH/NG，**没有单变量测过"页表页强制 uncached + 显式 flush"**。
`hakios.mali610.trial-686.c:886,913,941-953` 的 `gPtUncached` 逻辑是一条分支，
不是无条件保证。**风险：MCU walk 读到旧 PTE → 与"无 fault 但取指不成功"的形态吻合。**

#### ⑤ **[plausible] MTK 电源/时钟序列的某个环节让 GPU 处于"可读寄存器但不可执行"的半开状态**

支撑：`debug_top` 进入不可回退的 0x1b、`MCU_CONTROL=0` 无效（`GPU-ROUND-15.md:3`）、
`0x3034` 变 1 但无取指。三者共同指向"子系统被使能到一个状态后无法退出"。
**[I] 但这条最难验证，且与 ③④ 不互斥。** 建议放在 ③④ 之后。

#### ⑥ **[speculation] GPUEB 仍持有 MFG 总线**

你的 driver 已经怀疑过（`hakios.mali610.trial-686.c:2310-2320` 注释），
但 trial-686 的 `gpueb ... not mapped`（`trial-686-mali.txt:47,259`）意味着**这条从未被实测**。
`debug_top` 关 MCU 后仍忙，与"第三方持有总线"相容。**没有证据，只有相容性。**

#### ⑦ **[已排除] VA0 不可执行 / 段不可写 / 段被缓存污染**

- VA0 不可执行：ARM 参考固件同样不可执行（§6.1C）→ **排除**。
- 全段可执行可写（trial 605）→ 失败，但**在坏映射下测的，不构成证据**（`GPU-ROUND-7.md:161`）。
  建议在 16K 修复后的基线上**重跑一次 `mali_fwx=1`**，否则这条严格说仍是 open 的。
- 段数据缓存污染：673 已排除（§5.4）。
