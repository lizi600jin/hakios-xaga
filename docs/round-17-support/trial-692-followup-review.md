# 692后续推理评审

结论：反对用“fault=0”证明正常固件没有访问PROT区，也不把现有结果定性为MCU时钟/复位/启动握手未通。同意暂停无依据的新增寄存器写，优先选择能增加因果分辨率的离线调查；MFG0 probe继续取消。以下评审不是下一条真机实验的授权包。

## 对“692回答skipprot一半”的反对理由

692根本没有启用skipprot。trial-692-mali.txt:93、97、101明示sec6/7/8仍以flags0x2b、rw-映射；驱动:1062-1066分配普通内存，:1130-1153生成有效、可写的数据页。正常写这些页本就不应产生缺页故障。

所以两种情况都能产生fault=0：从未访问该区；访问了有效、可写的映射。692不能区分两者，也没有替代“不映射该区”的干预。把“访问未映射地址会fault”搬到仍有映射的对照里，是前提偷换。

没有采到fault，也不是所有MMU/fetch/store路径正常的证明。有限采样不等于全过程恒0；硬件不产生可见fault与根本没发请求也不能仅凭这些读数区分。

## 另外两处数值/机制修正

- 从0x010018ed到0x03000000相差0x1ffe713，约31.994MiB；不是48MB以上。更关键的是，虚拟地址距离不决定访问时机：代码可构造目标地址后直接store，不会逐字节“走过去”。witness只覆盖reset向量、0x01000000代码和0x04000000/4的store链；其未完成store不能证明第一条指令未取到。
- 三个PROT固件节不等于三个PTE。当前覆盖64个4K叶；若跳过整个分配块，还会改变后续物理分配和页表布局。该干预的解释需要控制这些因素，不能简写成“少三项让walk变短”。

## 这是否支持底层时钟/复位/握手故障

它仍是候选，但不是已证结论。版本与JOB是有效的正向完成证据，没出现时不足以定位失败阶段；witness是一项端到端取指/执行/store可见性的实验，阴性同样没有分开这些环节。观察点位于核外不使正向证据无效，只限制阴性结果的定位能力。

至少仍有三个待区分的情形：CSF MCU未开始执行；reset取数/取指被阻塞；已经执行若干指令而首次可见store被阻塞。692的八个样本没有完成这个分类。不能用“多轮失败”把第三种排除后直接认定第一种。

## 我的下一步取舍

1. 目前不自动执行skipprot、不直接换固件刷入，也不添加未知GPUEB读。优先做离线候选固件兼容性/差异比较和时钟复位控制链审计，其成本低于一轮缺少因果依据的刷机。
2. 固件比较要核对目标GPU架构（当前GPU_ID=0xa8670004）、来源/完整哈希、容器和条目、SP/reset向量、vector/code/shared区域和接口布局、启动代码差异。只有找到能解释现象的变化，才提出具体换包试验；版本更新和体积变化本身不是依据。当前witness失败已经降低“仅正常固件主流程代码有问题”作为唯一解释的说服力，但未完全隔离异常向量、映射和布局。
3. 换观测手段的建议合理，但先证明哪个SPM/GPUEB信号真正对应CSF MCU的clock/reset/请求ACK、由AP/ATF/GPUEB谁控制，再定义正常与异常。MFG域有电不等于MCU复位已释放；GPUEB自身状态也不能直接当CSF MCU状态。没有对应关系就多读几个域状态，只是换一组不能定位的外部样本。三个禁读地址和mali_rpc禁用边界继续保留。
4. 在尚无上述新证据而必须从三个真机候选中选一条时，仍把skipprot列在换固件和段序前，因为它有明确的参考实现处理差异；但这是相对排序，不是高成功率判断。692并未给出新的合法降级证据，实际是否投入要看可控补丁和能回答的问题。段加载顺序目前仍最低，因为所有VA范围不重叠、复制与建表均在AUTO前完成。

下一个方案仍需给齐假设、证据、反证条件、盲区、替代方案。先讨论具体信号/代码差异，不以“再开一个从未试过的开关”替代假设。
