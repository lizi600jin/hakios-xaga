## 五、这一轮（MFG0 probe）作为第一个按新规程的例子

我刚发的 `HANDOFF-TO-CODEX-2026-11-13-1815.md` 是按旧格式写的。补一份元信息：

### 我的假设

> **MFG0（`0xEB8`）在健康机上一直开着（`0xC000224D`），而我们从来没碰过它。
> 如果它在我们这里是关的，GPU 的 AXI 主控域就没有 master 身份，下游访问会被静默丢弃 ——
> 这能解释「`debug_top` 卡 `0x1b` + MCU 零执行 + 无 fault」这个组合。**

### 支持证据

- `grep -n "0x0eb8\|MFG0" hakios.mali610.c` → **零命中**（驱动从未引用）
- `grep "0xeb8\|MFG0" trial-689-mali.txt` → **零命中**（日志从未出现）
- 健康机基线：`/tmp/xaga-r54/docs/GPUEB.zh-CN.md:460-530`（三次快照全一致）
- 偏移在 `gSpm` 4KB 窗口内（`0x1C001000 + 0xEB8 = 0x1C001EB8`），不在禁读列表

### 反证条件（什么会推翻它）

1. **读到 `0xC000224D`** → MFG0 是开的，假设直接作废
2. 读到关，但读的时机不对（我们没在渲染，健康机是在渲染时读的）→ **弱证据，不能判死**
3. `skipprot` 那条先跑成功 → 说明根因在别处，MFG0 只是巧合

### 我漏考虑的可能性（请补刀）

1. **`MFG0` 可能不由 SPM 控制**（它是常驻域，由 bootloader 直接开），
   那我们读到 `0xC000224D` 是"正常"，读到关是"bootloader 没做"，两种情况处理不同
2. **读 `0xEB8` 可能挂总线**（如果 MFG0 真的没电，读它自己的控制字可能不返回）
   —— 概率低（`0xEBC` 我们读了几百次没问题），但值得执行者判断
3. **健康机的 `0xC000224D` 可能是 Linux scpsys 写的，不是 bootloader** ——
   如果那样，裸机 XNU 就不可能复现这个状态

### 替代方案

如果 MFG0 是开的 → `mali_skipprot=1`（更正版，不用 `continue`）→ 段加载顺序 → 换固件

# 附录 A：2026-11-13 执行者对本轮总控的方法性判决（原文保留）

本轮主控（DSH）在离线反汇编中被执行者纠正 **7 处事实错误**。执行者被要求指出其中哪些属于
**方法性问题**而非一次性疏忽，回答如下（未做美化）：

## A.1 三类方法性问题

### 第一类：位域和常量没有统一机械核算

> RASR、CCR、移位编号、MOVT 连续出现同类错误，不能再归为独立手滑。规程应要求：
> **字段解码附权威定义和脚本算式，算完再解释。**

落实情况：
- 本轮 RASR 的 S/C/B 位置（应 bit18/17/16，我写成 16/17/18）
- CCR 的 DC/IC 位（应 bit16/17，我写成 17/16）
- `LSLS #n` 的源位（应 `31−n`，我写成 `32−n`）
- `movt r1,#0x101` 的值（应 `0x01010000`，我写成 `0x00010100`）
- `0x01010000` 的拆解（我编了"1.1"，实际高低半字是 `0x0101`/`0`）

**新规程条款**：任何位域/常量结论，必须在同一段文字里给出
(a) 权威定义的出处，(b) 可复跑的算式或脚本，(c) 算出来的原始数值。
三者缺一，该结论只能写成"待核"，不能进结论区。

### 第二类：用局部扫描证明全局行为

> 直接调用不代表没有上游门控，直接地址引用不等于所有写者，相同 offset 不证明寄存器别名。
> 报告必须注明扫描范围、路径条件和未覆盖的间接访问，限制使用"全部、唯一、必然"。

落实情况：
- "47 个调用点不受 mask 管" → 实际每个调用点自带门（`0x10000f6` 等 5 处 `lsls`+`bmi`）
- "只有 4 处引用 0x202bbd0" → 只覆盖直接构造地址的指令，`add`/`ldr` 间接访问未扫
- "0x3034 就是 GPU_STATUS" → 同 offset 不等于同寄存器

**新规程条款**：写"全部/唯一/必然"必须同时写清扫描的**指令类型范围**和**已知未覆盖情形**。
默认写法是"在 X 范围内发现 N 处，未覆盖 Y"。

### 第三类：把必要条件升级成充分条件，尤其过度解释阴性

> non-cacheable 排除了一个缓存环节，却不证明写事务完成。规程应强制区分：
> **执行指令 → 发出请求 → 翻译/总线完成 → 内存可见 → AP 采样**；
> 每条定位结论先写一个仍符合现象的反例，排除后再升级。

落实情况：
- "版本字没变 ⇒ 固件没执行到" → 反例：执行到了但 store 在 AS0 翻译/总线失败，
  fault 进 `SCB->CFSR` 不进 `AS_FAULTSTATUS`，我们看不到。
- "non-cacheable ⇒ 一定能读到" → 反例同上。

**新规程条款**：五段链条（执行→请求→翻译→可见→采样）必须逐段标注"已证/未证"。
**阴性结论在写成结论之前，必须先写一个仍能解释该现象的反例**；写不出反例才能升级。

> 任何形如"X 不存在 / X 没有发生 / X 就是这个意思"的结论，
> 必须先在旁边写出**至少一种"X 存在但我看不到"或"X 存在但语义不同"的可能**，
> 并说明排除它的证据。写不出排除证据的，只能写"未观测到 X"。

三个具体检查点：

1. **可见性**：我看到的层级和它发生的层级是同一个吗？（缓存 / 总线 / 翻译）
2. **存在性**：读回 0 可能是"不存在"、"被忽略"、"需要前置条件"三种，分得开吗？
3. **语义**：同名/同 offset 的东西一定是同一个吗？（编译期常量 vs 硬件寄存器）
