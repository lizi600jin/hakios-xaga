# 最早的可被 AP 看见的写，是 `0x1002fd6`（2026-11-14 00:45）

**手机零访问。纯静态分析，扫描器已修正两次。**

---

## 1. 问题

我们所有能观测的字，都是固件跑到很后面才写的东西（版本字 `0x1003012`、JOB IRQ `0x100301c`）。
"固件取指成功了吗"这个最基础的问题，现有观测答不了。

**要找的**：复位入口 `0x10018ec` 之后，**最早一条落在"AP 能读且不经 D-cache"地址上的写**。

---

## 2. 方法

用 capstone 的 `regs_access()` 做**寄存器失效跟踪**（不是简单的 movw/movt 配对）：

- 遇到 `movw rX,#imm` 记录低位；
- 遇到紧随的 `movt rX,#imm` 合成完整常量；
- **任何对 rX 的其它写入都清掉记录**（这一点是关键，见 §5）；
- 遇到 `str*` 且基址寄存器持完整常量时，记录目标地址。

全代码段 22080 条指令，得到 616 条"到常量地址"的 store。

---

## 3. 结果：共享区写入只有 7 处

| 指令地址 | 目标 | 说明 |
|---|---|---|
| `0x10001ce` | `0x04002000` | CSG 控制块（在 `0x10001b4` 那个块里） |
| **`0x1002fd6`** | **`0x04000018`** | **glb_control +0x18 ← 启动路径上最早** |
| `0x1003012` | `0x04000000` | glb_control.version（发布点） |
| `0x1009010` | `0x04002000` | 运行期 CSG |
| `0x10092ba` | `0x04002000` | 运行期 CSG |
| `0x10096ea` | `0x04002000` | 运行期 CSG |
| `0x1009d50` | `0x04002000` | 运行期 CSG |

`0x10001ce` 在程序序上更早，但它在 `0x10001b4` 那个分支块里，**不在从复位入口到发布的直线上**
（那条分支判 `r8` 的位，冷启动不一定走）。

---

## 4. 结论

**从 `0x10018ec` 到 `0x1002fd6` 之间，固件只写这三类地址：**

| 类别 | 范围 | AP 能看吗 |
|---|---|---|
| PPB | `0xE000xxxx` | ❌ 私有，AP 读不到 |
| sec2-4 数据 | `0x20xxxxxx` | ⚠️ 能读，但 **write-back 且 D-cache 已开** |
| MCU 外设窗口 | `0x40xxxxxx` | ❌ 且 AS0 里 L1 table unset |

**没有一条落在 Non-cacheable 的共享区（`0x04000000`）。**

→ **在现有页表与内存属性配置下，无法区分"没取指"和"取了但停在 `0x1002fd6` 之前"。**

这是一个**否定性结论，但它是可用的**：它说明下一轮不能再靠"读某个字"来回答这个问题，
必须引入新的观测手段（MCU 的 ITM/DWT 追踪、或让固件更早写共享区）。

---

## 5. 扫描器修正记录（两次，都是同一类错误）

### 第一次：`0x1000280` 假阳性

初版扫描器报告 `0x1000280 -> 0x04002000  str.w fp,[r0,#0x100]`，我一度以为找到了早期检查点。
实际指令序列：

```
0x1000262  movw r0, #0x2000
0x1000266  movt r0, #0x400       ; r0 = 0x04002000
...
0x100027c  movt r0, #0x4002      ; r0 = 0x40020000   ← 寄存器被重用了
0x1000280  str.w fp, [r0, #0x100]  ; 实际写 0x40020100
```

扫描器把**上一个** movw 的低位和**这一个** movt 拼在一起，跨了寄存器重用。
→ 真实地址是 `0x40020100`（外设窗口），不是共享区。

### 第二次：小地址噪声

修正前的结果里还有 `0x370`、`0x394`、`0x8f5`、`0x966` 这类地址 —— 同样是跨寄存器重用的残留。

### 两次的共同点

**我相信了扫描器的输出，没有核对实际指令序列。** 这和附录 D 记的第五类错误是同一个形状：
把工具的输出当成了事实。

→ 这条应加进附录 A 的第一类：**扫描结果必须抽样回到指令级核对，不能直接引用。**

---

## 6. 这条结论的边界

1. **只覆盖"到常量地址的 store"**。如果某处用 `add`/`ldr` 从内存取地址再写，本扫描看不到。
   但 `0x1002fd6` 之前那段代码里没有 `ldr` 出外部地址再写的模式（已抽查 `0x10025xx-0x1002fxx`）。
2. **`str` 之外的写没扫**：`stm`、`strd`、`strb`、`strh` 已包含（用 `startswith('str')`），
   但 `push`/`stmdb` 之类没有。它们只写栈（sec2/3/4），不影响结论。
3. **"AP 能读"只考虑了内存属性**，没有考虑 AS0 翻译是否成功。
   如果 MCU 的 `0x04xxxxxx` 访问不走 AS0，那结论更强；如果走，结论不变（共享区仍然能读）。


---

## 7. 补做：`ldr` 从内存取值再写（间接寻址）的检查

§6 的第 1 条边界说"如果某处用 `ldr` 从内存取地址再写，本扫描看不到"。这一条我已经补做。

**方法**：在 `0x10018ec..0x1002fd6` 窗口内找所有 `ldr rX,[...]` 且 6 条指令内出现
`str [rX]` 的位置，共 **24 处**。其中 18 处是 `ldr rX,[pc,#imm]` 的字面量池加载，
解析字面量得到目标地址：

| 目标 | 数量 | 类别 |
|---|---|---|
| `0x40022000` / `0x40022004` / `0x40022010` / `0x40003030` | 4 | 外设窗口 |
| `0xE000ED24` / `0xE000ED84` / `0xE000EF50` / `0xE000ED14` / `0xE000EF68` / `0xE000EF5C` / `0xE000EF70` / `0xE000EF58` / `0xE000ED0C` | 13 | PPB |
| `0x02000000` | 1 | sec2（write-back） |

**没有一个是共享区 `0x04000000-0x04094000`。**

剩余 6 处是 `ldr rX,[rY,#imm]`（真间接），需要数据流追踪才能定值。
它们都在 `0x1002a34..0x1002f76` 之间，而这一段已经被 §3 的常量扫描覆盖过
（该段所有 store 的目标都是常量）。抽查 `0x1002d54 → 0x1002d66`：

```
0x1002d54  ldr r1, [r0]        ; r0 = 0x04002000, 所以 r1 = *0x04002000
0x1002d56  str r1, [r2]        ; r2 = 0x0202c78c
...
0x1002d66  str r0, [r1]        ; 注意 r1 在这里已经被 0x1002d5e 重载成 0x0202c790
```

→ `0x1002d66` 写的是 `0x0202c790`（sec2），不是共享区。

**结论不变，而且现在覆盖了间接寻址这条路径。**

## 8. 6.1sol 的两条缺口，都成立（00:55）

### 缺口一：我把"共享区只有七处写"说得太满

它指出 `0x1002ff2` / `0x1002ff4` / `0x1002ff8` 也是共享区写，我的扫描漏了。
**核实成立。** 那三条用**计算基址**：

```
0x1002fce/0x1002fd2  r0 = 0x04000000
0x1002fea  r6 = r3 + r3*4
0x1002fee  r6 = r0 + r6<<5        ; = 0x04000000 + r3*0xa0
0x1002ff2  str r4,[r6,r7]         ; 共享区
0x1002ff4  str r4,[r6,r5]         ; 共享区
0x1002ff8  str r1,[r2,r6]         ; r2 = 0x04000000+0x1040，每组 +0xa0
```

我的常量地址扫描**只能**看见 movw/movt 直接构造的目标，看不见 `base + index*stride`。

→ 它们执行在 `0x1002ff2..0x1002ff8`，**晚于 `0x1002fd6`**，所以不构成更早的检查点。
→ 但这条证明**我的扫描不是穷举**，"只有七处"这个说法要撤回。

### 缺口二：缓存时序不能统一按"已开启"处理 —— 这一条我核错了

它说 `0x1003126` 的 `push {r4,r5,r7,lr}` 发生在 D-cache 开启**之前**，
会把返回地址写到 `0x0203effc`。

我核了调用顺序：

```
0x1001922  bl 0x1003126      ; MPU 编程，其中 push 写栈到 0x0203effc
0x100192a  bl 0x10019e2      ; 开 I-cache
0x100192e  bl 0x1001a2a      ; ★ 这个函数一次做完两件事
```

而 `0x1001a2a` 函数体是：

```
0x1001a2a  push {r4}                    ; 又是栈写
0x1001a36..0x1001a4e                    ; 用 CCSIDR 循环做 cache invalidate
0x1001a54  ldr r0,[CCR]
0x1001a58  orr r1,r1,#0x10000           ; bit16 DC = 1  -> 开 D-cache
0x1001a5c  str r1,[r0]
0x1001a66  pop {r4}
0x1001a68  bx lr
```

**我之前的 §4 说"D-cache 已开"是对的**（`0x100192e` 这次调用就开了），
但**我在算"最早可见写"时把整个窗口都当成 D-cache 已开**，而 `0x1001922` 那次
`bl 0x1003126` 的栈写发生在 `0x100192e` **之前** —— 那时 D-cache 还是关的。

→ 所以 `0x0203effc` 的那个栈写在**理论上**是直写内存的。
→ 但它不是可用的检查点，理由有三：
  1. 栈地址 `0x0203effc` 在 sec4（`0x203f000-0x2040000`），这一页是**栈**，
     后续会被大量覆盖，前后值无法区分；
  2. 该值（返回地址高半字）是 ROM 常量性质的值，不是"固件活动"的独特指纹；
  3. 它在 `0x0203effc`，而我们读 sec4 是 cacheable 映射，读之前要 invalidate 整个区，
     而 invalidate 会把后续写入一并丢弃。

**结论**：它不构成检查点，但我的"统一按已开处理"这个简化确实不严谨。
