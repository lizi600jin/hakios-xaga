# fwlog 通道补丁草稿（2026-11-13 20:25，未落地）

**状态：草稿。驱动源码零改动，手机零访问。** 等 6.1sol 的 A/B/C 判决后再决定是否实现。

---

## 1. 要解决什么

固件有 47 个 printf 调用点，全部汇到 `0x100971e` 的 fwlog 环。启用条件是 sec0 的四个字
（`0xb0` size / `0xb4` insert 地址 / `0xb8` extract 地址 / `0xbc` data VA）**全部非零**。
映像里四个字全是 0，所以 `0x1002f4c` 的 `beq` 每轮都跳走，`0x1002f92` 把状态清零，通道从未启用。

补上这四个字，固件就会把自己的 log 写进我们管理的内存。**这是 17 轮里第一个能拿到"固件自己说的话"
的通道。**

---

## 2. 布局（已核算，无新页表）

| 项 | VA | 大小 | 属性 |
|---|---|---|---|
| 环数据 | `0x040A0000` … `0x040B0000` | 16 KB（4 页，对齐 kbase `fwlog` 的 `num_pages=4`） | `IDX_NC` + `PTE_PAGE` + `PTE_AF` + `PTE_RW`（照抄 sec9） |
| insert u32 | `0x040B0000` | 4 B（独占 1 页，省事） | 同上；初值 0 |
| extract u32 | `0x040B1000` | 4 B | 同上；初值 0 |

**为什么不需要新页表**：`0x4000000` 与 `0x40A0000` 的 L0/L1/L2 索引完全相同（`0,0,32`），
只有 L3 索引不同（0 vs 160）。sec9 已经把 L2=32 的 L3 表建出来了，所以只需在
**已有 L3 表**里写 6 个 leaf（160..163 环，256 = `0x40B0000`，257 = `0x40B1000`）。

`gPtCount` 在 692 实测是 **9**，上限 `MALI_PT_MAX=512` —— 余量充足，而且这条改动根本不消耗。

## 3. 四个字怎么填

| sec0 偏移 | 值 | 语义 |
|---|---|---|
| `0xb0` | `0x4000`（16384） | 环字节数；固件用 `size-1` 做掩码，**必须是 2 的幂** |
| `0xb4` | `0x040B0000` | 一个 u32 的 **VA**，该 u32 存 insert 偏移（固件自己维护） |
| `0xb8` | `0x040B1000` | 一个 u32 的 **VA**，该 u32 存 extract 偏移（host 读完后推进） |
| `0xbc` | `0x040A0000` | 环数据的 **VA**（直接是 VA，不是指针） |

**`0xb4`/`0xb8` 是"地址的地址"**，这一点已由固件反汇编钉死：

```
0x100972c  ldr r2, [r6,#0x18]   ; r2 = extract 槽位
0x1009730  ldr r2, [r2]         ; 二次解引用，取到真正的偏移
```

## 4. 实现步骤（按依赖顺序）

1. `mem_alloc(&gFwLogRing, 4 * PAGE_SIZE)` —— 复用现成函数，它内部走 `mem_alloc_low`/`mem_alloc_high`。
2. `mem_alloc(&gFwLogIdx, PAGE_SIZE)` —— insert/extract 各占页首 4 字节。
3. 两处 `mem_flush()`。
4. 对 6 个 VA 逐个 `pt_map(gMcuRoot, va, mem_pa(...), leaf)`：
   ```c
   leaf = PTE_PAGE | PTE_AF | PTE_UNPRIV | ((uint64_t)IDX_NC << 2);
   if (!gMaliPtVendor) leaf |= PTE_NG | PTE_SH_OS;
   ```
   **不要加 `PTE_XN`**（数据页，但固件也没要求；加了无害，留着不动更省事）。
   **不要加 `PTE_RDONLY`** —— 固件要写。
5. 写 sec0 四个字：
   ```c
   volatile uint32_t *log = (volatile uint32_t *)sect_at(0ull);
   log[0xb0/4] = 0x4000;
   log[0xb4/4] = 0x040B0000;
   log[0xb8/4] = 0x040B1000;
   log[0xbc/4] = 0x040A0000;
   flush_all_sections();
   ```
6. 启动后读取，用 kbase 的 wrap 算法（`mali_kbase_csf_trace_buffer.c:479-513`）：
   ```
   insert = *insert_va; extract = *extract_va;
   if (insert >= extract) 搬 [extract, insert)
   else                   搬 [extract, size) + [0, insert)
   *extract_va = 新位置;
   ```
7. 日志打印：**只打可打印字节，遇到非可打印就十六进制**。环里可能是任意字节，直接 printf 会污染串口。

## 5. 三个必须避开的地雷

### 5.1 `continue` / 提前 `return`
`load_firmware()` 的 `offset += esize;` 在循环尾部（驱动 `:1210`）。任何提前跳出 = **死循环**。
这个项目因此砖过 3 次板。**新代码只做"多加一个映射"，不改 `offset` 的推进，不插入任何 `continue`。**

### 5.2 层数不清零
`pt_map()` 要求 L0→L3 的中间表存在。sec9 已建好 L2=32 的 L3，但**如果未来某次改动让 sec9 没被加载**
（比如固件换了、段表变了），`pt_map` 会自己建表 —— 那是安全的（它内部检查 `table[index] & 1`），
只是消耗 `gPtCount`。**不要假设"一定已存在"去做裸写数组。**

### 5.3 write-combining / cache
环是 `IDX_NC`（non-cacheable）。CPU 侧 `mem_alloc` 出来的页仍然是 **cacheable in kernel_map**
（驱动 `:744-760` 那段注释已经为此踩过坑，导致三次复位失败）。
所以读环之前必须 `FlushPoC_DcacheRegion()`（或 `invalidate`），否则读到的是 CPU 缓存里的旧值。
`mem_flush()` 只做 clean，**读之前要 invalidate** —— 这是这条路径和现有 `read_witness()` 的差别，
`read_witness()` 的共享段也是 NC，但它读的是很少变的 marker，我们读的是 MCU 高频率写的环形区。

## 6. 判据（三条，互斥且穷尽）

| 观察 | 结论 | 强度 |
|---|---|---|
| 环里有任何字节 | 固件执行到了某个 printf 调用点，**内容直接说它停在哪** | 最强 |
| `insert` 前进了但内容是乱码/看不懂 | CPU 确实在**取指并 store** —— 17 轮里从未有过的正向证据 | 强 |
| `insert` 恒 0 且 `size`/`data_va` 保持我们写进去的值 | 连复位后最早的 printf 都没到（`0x1002f2a` 之前只有 MPU/cache/栈初始化） | 中等（比现有所有阴性判据都强） |

**第 3 条为什么比现有判据强**：`0x1002f2a` 在复位后非常早 —— 前面只有 `cpsid`、两条 MMIO store、
`msr psp/control`、MPU 编程、cache 使能、`cbz` 跳过 PROT。跑到 `0x1002f2a` 意味着核心至少执行了
**几十条指令**。而 `insert==0` 说明连第一条 printf 都没执行到。这与"根本没取指"是可区分的。

## 8. 补充（20:35）：fwlog 还有第二道门 —— `0x3020` bit17 的 host→MCU 通知

我刚从固件反汇编里挖出来的，会改变启用步骤，**如果 6.1sol 的判决在这之后才到，以本节为准**。

`0x10093d6` 那个函数（fwlog 启用检查的入口）做三件事：

```
0x10093e0  bl  #0x1006c34            ; ★ 先调这个
0x10093e4..0x10093f6                 ; 把 [0xac8..0xad4) 这一段清掉（24 字节）
0x10093fa  ldrb r0, [0x202c7ac]      ; 配置是否生效
0x1009404  cmp  r0, #1
0x1009406  bne  #0x100942c           ; 没生效 → 跳过
0x1009410  ldr  r0, [0xac8]          ; ★ 第一道门
0x1009412  cbz  r0, #0x1009420       ; 为 0 → r0 = 0
0x100941c  ldr  r0, [0xacc]          ; ★ 第二道门：enable mask
0x1009422  str  r0, [0x202c7a8]      ; 把 mask 交给 writer
```

**`0x1006c34` 是什么**：

```
0x1006c3c  ldr  r2, [0x202c8fc]      ; 一个"要不要通知"的标志
0x1006c46  cbz  r2, #0x1006c62       ; 为 0 → 直接返回
0x1006c48  ldr  r2, [0x40003020]     ; ★ 读 MCU 控制块
0x1006c4a  tst  r2, #0x20000         ; ★ bit17
0x1006c4e  beq  #0x1006c48           ; 等它置位（无界轮询！）
0x1006c54  str  #0x20000, [0x40003024]  ; 写 clear
0x1006c56  str  r0, [0x40003030]     ; ★ 把参数写进 0x3030
0x1006c58  ldr  r0, [0x40003020]     ; 再读
0x1006c5a  tst  r0, #0x20000         ; 再等一次
0x1006c5e  beq  #0x1006c58           ; 又一个无界轮询
```

`0x40003020` 就是主机侧同一个 `0x3020`。**692 实测 `0x3020 = 0x600`**（bits 9、10），
bit17 = 0。

所以：**如果 `0x202c8fc` 那个标志非 0，固件会卡在 `0x1006c48` 的轮询里** —— 而 bit17 永远不
会由我们自己置位。这是一个**可能的新死锁点**，而且它比 fwlog 更早（在启用检查的第一步）。

两个未知：
1. `0x202c8fc` 在映像里初值是什么？（它在 sec2 的零填充尾巴里吗？）
2. `0x3020` bit17 的语义到底是什么？主机侧 692 从未写过它，读到 `0x600`。

**这直接影响实现**：如果第一道门就卡住，那么"填 fwlog 四个字"根本轮不到执行。
必须先确定 `0x202c8fc` 的初值，否则这一轮可能又是白跑。

## 10. 定论（20:45）：`0x202c7a8` 那道门只管 3 个调用点，47 个直连 writer 不受它管

我按"谁调用谁"把两段分开了：

| 入口 | 调用点数 | 说明 |
|---|---|---|
| `0x10096f8`（带日志级别检查 `ldrb 0x202c7a8` → `bxpl lr`） | **3** | `0x1003414`、`0x1003958`、`0x10039fa` |
| `0x100971e`（writer 本体，直接进） | **47** | `0x1000076`、`0x100033a`、`0x100093a`… 遍布全代码段 |

所以：

1. **47 个位置不受 `0x202c7a8` 影响**，它们直接进 writer。
2. writer 自己的第一件事（`0x100972c`）是读 `[0x202bbd0+0x18]` 这个**指针**取 extract —— 前提是
   `0x1002f4c` 那道门（`0xb0..0xbc` 四个字全非零）已经通过、`0x202bbd0` 被正确填充。
3. **结论：只要填对 `0xb0..0xbc` 四个字，47 个调用点里任何一个被执行到，都会写进环。**

executor 的反证（"启动路径在 `0x1002f7a-0x1002f84` 主动把 `0x202c7ac` 置 1"）成立，
但它把 `0x202c7a8`（日志级别，管 3 个点）和 `0xacc`（trace enable mask，交给 writer 的那份）
当成同一层了。实际是三层：

```
第一层 0x1002f4c  : 0xb0..0xbc 全非零  -> 0x202bbd0 被填好（否则清零、通道死）
第二层 0x1002f6a  : 若 [0xac8]!=0，把 [0xacc] 抄到 0x202c7a8   （启动路径自己做）
第三层 0x10096f8  : 只有 3 个调用点走这里，检查 0x202c7a8 的 bit1
```

**实现只需要保证第一层。** 第二三层是固件自己的事，且只影响 3/50 的调用点。

## 12. 更正 §10：executor 又对了 —— 每个调用点都有**自己的**门，不能只看 writer 本体

我 §10 的"47 个直连、不受 mask 管"是错的。实际结构是：**门在每个调用点自己身上，不在 writer 入口**。

第一条反例（`0x1000076` 那个调用）：

```
0x10000ec  movw r0,#0xc7a8 ; movt r0,#0x202    -> r0 = 0x202c7a8
0x10000f4  ldrb r0,[r0]                         -> r0 = 日志类别字节
0x10000f6  lsls r0,r0,#0x1b                     -> 左移 27，把 bit5 顶到 N
0x10000f8  bmi  #0x1000070                      -> bit5==1 才跳去调用
0x10000fa  ...                                   -> bit5==0 直接跳过 writer
```

`0x1000070` 才是 `movs r0,#0; mov.w r1,#0x44000; bl 0x100971e`。

**`0x202c7a8` 不是一个"级别"，是一个类别位图。** 我扫出 5 个门，各测不同的位：

| 门地址 | 左移 | 测的位（= 31 − n） |
|---|---|---|
| `0x10000ec` | #27 | bit4 |
| `0x100034c` | #27 | bit4 |
| `0x10006c0` | #26 | bit5 |
| `0x10009f0` | #28 | bit3 |
| `0x1001494` | #29 | bit2 |
| `0x10096f8`（前面那个） | #30 | bit1 |

> 更正：本节初稿把被测位写成 `32 − n`，**错了一位**（6.1sol 21:05 指出）。
> `LSLS #n` 把 bit *i* 移到 bit *i+n*，N 是 bit31，所以 `i = 31 − n`。
> 数值验算：`bit4=0x10 << 27 = 0x80000000`，N=1 ✅

而这 5 个门在冷启动时读到的 `0x202c7a8` 是 **0**（它落在 sec2 零填充尾巴里），
**所以 47 个 writer 调用点在当前实现下一个都不会执行。**

## 13. 因此实现必须多两步（§11 作废）

要让日志真的出来，需要按顺序满足：

1. **`0xac8` 非零** —— 让启动路径（`0x1002f4c` 之后）走到 `0x1002f5e` 那支。
2. **`0xacc` 是要的类别掩码** —— 启动路径在 `0x1002f6a-0x1002f78` 把它抄到 `0x202c7a8`。
3. **`0xb0..0xbc` 四个字非零** —— 让 `0x202bbd0` 被正确填充（否则清零）。

三步里的 (1)(2) 在同一个 `if` 分支里（`0x1002f5a` 的 `cbz r0, 0x1002f7a` 就是判 `0xac8`），
所以**要么一起给，要么一起不给**。

---

## 14. 这让判据变简单了，而不是更复杂

因为现在只有两种可能的失败形态，都可区分：

| 现象 | 含义 |
|---|---|
| `0x202c7a8` 仍为 0 | 固件**没执行到** `0x1002f5e`（`0xac8` 分支）—— 说明更早就停了 |
| `0x202c7a8` 变成我们写的值 | 固件执行到了 `0x1002f6a-0x1002f78` —— **这是"执行了几十条指令"的直接证据** |
| `0x202c7a8` 正确 + `insert` 前进 | 固件跑到了某个 printf —— **最强证据** |
| `0x202c7a8` 正确 + `insert` 不动 | 固件过了初始化但没到任何 printf |

第二条本身就值得一轮：**`0x202c7a8` 被固件从 0 改写成非 0，这是"MCU 真的在跑指令并 store"的
不可伪造证据**，比 witness 桩可靠（witness 换了复位向量，会改变被测对象；这个不改变任何控制流）。

**这是本轮最重要的结论**：即使 fwlog 一条日志都没输出，只要 `0x202c7a8` 从 0 变成我们写的值，
就证明核心在取指。而这件事**只靠填 `0xac8`/`0xacc` + `0xb0..0xbc` 就能测**，不需要额外硬件。

## 16. 追加更正（21:30）：writer 的真实追加路径在 `0x100e98c`，我引的 `0x1009792` 是错的

6.1sol 指出 `0x01009792–979a` 是**读旧记录到栈**，不是追加方向。我核了，它对。

真实结构：

```
0x10097d8  r0 = sp+0x10
0x10097da  bl 0x100e98c        ; 追加 8 字节（payload + cycle counter）
0x10097de  r0 = sp+8
0x10097e0  bl 0x100e98c        ; 再追加 8 字节
0x10097e4  dsb
0x10097e8  ldr r0,[r6,#8]      ; 取新 insert
0x10097ea  ldr r1,[r6,#0x14]
0x10097ec  str r0,[r1]         ; ★ 这才是"发布 insert"
0x10097f0  cmp r7,r0
0x10097f2  beq 0x10097fe       ; 期间变了就重试
```

而 `0x100e98c` 才是追加助手：它算 wrap、`subs r0,#1` / `cmp r0,#8` 做**有界检查**，
再用 `0x100ee3e`（memcpy）写两次（跨环尾时分两段）。

加上它前面 `0x1009734-0x974a` 反复读 `0x40003090`/`0x40003094`（MCU MMIO cycle counter）等一致 —— 
**writer 里确实有等待和 MMIO 访问，进去就可能成为新的阻塞点。** 这正是 6.1sol 判 C 的核心论据。

所以判 C 接受，完整 fwlog 通道**不在下一轮做**。

## 17. 若将来仍要做，必须按 6.1sol 的 (c) 修正（已记录，不实施）

1. `4 * PAGE_SIZE` 在 16K 页下是 **64KB**；16KB 应用 4 个 `PT_LEAF_GRANULE`，且每叶用
   `mem_pa(m, offset)` 重新求 PA（不能假设跨宿主页物理连续）。
2. `[0x40A0000,0x40B0000)` 是 64KB；16KB 右端是 `0x40A4000`。`0x40B0000`/`0x40B1000` 的 L3
   索引是 **176/177**（我原来写 256/257，差 80）。
3. sec9 实际**含 `PTE_XN`**；"照抄 sec9 但不加 XN"不是同一属性。NC index 在 bits4:2。
4. CPU 侧映射仍是 cacheable，GPU 的 `IDX_NC` 不改变它；`mem_flush()` 的实际语义要按驱动
   `:768-782` 核，不能笼统说"只 clean"。
5. 新区域必须登记到 `gSect` 或被独立管理（`sect_at()`/`flush_all_sections()` 只遍历 `gSect`）。
6. 新增逻辑放在全部原段装载**之后**的独立步骤，保留 `offset += esize`。
