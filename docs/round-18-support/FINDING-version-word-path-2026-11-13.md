# 关键结论（22:10）：版本字判据是可靠的；固件没走到它，而不是我们看不到它

**手机零访问。这是纯离线反汇编的结论。**

---

## 1. 版本字的写入点，我定位到了

```
0x1002fce  movw r0, #0      ; movt r0, #0x400   -> r0 = 0x04000000（glb 接口基址）
0x1002fd6  str  r1, [r0, #0x18]
0x1002fdc  r2 = r0 + 0x1040                    ; 0x04001040
0x1002ff8  str  r1, [r2, r6]                   ; 填 CSG 输入块，步长 0xc，8 次
0x1003008  movs r1, #0
0x100300a  dsb  sy                             ; ★ 发布前的屏障
0x100300e  movt r1, #0x101                     ; r1 = 0x01010000
0x1003012  str  r1, [r0]                       ; ★★ 写 0x04000000 —— 就是 version 字
0x1003014  mov.w r0, #-0x80000000
0x1003018  dsb  sy
0x100301c  str.w r0, [r8, #0xff0]              ; 发 JOB global IRQ
```

**这正是驱动已经在监视的那个字。** `hakios.mali610.c:3659` 写哨兵 `0xff5aa5f0`，
`3962` 之后读回。692 的读数（日志第 238 行）：

```
mali: version word 0xff5aa5f0 (untouched; no firmware version published) trial 692
```

---

## 2. 这个判据为什么是可靠的 —— 缓存属性已核对

- `0x04000000` 落在 **MPU region 4**（`0x04000000`，64 MB，RASR `0x110c0033`）。
- 按正确位布局（bit18=S、bit17=C、bit16=B）：`TEX=001 C=0 B=0 S=1`
  → **Normal, Non-cacheable, Shareable**。
- MCU 的这个 store **直接到内存**，不经过它自己的 D-cache。
- AP 侧读共享段用 `FlushPoC_DcacheRegion`（clean+invalidate），能读到。

→ **不存在"写了但看不到"的可能。** 版本字保持哨兵，就是**固件真的没执行到 `0x1003012`**。

---

## 3. 这句话把搜索范围缩到了哪里

`0x1003012` 之前必须走的路径：

```
0x10018ec  复位入口
    ↓  MPU 13 区、cache 使能、cbz 跳过 PROT
0x1002aec  主初始化（那一大段）
    ↓
0x1002f2a  fwlog 初始化（判 0xb0..0xbc 四个字）
    ↓  仅 232 字节直线
0x1003012  写版本字   ← 从未到达
```

所以固件停在这 5926 字节代码路径的**某处**，且不是"最后的发布动作失败"。

**结合 17 轮的观测**：`AS_FAULTSTATUS=0`、`GPU_FAULT_STATUS=0`、`MCU_STATUS=1`、
`debug_top=0x1b`、witness 桩（绕过全部初始化）也不动。

---

## 4. 这条结论的边界（必须写清楚）

1. **它不定位停在哪。** 只排除"已经跑完初始化但发布失败"这一种。
2. **它不解释为什么。** 时钟、总线、复位、固件本身的早期指令，都可能。
3. **它依赖一个假设**：`0x04000000` 的写入确实不经 MCU 的 D-cache。
   依据是 MPU region 4 是 Non-cacheable —— 这是固件自己配的，不是我们猜的。
4. **它和"看不到"是两件事。** 我之前几轮里说"版本字没变"时，没有区分这两者；
   现在这个区分由 MPU 属性撑住了：**是没写，不是没看到。**

---

## 5. 这轮副产物：`0x202bbe0` 探针作废

我原本想用 sec2 里的 `0x202bbe0`（镜像初值 1，被 else 分支清零）做检查点。
6.1sol 指出 region 3 是 **write-back**（`TEX=001 C=1 B=1 S=0`），
而且固件在复位早期把 D-cache 打开了（`0x1001a58`，`orr CCR,#0x10000` → bit16 DC）。
→ MCU 对那个字的写会停在它自己的 cache 里，AP 看不到。**方案作废。**

**这个对比正好说明：能用的检查点必须在 Non-cacheable 区（region 4 / region 0），
而版本字就在 region 4 里。**

---

## 6. 追加更正（22:20）：CCR 的 DC/IC 位我也写反了

6.1sol 再次纠正。权威定义（[CMSIS / opencm3](https://arcoslab.gitlab.io/libopencm3/lm4f/html/scb_8h.html)）：

```
SCB_CCR_DC  (1 << 16)   data cache enable
SCB_CCR_IC  (1 << 17)   instruction cache enable
```

固件里的两处：

| 地址 | 指令 | 效果 |
|---|---|---|
| `0x10019f6` | `orr r1,r1,#0x20000` | bit17 → **I-cache 使能** |
| `0x1001a58` | `orr r1,r1,#0x10000` | bit16 → **D-cache 使能** |

我先前把 `0x10019f6` 写成"打开 D-cache"，**错了**。D-cache 由 `0x1001a58` 打开。

**但结论不变**：D-cache 确实在复位早期被打开（`0x1001a58`，在 `0x1001a2a` 那个 cache
invalidate 之后、`0x1001a66` 返回之前）。所以 `0x202bbe0` 探针仍然作废 —— 只是理由那一条
的出处应该是 `0x1001a58` 而不是 `0x10019f6`。

**而 §1-§3 的版本字结论不受影响**：`0x04000000` 在 MPU region 4（Non-cacheable），
无论 D-cache 开不开，那个 store 都直接到内存。

## 7. 自查结果（22:30）：三个盲区中的 (1) 已排除

用 capstone 的 `regs_access()` 逐条核 `0x1002fce..0x1003012` 这 70 字节：

| 地址 | 指令 | 写 r0? |
|---|---|---|
| `0x1002fce` | `movw r0,#0` | ✅（建基址） |
| `0x1002fd2` | `movt r0,#0x400` | ✅（基址 = `0x04000000`） |
| `0x1002fd6` | `str r1,[r0,#0x18]` | — |
| `0x1002fdc` | `add.w r2,r0,#0x1040` | —（只写 r2） |
| `0x1002fee` | `add.w r6,r0,r6,lsl#5` | — |
| `0x1003012` | **`str r1,[r0]`** | — |

从 `0x1002fd2` 到 `0x1003012`，**没有任何指令写 r0**。中间那个两重循环
（`0x1002fea..0x1003006`，8 组 × 8 个 0xc 步长的 str）只动 r2/r3/r6/r1。

→ **`0x1003012` 写的就是 `0x04000000`**，即驱动监视的 version 字。这一条成立。

盲区 (2)：region 编号大的优先，region 4 > region 0，`0x04000000` 由 region 4 决定
（Non-cacheable）。成立。
盲区 (3)：CSG 输入块（`0x04001040` 起，8×0xc）也在 region 4 内，同样可观测；
但它的初值在映像里就非零，区分度不如 version 字。

## 8. 更正（22:40）：`movt r1,#0x101` 得的是 `0x01010000`，不是 `0x00010100`

我算错了 256 倍。正确：

```
0x1003008  movs r1, #0        -> r1 = 0x00000000
0x100300e  movt r1, #0x101    -> r1 = (0x101 << 16) | 0x0000 = 0x01010000
0x1003012  str  r1, [r0]      -> version 字被写成 0x01010000
```

`0x01010000` 的高低半字是 `0x0101` / `0x0000`。

> **撤回**：我曾写"按大/小版本各 16 位拆是 1.1，说明接口版本是另一套编号"。
> 这是编的。`0x0101` = 257，`0x0000` = 0，没有任何明显的 1.1 拆法。
> 具体版本格式必须查接口定义，我没查。

## 9. 6.1sol 的第二条：非缓存 ≠ store 已完成（这一条我接受，并下调结论强度）

它说："non-cacheable 只能排除 MCU 私有 D-cache 滞留，不能保证一次 store 已完成下游翻译和总线写入。"

这是对的，而且我这轮已经吃过同类教训（把"能读到"和"写了"混为一谈）。具体地：

- Non-cacheable 保证**不经过 MCU 的 D-cache**，但 store 仍要经过 **AS0 翻译**（如果 MCU 的
  `0x04xxxxxx` 访问走 AS0）和**总线**才能落到 DRAM。
- 如果 AS0 翻译失败，store 会产生 **BusFault/MemManage**，而那个异常**不会**进
  `AS_FAULTSTATUS`（那是 GPU MMU 的寄存器）—— 会进 `SCB->CFSR`，而我们读不到 CFSR。
- 所以"哨兵未变"有两种解释：**(a) 没执行到 `0x1003012`**；**(b) 执行到了，但 store 在翻译/总线上失败**。

**我把 §3 的结论从"固件真的没执行到"下调为"没有观测到这次 store 成功"**，并把 (b) 列为同等
候选。这与 17 轮里 `AS_FAULTSTATUS=0` 但不排除私有 fault 的整体图景一致。

→ 因此"下一轮反推 `0x1003012` 之前哪一步最可能断"这个提议**前提不足**：我还没有排除
"执行到了但 store 失败"。要排除它，需要一条能看见 MCU 私有 fault 的通道，而目前没有。
