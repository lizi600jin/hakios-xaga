## 0. 先认错：上一版 §5 是错的

我把 `0x150b0000` / `0x050b0000` 当成 SRAM/外设基址去追查了。**它们是 MPU RASR 的属性位域，不是地址。**

我用 unicorn 2.1.4 真模拟了 `0x1003126` 整段（`out/round-18-support/mpu_unicorn.py`），
拿到 firmware 实际写进 `MPU_RBAR`/`MPU_RASR` 的 13 个区域：

| region | base | size | AP | XN |
|---|---|---|---|---|
| 0 | `0x00000000` | 4 GB | `0b000` | 1 |
| 1 | `0x00000000` | 4 KB | `0b101` | 1 |
| 2 | `0x01000000` | 64 KB | `0b101` | 0 |
| 3 | `0x02000000` | 256 KB | `0b001` | 1 |
| 4 | `0x04000000` | 64 MB | `0b001` | 1 |
| 5 | `0x08000000` | 128 MB | `0b001` | 1 |
| 6 | `0x10000000` | 128 MB | `0b001` | 1 |
| 7 | `0x18000000` | 128 MB | `0b001` | 1 |
| 8 | `0x20000000` | 128 MB | `0b001` | 1 |
| 9 | `0x28000000` | 128 MB | `0b001` | 1 |
| 10 | `0x30000000` | 128 MB | `0b001` | 1 |
| 11 | `0x40000000` | 256 KB | `0b001` | 1 |
| 12 | `0xE0000000` | 1 MB | `0b001` | 1 |

`MPU_CTRL <- 0x3`（ENABLE=1 PRIVDEFENA=1）。

**这张表是自洽的**：region 2 覆盖代码 `0x1000000` 且 XN=0（可执行），region 4 覆盖共享区
`0x4000000`（64 MB），region 11 覆盖 `0x40000000` 的外设窗口，region 12 覆盖 PPB。
没有一个区域把代码或数据挡在外面，PRIVDEFENA 又把全特权态兜住。

→ **"MPU 配错导致 MemManage fault" 这条假设不成立，我撤回。**

它的第二个反证（它自己提的）更硬：**691 的 witness 桩绕过了整段 MPU 初始化**（桩从 `0x1000000`
直接开跑，不经过 `0x10018ec`），而 691 一样是什么都没有。所以"这段初始化有问题"无论真假，
都解释不了两轮共同失败。

## 1. 新发现（这是本轮唯一有价值的东西）：固件的日志走 **semihosting**，而我们没有 host 端

固件里所有 printf 的底层是 `0x100f806`：

```
0x100f806  push  {r3,r4,r5,lr}
0x100f808  mov   r4, r0
0x100f80a  strb.w r0, [sp]        ; 字符放到栈上
0x100f80e  mov   r1, sp
0x100f810  movs  r0, #3           ; SYS_WRITEC (=3)，ARM 半主机规范
0x100f812  bkpt  #0xab            ; ★ 半主机调用
0x100f814  mov   r0, r4
0x100f816  pop   {r3,r4,r5,pc}
```

全代码段只有**一处** `bkpt`（`0x100f812`），所有 log/printf 都汇到这里。
`r0=3` 正是 ARM 半主机（semihosting）的 `SYS_WRITEC`。

**半主机要求 host 端在调试器里接管 `BKPT 0xAB` 异常并替固件做 I/O。** 我们这里没有 host：

- XNU 侧没有半主机服务，`BKPT` 在 MCU 上只会变成一个调试事件 / HardFault。
- `grep` 全驱动：没有任何 `fwlog`/`0xb0`/`0xacc` 相关代码 —— **这段日志从来没被读过一次**。

顺带把 fwlog 的结构也确认了（`kbase_csf_trace_buffer.c:283-291`）：

```
type=1  size_addr=0x9c  insert=0xa0  extract=0xa4  data=0xa8  enable=0xac  count=4
```

—— 等等，这是 `firmware trace` 那条。`fwlog` 那条是：

```
type=1  size_addr=0xb0  insert=0xb4  extract=0xb8  data=0xbc  enable=0xacc  count=11
```

`size/insert/extract/data_va` 在**映像里全是 0**，kbase 的做法是运行期
`kbase_csf_update_firmware_memory()` 把 host 分配的 BO 的 GPU VA 写进去
（`mali_kbase_csf_trace_buffer.c:206-220`）。**我们的驱动没做这一步，所以这四个字一直是 0。**

这意味着：**即便固件跑起来、即便它想写日志，写入地址也是 0 —— 会打到 sec0 的向量表上**（当前映射
里 `0x0` 是可写的 r--，`0xb0` 落在 2836 字节数据范围内）。这可能是另一个"看起来什么都没发生"的来源。

## 2. 固件自带的崩溃日志：如果它能跑，它会自己把 R0-R11 + Fault address 打出来

section 0 里有一整块格式化字符串（VA `0x950`-`0xa10`）：

```
'Exception: %s '
'Fault address: 0x%0x '
'R0:  0x%08x R1:  0x%08x R2:  0x%08x R3:  0x%08x\n'
'R4:  0x%08x R5:  0x%08x R6:  0x%08x R7:  0x%08x\n'
'R8:  0x%08x R9:  0x%08x R10: 0x%08x R11: 0x%08x\n'
'===================== CSFFW Oops! =====================\n'
```

以及 R0-R11 的影子寄存器名字 `CSHWIF*`/`ITER_*`、`GPU_FAULTSTATUS=`、`GPU_STATUS=`。

而且向量表确认了这套机制是活的：

| 向量 | 值 |
|---|---|
| Initial SP | `0x02040000` |
| Reset | `0x010018ed` |
| NMI / HardFault / **MemManage / BusFault / UsageFault** | **全部 `0x010019b1`**（同一个 handler） |

`0x10019b0` → 取 MSP/PSP → `bl 0x10021ac`。`0x10021ac` 里有 `%s`、有 `0xad4` 的 8 项跳表、
有 `0x202c218` 的序号表 —— 这是一个**完整的异常分派 + 打印**框架。

**这套 code 一旦执行，就会往 semihosting 打一条完整现场。**
所以我们不是"没有观测手段"，是**观测手段在固件里面，而 host 端没接**。

## 3. 三条路线，我按 ROI 排序（请 6.1sol 打分）

| 序 | 做什么 | 代价 | 能证伪什么 | 我的置信 |
|---|---|---|---|---|
| **A** | **给 `fwlog` 环填上真实地址**（size/insert/extract/data_va + enable mask），让固件的 `SYS_WRITEC` 有地方可落；再做 host 端读环 | 一轮刷机 + 少量代码 | 如果拿到 `CSFFW Oops!` 或任何字符串 → **固件执行了**，且能直接读出停在哪、R0-R11 是什么。阴性也有意义：环是空的说明连 putchar 都没到 | **高** |
| B | 在 XNU 里实现 `BKPT 0xAB` 的 host 端接管（真正的 semihosting 服务） | 大（要挂 MCU 的 debug 异常路径，我们没有这条路） | 同 A，但更彻底 | 低（成本不划算，A 已经能拿到写入的字节） |
| C | 回到"第一个 store 写 `0x40022000` 但 AS0 没映射"那条（上一版 §4） | 零成本 | 见下 | 中 |

关于 C，补一条上一版没说清的证据：固件里 `movw/movt` 构造的地址中，落在共享区的是
`0x04002000`（11 处）和 `0x04000000`（1 处，`0x1002fd2`）；落在 `0x40000000` 附近的是
`0x40022000`/`0x40022004`/`0x40003034`/`0x40003030`/`0x40022010`。
**`0x40002000`（低半）和 `0x40022000`（高半）不是一回事**，前者在共享区 VA 内、后者在外设窗口。
这更加支持"MCU 访问外设/PPB 不走 AS0 翻译"，也就是上一版 §4 的 (i)。

## 4. 我现在的判断（供你反驳）

1. `skipprot` 应当关闭 —— 机制上可证明无影响，不再占用真机轮次。
2. 上一版 §5（MPU fault）撤回。
3. **A 是 17 轮以来第一个"能拿到固件自己说的话"的通道。** 之前所有轮次都在猜固件状态；
   这条路线让固件自己报。即使它仍然什么都不说，那也是"连 putchar 都没执行到"这个强得多的事实。
4. 但 A 有个必须先解决的前提：`0xbc` 里那个 `data_va` 我们要填一个**真实可写的 GPU VA**。
   候选：把 `fwlog` 的 data 区放在共享段 `0x4000000-0x4094000` 内部（8192 字节已映射、已 nc shared），
   比如 `0x4008000` 起 4 页（`fwlog` 的 `num_pages` = 4，见 `trace_buffer.c:129`）。
   **这条路不需要新增内存分配**，只改 sec0 里那 4 个控制字。
