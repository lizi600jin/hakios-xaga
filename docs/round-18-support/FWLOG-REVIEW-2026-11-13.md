# fwlog 最终审查：C，当前不投入下一轮完整通道试验

审查覆盖 `OFFLINE-FINDINGS-2026-11-13.md`、第二版、第四版、`fwlog-patch-draft.md` 及主控后续更正。先前协作规程继续适用。本轮仅静态分析，没有改驱动、构建、执行/模拟固件、访问手机或刷机。以下建议不是已执行的试验。

## (a) C：当前完整 fwlog 方案不值得占下一轮，先停草稿实现

**认可最新方案的正向证据：** 如果 host 仅填写 sec0 配置，未填写内部状态，并且启动前确认 `0x0202c7a8=0`，启动后同步读到它变为预期非零 mask，同时内部 ring 状态匹配预期，则支持 MCU 执行了原生初始化和内存写回。不能再用“没有日志”否定这一正证据。

但同类执行正证据可用**既有、未经改动的固件内存检查点**取得，不必先增加环映射、描述符、类别启用及并发消费。当前真正需要验证的是执行进度，完整日志通道还没有被证明能在现有版本/JOB 完成证据之前给出一条必写记录。因此建议本次停止完整通道实施，保留为后续候选。

## (b) 理由与证据

### 1. 有一个更小的既有检查点

固件内部状态块 `0x0202bbd0` 的七个初始字来自镜像文件数据，实际是：

`[0, 0, 0, 0, 1, 0, 0]`

所以 **`0x0202bbe0` 初值为 1**，不能把整个状态块都称作零填充尾部。

当前原始 sec0 的 `0xb0..0xbc` 全为 0；若执行到 `0x01002f88`，会以 `r0=0x0202bbd0, r1=0x1c` 调 `0x0100ee70`。该函数置 `r2=0` 并进入字节清零循环。因此该路径将把 `0x0202bbe0` 从 1 清为 0。

复核材料：`offline-review-2026-11-13-support/shared-config.txt:25–26`；`disassembly.txt` 中 `fwlog_init_block`、`memclr_28_bytes` 两段。

后续若另行设计试验，可只从 **现有 section 2 的 CPU 映射**观察此字的启动前后值，保持 692 固件配置不变，不新增 MMIO、不改固件字节、不建新 ring。若排除 host 对该字的后续写入并保证缓存同步，1→0 至少是新的 MCU 内存写回正证据；具体归因到哪一条写指令仍需其他写者审计。不变仍不能证明未取指。

### 2. 最新 mask 复制推理成立，阴性定位仍不成立

实际依赖顺序为：

1. `0xb0..0xbc` 全有效，否则跳 `0x01002f88` 清状态。
2. `0x01002f5a–64` 读取 `[0xac8]`；非零时 `0x01002f66–78` 将 `[0xacc]` 复制到 `0x0202c7a8`。
3. 有效描述符路径在 `0x01002f7a–84` 将 `0x0202c7ac` 置 1；无论 mask 是否复制都会执行。**这不是跨“描述符无效”分支的无条件写。**

因此不需要为首次配置额外强制调用 config-apply。冷启动初值为零不能推导运行时恒为零。

但草稿 §14 的阴性结论仍超界：最终 mask=0 只是未采到预期复制/保留结果；mask 正确但 insert 不动也不能推出“未到任何 printf”。类别门、事件是否触发、extract 访问、时间戳读取、缓存可见性及后续状态更新都是独立限制。host 自己填写的 size/data 保持原值，不是固件读过它们的证据。

### 3. 调用图不能替代分支条件

主控已撤回“只有 3 个调用点受 mask 影响”，撤回正确。两个独立反例：

- `0x010000ec–f4` 读 `0x0202c7a8`，`0x010000f6` 左移 27，`0x010000f8` 按 N 跳到 `0x01000070`，再在 `0x01000076` 直接调用 writer。
- `0x0100034c–54` 读同一 mask，`0x01000356` 左移 27，`0x01000358` 跳到 `0x01000320`，再在 `0x0100033a` 直接调用 writer。

均检查 **bit4**；`31-n` 才是左移 n 后移入 N 的源位。反例见 `disassembly.txt:550–579`。本审查不把这两个反例扩张为已经逐一证明所有 47 个调用点的控制流。

### 4. writer 是二进制事件通道，不承诺异常文本或卡点 PC

`0x0100974e` 保存 payload 与 cycle counter；`0x010097d8/97de` 两次调用 `0x0100e98c`，各追加 8 字节。`0x010097e8–ec` 才发布 insert。第四版引用的 `0x01009792–979a` 是读旧记录到栈，不能作为追加方向的证据。

`0x01002f2a` 是初始化块，不是 printf。该初始化之后到 `0x01003012` 写版本、`0x0100301c` 发 JOB IRQ 的直线/循环路径没有直接事件 writer 调用。没有完成所有间接路径的否定证明，但目前缺少“版本发布前必写某事件”的正向证明。

所以有效记录只能定位到对应事件已发布，不能保证它就是最终卡点；任意非零字节也不等于 `CSFFW Oops`。异常诊断仍包含 semihosting，不能由启用 ring 保证其不被触发。

### 5. 是否“同时改两个变量”

不能按字段数量机械计数。ring、counter 和四个描述符是同一个内存通道的依赖项；**是否开启类别输出**则是可以独立控制的行为，启用后会改变类别分支结果并执行额外操作。

尤其 writer 在首次追加前要读取 extract 指针，并在 `0x01009734–974a` 反复读取 MCU MMIO cycle counter。某些新阻塞可能发生在 writer 内、第一次 insert 发布之前。因此保留正常 reset 向量不等于没有改变执行路径，也不能无条件称为比 witness 更可靠。

若将来实施该通道，先配内存与描述符、再按证据决定启用类别，是更清楚的分阶段设计；**现在不要预先承诺两轮刷机**。先考虑上面的既有检查点。

## (c) 草稿中必须修正的实现问题

1. **4K 与 16K 混用。** 草稿 `mem_alloc(..., 4 * PAGE_SIZE)` 在当前 16K 宿主页配置下是 64KB，不是 16KB。16KB ring 应按四个 `PT_LEAF_GRANULE` 计量；每个 GPU 叶用 `mem_pa(m, offset)` 重新求 PA，不能假设高内存跨宿主页物理连续。驱动证据 `:721–738、785–795、854–858、1184–1186`。
2. **布局算术不一致。** `[0x040a0000,0x040b0000)` 是 64KB；16KB 的右端是 `0x040a4000`。insert/extract VA 若仍选 `0x040b0000/0x040b1000`，L3 索引为 **176/177**，不是 256/257。ring 的四叶才是 160–163。新地址范围也不能用一个连续 section 宣称所有中间空洞都已映射。
3. **保持既有数据页属性。** sec9 实际含 `PTE_XN`；草稿“照抄 sec9 却不加 XN”不是同一属性。NC index 应移到 bits4:2，RW 使用现有 `PTE_UNPRIV` 编码。不要在本轮夹带其他权限变量。
4. **CPU 缓存与 GPU NC 分开核对。** `mali_low=0` 的 CPU 映射仍缓存；GPU `IDX_NC` 不会改变它。草稿称 `mem_flush()` 只 clean，与驱动 `:768–782` 的调用及注释不符。按实际 clean/invalidate 与所有权交接处理；持续消费时应避免 host 脏 extract 缓存行回写覆盖 MCU 的 insert。首轮若只观察，应优先有界快照，避免消费循环。
5. **新内存对象的管理不能省。** 若后续使用 `sect_at()`/`flush_all_sections()`，新区域必须登记，或由独立对象显式管理；二者只遍历 `gSect`。全部分配、建叶、配置同步必须在 AS0 激活/AUTO 之前完成，失败即退出启动。
6. **不动容器解析循环的推进。** 将新增准备逻辑放在全部原段装载完之后的独立步骤；保留 `offset += esize`。`continue` 才会跳过推进导致死循环；`return false` 是退出函数，不等同死循环。读环先检查两个索引均小于 size，长度与重试次数有上限，不等待日志出现。

以上驱动行号均指 `/home/lizi/IOS/hakios-mtk/mtk/mt6895/drivers/gpu/hakios.mali610.c`。

## 此前离线报告的其他审查结论

- **PROT 分支：** `r4 = *0x40003034 & 0x80` 和 `cbz` 字节核对成立；MCU/AP 别名以及读取瞬间的值仍未建立对应，不能把 AP 采样 bit7=0 提升成所有运行路径必不执行的证明。字面量扫描也不是所有计算地址访问的证明。
- **外设未映射：** 692 CPU walk 的 table unset 成立；尚不能证明该 MCU 外设请求经过 AS0，更未证明本轮执行到请求。不能由此断言 fault 记账失效。
- **MPU：** RASR 属性和区域表已核对；没有静态配置错误证据。`MPU_CTRL=3` 是 ENABLE|HFNMIENA，PRIVDEFENA=0。691 witness 绕过此初始化仍无标记，阻止将它当共同根因。Unicorn 写值是模型计算，不是硬件 MPU 状态读回。
- **config-apply：** `0x010093f6` 调 `0x01001b80`；后者逐缓存行写 `0xe000ef70`，属于缓存 clean/invalidate，不是将 `[0xac8,0xad4)` 的配置值清零。
- **BKPT：** 不能由“XNU 无服务”推导 Mali 调试状态。Armv7-M 规则分别允许 Debug state、可抢占的 DebugMonitor、否则 HardFault；在 HardFault/NMI 中且 halting debug 禁用时再遇断点可 lockup。SoC 后续是否复位仍未知。[Arm DDI0403E.e §C1.5](https://documentation-service.arm.com/static/606dc36485368c4c2b1bf62f?lang=en#page=694)
- **两个输出通道：** 已核对的异常 puts 路径执行 `r0=3; BKPT #0xab`，与 fwlog 环没有已建立的自动桥接；前者符合 SYS_WRITEC。[Arm Semihosting §6.23](https://github.com/ARM-software/abi-aa/blob/main/semihosting/semihosting.rst#623-sys_writec-0x03)
