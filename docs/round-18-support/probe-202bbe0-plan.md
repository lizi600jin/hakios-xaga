# 零成本探针：观察 `0x202bbe0` 从 1 变 0（取代整个 fwlog 方案）

**2026-11-13 21:20。手机零访问。驱动零改动。**

6.1sol 判 **C**（不投入完整 fwlog 通道），并给出这个更小的替代。我逐条核过它的事实，
**全部成立**；这个方案比我上一版好一个数量级。

---

## 1. 它说的既有检查点，我验证了

`0x202bbe0` 在**固件映像里初值是 1**（sec2 文件数据内）：

```
0x202bbd0 = 0        ← 四个 host 字段（size / data / insert / extract）
0x202bbd4 = 0
0x202bbdc = 0
0x202bbe0 = 1        ← ★ 这个
0x202bbe4 = 0
```

而 `0x1002f88` 那个 else 分支（四字段为 0 时走到）会调 `0x100ee70(0x202bbd0, 0x1c)`：

```
0x100ee70  movs r2, #0
0x100ee72  b    0x100ee62
0x100ee66  strb r2, [r0], #1     ; 逐字节写 0
0x100ee6a  subs r1, r1, #1
0x100ee6c  bhs  0x100ee66
```

范围 `[0x202bbd0, 0x202bbd0+0x1c) = [0x202bbd0, 0x202bbec)`，**包含 `0x202bbe0`**。

→ **`0x202bbe0` 会从 `1` 变成 `0`。这是固件自己做的 store，不需要我们启用任何通道。**

---

## 2. 为什么这比 fwlog 方案好

| 维度 | fwlog 方案 | `0x202bbe0` 探针 |
|---|---|---|
| 改动 | 新分配 + 6 个页表项 + 5 个 sec0 控制字 | **零改动**（只加一次读取和一行 printf） |
| 改变固件行为 | 是（启用日志类别 → 进 writer → 可能新增阻塞） | **几乎没有**（只走它本来就走的 else 分支） |
| 引入的新变量 | 2~3 个 | **0 个** |
| 判据强度 | 强（有内容） | 中强（1→0 是"执行到 `0x1002f88`"的直接证据） |
| 失败风险 | 中（新映射、新 VA、可能卡在 writer） | 极低 |

`0x1002f88` 在复位后的位置：前面只有 `cpsid` → 2 条 MMIO store → `msr psp/control` → MPU 编程
（13 个区域）→ cache 使能 → `cbz` 跳过 PROT → `b.w 0x1002aec` → 一大段初始化 → `0x1002f2a`。
**跑到这里意味着执行了几百条指令**，比现有任何判据都靠后。

## 4. 新方案的具体形态

**变量**：`mali_fwprobe=1`（默认 0）

**动作**（全部是读，除了无）：

1. 固件段加载完之后（`load_firmware()` 返回前，`gSect` 已就绪），通过 `sect_at()` 读
   `0x202bbe0`，打印初值。预期 `1`。
2. AUTO 之后、DISABLE 之前，再读一次，打印。预期 `0`。
3. 两次读之间 `mem_flush()` 保证 CPU 缓存与 DRAM 一致（这段是 cacheable，MCU 不 snoop）。

**判据**：

| 观察 | 结论 |
|---|---|
| `1 → 0` | **MCU 执行到了 `0x1002f88`** —— 复位后几百条指令，17 轮来第一个正向证据 |
| `1 → 1` | 没执行到那里（或执行到但 store 未可见；需与 `AS_FAULTSTATUS`/版本字一起看） |

**这个方案的风险点只有一个**：`0x1002f88` 那个 else 分支只有 3 条指令（`movw`/`movs`/`movt`/`bl`），
如果固件卡在 `0x1002f2a` 之前的任何地方，`0x202bbe0` 就保持 1。**阴性结果不能定位**，但阳性结果
是硬证据。

## 5. 我接受的 C 判决理由

- 「启用 mask 会改变执行行为」—— 这是我上一版最大的盲区。我一直在论证"能不能读到"，没有论证
  "读到的东西是不是我造成的"。writer 路径里有 `dsb`、有 MMIO 时间戳读取、有可能的等待循环，
  一旦进去就可能变成新的阻塞点。**用一个会改变被测对象的办法去测被测对象，是方法错误。**
- 「缓冲区配置与类别输出是两件可独立切换的事，但现在不必预付两轮刷机成本」—— 对。
- 「§14 阴性判据仍需撤回」—— 接受。mask 为零不能定位停止阶段。

## 4b. 自查补充（21:40）：`0x202bbe0` 的写者已穷举，只有两条路径

我扫了整个代码段里所有指向 `0x202bbd0..0x202bbec` 的直接引用，只有 4 处，全部指向**基址**
`0x202bbd0`：

| 引用点 | 角色 |
|---|---|
| `0x1002f36` | 初始化：`strd r1,r2,[r0]`，把 sec0 的 `[0xb0]`/`[0xbc]` 写进 `+0x00`/`+0x04` |
| `0x1002f8e` | 清零：`r0=0x202bbd0, r1=0x1c` → `0x100ee70` |
| `0x1009728` | writer（只有启用后才会执行） |
| `0x100e996` | 追加助手（同上） |

**关键：两条启动路径对 `+0x10`（`0x202bbe0`）的处理完全不同**

- **四字段有效路径**（`0x1002f3e` 之后的 `strd`）：只写 `+0x00`/`+0x04`/`+0x14`/`+0x18`，
  **不碰 `+0x10`** → `0x202bbe0` 保持镜像里的 `1`。
- **四字段无效路径**（`0x1002f88` 的 else）：`0x100ee70(0x202bbd0, 0x1c)` 把
  `[0x202bbd0, 0x202bbec)` 全部清零 → **`0x202bbe0` 从 `1` 变 `0`**。

→ 这个探针的语义是**单向**的，而且反直觉：**`1 → 0` 说明固件走到了"关闭日志"的 else 分支**，
即"固件执行了，且我们没给日志配置"。它测的不是"日志能用"，而是"**固件跑到了 `0x1002f88`**"。

**副作用提醒**：一旦以后真的去填那四个字段，这个探针就失效（会停在 1）。
两件事不能同时做 —— 这本身也是"不该在同一轮里改两个变量"的又一个例证。

## 4c. 我的盲区（自列，供 6.1sol 补充）

1. **我还没排除"固件在更早的地方也写 `0x202bbd0+0x10`"**。上面的穷举只覆盖"直接构造该地址"的
   指令；如果某处用 `add`/`ldr` 算出地址，我的扫描会漏。这条我需要 6.1sol 帮核。
2. **可见性**：sec2 是 cacheable 映射（`IDX_CACHE`），MCU 不 snoop。CPU 在 AUTO 之后读到的可能是
   自己 cache 里的旧值（`1`）。必须 `invalidate` 之后再读，而驱动现有的 `mem_flush()` 是 clean
   方向。这一点我在文档里写了，但具体用哪个函数（`FlushPoC_DcacheRegion` 还是 `invalidate`）
   需要在驱动里找可用的符号。
3. **`1 → 1` 的阴性不可定位**：固件可能卡在 `0x1002f88` 之前的任何地方，包括我完全没分析过的
   中间几千条指令。这条我在判据表里已经写明"不宣称"，但值得强调。

## 4d. 可见性问题已闭环（21:50）

三个事实拼起来，这个探针的可见性是确定的：

1. **驱动侧缓存例程自带 invalidate**。`hakios.mali610.c:56-59` 与 `:768-772` 的注释与实现都写明：
   `FlushPoC_DcacheRegion` 是 **clean 后接 invalidate**，调它一次就等于双向交接。
   所以"只能 clean、读不到 MCU 写入"这个担心不成立 —— **不需要新符号**。
2. **sec2 在 GPU 侧是 cacheable**（692 日志：`section 2 ... (rw- cached)`，`memattr index 0`）。
   我们的探针字 `0x202bbe0` 就在 sec2 内。
3. **MCU 侧对这段是 write-through**。MPU region 3（`0x02000000`，256 KB，正好覆盖 sec2/3/4）
   的 RASR = `0x110b0023` → `TEX=1 C=1 B=0 S=1` = **Normal, write-through, shareable**。
   WT 意味着 MCU 的 store 会到达内存，而不是停在它的 write-back 缓存里。

→ **MCU 写 → 到内存 → AP `FlushPoC_DcacheRegion` → AP 读到新值。** 全链路没有 write-back 陷阱。

这个也是我先前没说清的一点：我曾担心"MCU 不 snoop"，但那是针对 **AP 侧 cacheable + GPU 侧 NC**
的常规场景；这里 MCU 自己也是 WT + shareable，风险比我以为的低。

## 4e. 撤回 §4d：6.1sol 完全正确 —— region 3 是 **write-back**，而 D-cache 在复位就是开的

我把 RASR 的 S/C/B 位置搞错了。正确布局（Arm Cortex-M7 Generic User Guide Table 4.55 /
ARMv7-M RASR）：

```
31:29 保留 | 28 XN | 27 保留 | 26:24 AP | 23:22 保留 | 21:19 TEX | 18 S | 17 C | 16 B | ...
```

我原来把 **S 放在 16、B 放在 18**，正好**互换**。

按正确位置重算 `0x110b0023`：

| 字段 | 值 |
|---|---|
| XN | 1 |
| AP | `0b001`（特权 RW） |
| TEX | 1 |
| **S (bit18)** | **0** |
| **C (bit17)** | **1** |
| **B (bit16)** | **1** |
| SIZE | 2^18 = 256 KB |

`TEX=001, C=1, B=1` → **Normal, Write-Back, no Write-Allocate**（[ARM 官方表](https://developer.arm.com/documentation/dui0646/c/Cortex-M7-Peripherals/Optional-Memory-Protection-Unit/MPU-access-permission-attributes)）。
不是 write-through。我错了。

更糟的是 D-cache 的状态。固件在复位早期就把它**打开**了：

```
0x10019e2  dsb; isb
0x10019ea  mov.w r1, #0
0x10019f0  str  r1, [0xE000EF50]      ; ICIALLU
0x10019f2  ldr  r0, [CCR 0xE000ED14]
0x10019f6  orr  r1, r1, #0x20000      ; bit17 IC = 1 -> I-cache
0x10019fa  str  r1, [r0]
```

而 `0x1001a2a`（下一个被调的）只做 I/D-cache **invalidate**，不是 disable。
真正的 D-cache **关闭**函数在 `0x1001a06`（`bic r1,r1,#0x20000`），
它只被 `0x1009198` 和 `0x1009f1c` 调 —— 都是运行期路径，不在复位序列里。

→ **MCU 对 `0x202bbe0` 的写会先进它自己的 D-cache，未必落到 DRAM。**
AP 侧的 `FlushPoC_DcacheRegion` 只能清 AP 的缓存，**管不到 MCU 的**。

**结论：这个检查点在没有 MCU 侧 clean 的情况下，`1 → 0` 可能根本观察不到。§4d 作废。**
